## 선언과 권한 표

- **되는 것.** 선언 파일의 타입(`Manifest`)과 검증(`Manifest::check`): 서비스(서버 · 정적), 일정, database(스키마 · 업무 역할), 비밀(만드는 것 · 넣는 것),
  저장소에서 한 번 도는 빌드(`[build] command`), 로그인 없이 내줄 경로(서비스의 `public`, 서비스의 `path` 아래의 평범한 경로만 · 레이어와 MCP 의 경로는 못 적음),
  정적 서비스의 되돌림(`fallback`, 폴더 안의 파일만). 일정의 cron 식(다섯 칸, UTC)은 core 의 `cron` 이 읽어 맞는 때가 한 번은 오는지까지 본다.
  새 칸은 모두 없어도 되고, 없으면 앞의 선언이 그대로 읽힌다.
  값을 적을 자리가 없고 모르는 칸은 읽지 않습니다. 권한 표의 타입(`Access`)과 검증: 다섯 가지 말(none · read · read own · read write · read write own),
  표마다 모든 역할을 적어야 하고, 행 단위 규칙을 끄려면 까닭을 적어야 합니다. 문제는 찾은 것을 모두 돌려줍니다.
  CLI(`orbital check` · `plan` · `diff`)가 폴더의 두 파일을 읽어 검사하고, 세워질 SQL 과 권한 변화의 문장을 보입니다.
  본보기는 `examples/` 에 둘 있고 실제로 빌드해 서는 앱입니다(Next.js 풀스택 `todo-next`, NestJS + Vite 를 npm workspaces 로 둔 `hr-nest-vite`).
  일정(`[[schedule]]`)은 운영에서 그 시각에 레이어가 부릅니다([빌드와 프리뷰](#빌드와-프리뷰)). 일정의 `role` 은 그 서비스의 `roles` 가운데 하나여야 합니다.
- **남은 일.** 업무 역할과 표에 사람이 읽는 이름을 붙이기(승인 카드의 문장에 `manager` 대신 「팀장」). 밖으로 나가는 네트워크의 선언. 일정의 시간대.

## 역할과 권한

- **되는 것.** 역할 계획(`provision` · `grants`): 소유자, 마이그레이션, 업무 역할의 묶음, (서비스, 업무 역할)마다의 로그인. 권한은 먼저 모두 걷고 권한 표에 적힌 것만 줍니다.
  권한 검사(`check::judge`): 실제 DB 의 모습이 선언과 권한 표에 정확히 같은지 봅니다(모자라도 남아도 실패). 권한 변화의 문장(`describe::changes`).
  속성 테스트가 「어떤 선언이든 계획대로 세운 DB 는 검사를 통과한다」와 「권한을 하나라도 더하면 실패한다」를 잽니다.
  `orbital-pg` 가 계획을 실제 PostgreSQL 에 세우고(`provision` · `migrate` · `grant`), 실제 DB 의 모습을 읽어(`snapshot`) 검사에 넘깁니다.
  실제 DB 의 테스트가 「다른 역할로 바꿔 타지 못한다」, 「표를 만들거나 고치지 못한다」, 「다른 인스턴스의 database 에 접속하지 못한다」,
  「마이그레이션이 선언에 없는 스키마를 만들지 못한다」를 그 역할로 접속해 해 보는 것으로 잽니다.
  **선언에서 뺀 역할을 걷습니다.** 승격에서 새 release 의 선언에 없는 묶음 · 로그인(core 의 `stale_roles`)을 권한을 세운 뒤 지웁니다(`Admin::retire`).
  그 역할이 아직 무엇의 주인이면 운영을 건드리기 전에 승격을 멈추고 까닭을 알립니다. 권한만 남았으면 그 권한을 걷고(되돌릴 지점의 database 까지) 지웁니다.
  권한 검사는 남은 역할을 어긋남(`RoleNotDeclared`)으로 봅니다. 앞의 release 로 되돌릴 때는 그 선언으로 역할을 다시 세웁니다.
- **남은 일.** 씨앗 데이터에서 역할마다 실제로 읽어 「자기 행만」을 재기(권한 검사의 한 항목으로). 「남의 행」을 가르는 열을 선언에서 알 수 없어
  틀린 관문이 될 수 있습니다(팀장의 `read own` 처럼 같은 역할의 사람끼리 겹치는 행이 정당한 앱이 있습니다). 지을 수 있는 가장 좁은 것은 「`read own` 만 가진
  역할이 사람 없는 신원으로 읽으면 0 행」이고, 그것도 공개 행을 둔 앱을 막을 수 있어 사람의 결정을 기다립니다.
  함수 · 뷰 · 열 단위의 권한. 어떤 마이그레이션이 이미 돌았는지의 기록.
- **결정.** [로그인은 서비스와 업무 역할마다 두고 비밀번호를 두지 않는다](decisions/2026-11-25-로그인은-서비스와-업무-역할마다-두고-비밀번호를-두지-않는다.md)

## 토큰

- **되는 것.** 범위 판정(`scope::judge`): 조직과 인스턴스가 다르면 없는 것으로 답하고, 만료 시각부터 거절하고, 능력에 없는 일은 거절합니다.
  운영을 바꾸는 능력은 타입에 없어서 적어 보내도 읽히지 않습니다. 받기만 하는 능력(`source_read`)은 코드를 받고 올리지 못합니다.
  토큰은 팩토리의 서버 안에만 있고 에이전트에게 가지 않습니다([관리 서버와 CLI](#관리-서버와-cli)의 작업). 속성 테스트 다섯(git 의 길로도 다른 인스턴스에 닿지 못한다를 더했습니다).
  **작업을 닫기.** service key 로 `DELETE /v1/instances/{id}/sessions/{작업}`(SDK `work.close()`)을 부르면 그 토큰으로 도는 다음 요청부터(진행 중인 git 의
  다음 왕복까지) 401 입니다. 작업의 식별자는 토큰의 글자의 sha256 앞 16바이트이고 토큰을 열 때 함께 돌려줍니다(토큰에는 일회값이 들어 같은 초에 내도 다릅니다).
  닫은 것은 control database 의 `revoked_work` 에 적어(토큰이 살 수 있는 가장 긴 12시간만 기억) 요청마다 봅니다. 관리 서버가 다시 떠도, 다른 관리 서버가 받아도
  거둔 채입니다. 다른 팩토리의 인스턴스는 없는 것과 같습니다. 관리 서버가 여럿이면 모두 같은 토큰의 열쇠(`ORBITAL_TOKEN_KEY`)를 씁니다.
- **남은 일.** service key 를 조직마다 내고 거두는 길(지금은 서버의 설정에 적습니다).

## 승격

- **되는 것.** 승격의 규칙(`release::promote`): 레이어가 빌드했고, 권한 검사를 통과했고, 리허설이 통과한(또는 필요 없는) release 만 오릅니다.
  승인은 release 의 식별자 하나에 묶여서, 승인한 뒤 commit 이 더해지면 그 승인으로는 올리지 못합니다. 고객의 요청과 기능 업데이트는 고객이,
  보안 · 법 · 핵심 패키지의 변경은 팩토리가 승인합니다. 승격 뒤 상태 확인에 실패하면 코드를 앞의 release 로 돌리고,
  되돌리면 데이터를 잃는 마이그레이션이면 기계가 정하지 않고 사람에게 묻습니다(`after_promotion`).
  선언의 로그인 방법이 쓰는 팩토리의 키(메일 · Google)가 없으면 막습니다(`missing_keys`, `Blocker::KeyMissing`). 문장은 에이전트가 고칠 수 없는 일임을 밝힙니다.
  위쪽이 적합성 테스트를 선언했으면 그 테스트를 통과하지 못한 release 도 막습니다(`Blocker::ConformanceFailed`, [rollout](#rollout)).
- **남은 일.** 마이그레이션이 더하기만 하는지 가리기(지금은 하나라도 돌았으면 「되돌리면 데이터를 잃는다」로 봅니다).

## DB 연결

- **되는 것.** proxy(`orbital-proxy`): 듣는 자리 하나가 서비스 하나이고, 서비스가 비밀번호 없이 업무 역할의 이름만으로 붙으면 그 서비스의 로그인으로 DB 에 대신 들어갑니다.
  선언에 없는 역할은 거절하고, database 는 인스턴스의 것으로 바꾸고, 역할을 바꾸거나 복제 연결을 여는 시작 설정은 버립니다. 질의 취소도 지나갑니다.
  서명된 신원(`orbital-pg::identity`, 형식 `v2`): router 가 세션을 확인해 사람(`sub`) · 세션(`sid`) · 업무 역할(`roles`)을 실어 서명하고, 앱은 트랜잭션마다 싣습니다.
  DB 안의 `orbital.claims()` 가 읽을 때마다 서명 · 인스턴스 · 만료를 확인하고 `v2` 만 읽습니다(업무 역할이 없는 `v1` 은 바르게 서명됐어도 읽지 않습니다).
  `orbital.role()` 은 연결의 업무 역할을, `orbital.granted()` 는 그 역할이 신원의 `roles` 에 있는지를 돌려줍니다. `orbital.subject()` 는 그때만 사람을 돌려줍니다.
  **역할 제한 정책.** `[auth]` 를 선언한 인스턴스에서는 레이어가 권한을 세울 때 권한 표의 표마다(행 단위 규칙을 켠 표) 제한하는 정책 `orbital_role`
  (`USING / WITH CHECK ((SELECT orbital.granted()))`)을 둡니다. 그래서 앱이 연결을 잘못 골라도(직원의 요청이 급여 관리자의 연결을 타도) 행이 나오지 않습니다.
  권한 검사는 이 정책이 있고 레이어가 둔 것과 같은지까지 봅니다. 행 단위 규칙을 끈 표(`rls = "off: 까닭"`)에는 정책이 걸리지 않으니
  프리뷰의 결과에 「알아 둘 것」(`notices`)으로 알리되 실패로 보지 않습니다. 사람 없이 업무 역할만 실은 신원(`Claims::for_role`, 스케줄용)은
  그 역할의 「모든 행」 권한만 쓰고 「자기 행」은 읽지 못합니다. 일정을 부를 때만 싣고 HTTP 로는 내주지 않습니다.
  **`[auth]` 가 없는 인스턴스는 다릅니다.** 사용자도 신원도 없으므로 역할 제한 정책을 두지 않고, 신원 없이 「모든 행」 권한이 그대로 돕니다.
- **남은 일.** 연결 모아 쓰기. proxy 와 DB 사이를 인증서로 믿기(지금은 닿는 자리를 막는 것에 기댑니다). 서명의 열쇠 바꾸기(옛 열쇠와 새 열쇠를 함께 받는 기간).
  앱이 신원을 싣는 SDK(`db.as`). 역할 제한 정책을 다시 둘 때 표를 잠그는 시간 재기.
  일정의 `role` 은 [빌드와 프리뷰](#빌드와-프리뷰)에 적었습니다(역할만의 신원 `Claims::for_role` 을 레이어가 싣습니다).

## 로그인

- **되는 것.** router(`orbital-router`): 프리뷰와 운영마다 하나가 서고, 레이어가 알리는 서비스의 주소는 router 의 주소 + 서비스의 `path` 입니다.
  **하위 도메인.** 기준 도메인(`Options::hosting`, `ORBITAL_BASE_DOMAIN`)을 준 레이어는 주소 하나(`ORBITAL_ROUTER_LISTEN`)에서 모든 인스턴스의 요청을 받고
  `Host` 로 가릅니다: `<인스턴스>.<기준 도메인>` 은 운영, `<인스턴스>-preview.<기준 도메인>` 은 프리뷰입니다. 판정은 core 의 `host::judge_host` 이고
  `Host` 만 봅니다(`X-Forwarded-Host` · `Forwarded` 는 믿지 않고, 요청 줄에 적은 주소가 `Host` 와 대소문자 말고 다르면 가지 않습니다). 호스트 이름은
  대소문자를 가리지 않으므로 소문자로 접고 이름 끝의 `.` 하나를 뗀 뒤 견줍니다(포트는 글자까지 같아야 합니다). 모르는 호스트와
  기준 도메인 자체는 404 입니다. 그 주소가 인스턴스의 origin 이 되어 쿠키 · 로그인 링크 · `Origin` 검사 · OAuth 의 발급자와 자원 · 프리뷰와 운영의
  `url` 이 이것으로 섭니다(스킴은 `ORBITAL_PUBLIC_SCHEME`, 바깥 포트가 있으면 기준 도메인에 함께 적습니다). 속성 테스트가 「어떤 호스트든
  기준 도메인 아래의 한 조각이 아니면(대소문자와 끝의 점을 접어도) 어느 인스턴스로도 가지 않는다」를 잽니다. 기준 도메인을 주지 않은 레이어는 전처럼 인스턴스마다 포트 하나를 냅니다.
  **재우고 깨우기.** router 는 서버 서비스로 넘기기 전에 그 서비스가 떠 있는지 보고, 자고 있으면 실행기로 띄워 포트가 열릴 때까지 기다렸다가 넘깁니다
  (`AppServer`). 동시에 온 첫 요청들은 한 번의 깨우기를 함께 기다립니다. 마지막 요청의 답이 끝까지 나간 뒤 정한 시간(`ORBITAL_SLEEP_AFTER`, 기본 5분)
  요청이 없으면 프로세스를 내리고, 처리 중인 요청이 있으면 재우지 않습니다. 깨우지 못하면(뜨지 않음 · 시간 초과) 503 과 `Retry-After` 로 답하고
  다음 요청에 다시 깨우며, 기록에는 `WAKE <서비스> <갈래>` 만 남깁니다. 앱의 포트는 깰 때마다 새로 받습니다. DB proxy 와 router 는 내리지 않습니다.
  깨우기를 기다리는 요청은 서비스마다 상한(`ORBITAL_WAKE_QUEUE`, 기본 128)까지이고, 넘친 요청은 기다리지 않고 곧바로 503 · `Retry-After` · `Connection: close` 입니다.
  서비스가 둘 이상이면 서비스마다 따로 자고 깨고, 값(비밀)이 바뀌면 둘 다 내려 다음 요청에 새 값으로 깹니다. 깨우는 중에 값이 바뀌면 그 첫 요청이 끝나자마자 재웁니다.
  하위 도메인을 쓰는 레이어도 다시 뜬 뒤 운영을 같은 주소에서 자는 채로 세우고, 빌드 폴더가 없으면 503 으로 답하다 빌드 뒤 같은 주소에서 섭니다(모두 테스트가 잽니다).
  요청은 `path` 가 가장 길게 맞는 서비스로 갑니다(`auth::route`). 서버 서비스에는 흘려보내고(앱으로 가는 연결은 살려 둡니다), 정적 서비스는
  빌드 결과의 폴더에서 파일을 내주되 폴더 밖(`..`, 풀어 쓴 `%2e%2e`, 폴더 밖을 가리키는 심볼릭 링크, `.` 으로 시작하는 파일)은 내주지 않습니다.
  **신원이 앱에 닿는 길은 하나입니다.** 밖에서 온 `x-orbital-` 머리말은 `[auth]` 가 있든 없든 언제나 지우고, 세션 쿠키를 확인했을 때만
  60초짜리 서명된 신원을 `x-orbital-identity` 에 붙입니다. **공개 경로**(서비스의 `public`)는 로그인을 요구하는 서비스에서도 세션 없이 들이고,
  세션이 있어도 신원을 싣지 않으며 세션을 읽지도 않습니다(core 의 `auth::is_public`: 조각의 경계로 글자 그대로 견주고, 풀어 보면 `.` · `..` · `/` · `\` 가 드는 조각,
  `//`, `;` 이 든 조각은 공개로 보지 않습니다). **일정의 경로**는 밖에서 온 요청이면 404 이고, 앱이 같게 읽을 수 있는 모양(대소문자 · 풀어 쓴 것 · `..`)까지 막습니다
  (`auth::schedule_path`). 정적 서비스는 `fallback` 을 선언했으면 화면을 원하는 요청의 없는 파일에 그 파일을 내줍니다(`auth::fallback_file`). 레이어의 쿠키(`__Host-orbital-*`)는 앱에 넘기지 않고, 앱이 그 이름으로 심지도 못합니다.
  사용자 · 초대 · 링크 · 세션은 인스턴스의 database 안 `orbital_auth` 에 있고 인증 역할만 읽고 씁니다. 토큰은 sha256 해시로만 둡니다.
  업무 역할은 뷰 `orbital.me`(자기 한 줄)를, `directory` 의 역할만 `orbital.users` 를 읽습니다.
  로그인 한 바퀴(`/_orbital/auth/…`): 링크 요청은 초대됐는지와 상관없이 같은 답(202 `{}`)이고, 같은 이메일로는 1분에 한 번만 링크를 만듭니다.
  답을 먼저 보내고 메일은 뒤에서 보내므로, 발송이 걸리는 시간으로 초대 여부를 짐작하지 못합니다.
  쓰고 남은 줄(로그인 링크 · Google 로그인의 표 · 인가 요청 · 인가 코드 · 세션 · OAuth 토큰)은 만료나(세션은 거둔 때부터도) 하루가 지나면
  새 줄을 적을 때 함께 지웁니다(판정은 core 의 `sweep`). 거둔 OAuth 토큰은 만료까지 남겨 다시 쓰인 refresh 토큰을 알아봅니다.
  링크는 15분, 한 번, 요청한 브라우저에서만 열리고, 세션 쿠키는 `HttpOnly; Secure; SameSite=Lax; Path=/` 입니다. 상태를 바꾸는 `POST` 는 `Origin` 이
  router 의 주소일 때만 받습니다. 로그인이 필요한 서비스는 세션 없이 화면을 열면 `login_path?next=…` 로, 화면이 아닌 요청은 401 로 답합니다.
  프리뷰에는 씨앗 사용자(`db/seed/users.toml`)가 들어가고, 씨앗 사용자로 들어가는 길(`/_orbital/preview/sign-in`, 작업의 `previewSignIn`)은 프리뷰에만 있습니다.
  팩토리는 service key 로 운영의 사용자를 다룹니다: 초대(`POST /v1/instances/{id}/users`), 목록(`GET …/users`, 마지막으로 들어온 때까지),
  업무 역할 바꾸기(`PUT …/users/{user}/roles`, 다음 요청의 신원부터 반영), 빼기(`DELETE …/users/{user}`, 막고 세션을 모두 거둠).
  SDK 는 `users.invite` · `list` · `setRoles` · `remove` 입니다. 운영이 아직 서지 않았으면 409 로 까닭을 알립니다. 에이전트의 토큰에는 이 길이 없습니다.
  신원을 레이어 밖으로 내주는 길은 없습니다.
  **MCP 의 인가(OAuth 2.1, MCP 인가 규격 2026-07-28 판).** `[auth.mcp]`(`service` · `path` · `consent_path` · `dynamic_registration`)를 선언한
  인스턴스에서 router 가 자원 서버를, Orbital Auth 가 인가 서버를 맡습니다. 발급자(`iss`)는 그 router 의 주소입니다.
  자원 서버: RFC 9728 메타데이터(`/.well-known/oauth-protected-resource[/<MCP 경로>]`), MCP 주소는 쿠키를 보지 않고 `Authorization: Bearer` 만 보며,
  토큰이 없거나 틀리면 401 과 `WWW-Authenticate: Bearer resource_metadata=…, scope="mcp"`(틀렸으면 `error="invalid_token"`)입니다.
  토큰은 이 자원(router 의 주소 + MCP 경로)용인지까지 보고, 신원(`v2`, 클라이언트 `cid`)에 서명해 앱에 넘기며 `Authorization` 머리말은 넘기지 않습니다.
  DB 의 `orbital.client()` 는 MCP 로 들어온 요청의 클라이언트입니다(브라우저 세션이면 NULL).
  인가 서버: RFC 8414 메타데이터, 인가 코드 + PKCE S256 만, redirect 는 등록된 것과 글자까지 같아야 하고 `https` 이거나 `localhost` 여야 합니다.
  클라이언트나 redirect 가 틀린 인가 요청은 그 redirect 로 보내지 않고 400 으로 멈춥니다. 인가 응답에 `iss` 를 싣습니다(RFC 9207).
  동의는 앱의 화면(`consent_path`)이 `/_orbital/oauth/requests/<id>` 를 읽고 승인 · 거절하며, 그 요청을 연 사용자의 세션에서만, 10분, 한 번입니다.
  코드는 5분 · 한 번이고 다시 쓰이면 그 코드로 낸 토큰을 모두 거둡니다. access 는 1시간, refresh 는 30일이고 쓸 때마다 갈며 다시 쓰이면 그 승인 전체를 거둡니다.
  토큰 · 코드 · 요청의 식별자는 해시로만 둡니다. 사용자는 `/_orbital/oauth/grants` 로 제 승인을 보고 거두고, 사용자를 빼면 그 승인과 토큰도 거둡니다.
  클라이언트 등록: 팩토리의 미리 등록(`POST /v1/instances/{id}/oauth-clients`, SDK `oauthClients.register`) → Client ID Metadata Documents
  (받아 오는 일은 갈아 끼우는 자리 `DocumentFetcher`. 실제 구현은 `https` 만 · 사설/이 기계/링크 로컬 주소 거절(이름을 푼 뒤에도) · 넘겨주기를 따라가지 않음 ·
  5초 · 64KB, 받아 온 문서는 그 답의 `Cache-Control: max-age` 만큼 기억하되 5분에서 하루 사이로 묶음, 말하지 않았으면 5분) → 동적 등록(RFC 7591, 끌 수 있음.
  인스턴스마다 1분에 열 번, 넘으면 429 와 `Retry-After`. 살아 있는 동적 클라이언트는 200개까지. 한 번도 승인받지 못한 것은 하루 뒤 다음 등록 때 지웁니다).
  PKCE 의 해시(SHA-256)는 어댑터가 `sha2` 로 계산하고 core 는 verifier 의 모양과 계산된 값이 맞는지만 봅니다(RFC 7636 부록 B 의 값으로 잽니다).
  다른 주소의 브라우저(CORS)에는 쿠키를 보지 않는 주소만 엽니다: `/.well-known/oauth-*`, `POST /_orbital/oauth/token` · `register`.
  `Access-Control-Allow-Origin: *` 이고 자격 증명(credentials)은 열지 않습니다. 로그인 · 동의 · 승인 목록은 열지 않습니다.
  `orbital_auth` 의 표와 `orbital.me` · `orbital.users` 뷰의 주인은 로그인하지 못하는 주인 역할(`Names::auth_owner`)이고, 앱의 표에는 닿지 못합니다.
  앱의 화면은 `@harmony/orbital/app`(`sendLoginLink` · `me` · `logout` · `consentRequest` · `approve` · `deny` · `grants` · `revokeGrant`,
  서버 쪽 `identityOf`)으로 같은 주소의 레이어를 부릅니다. 본보기 스캐폴드의 로그인 · 동의 화면이 이것을 쓰고, 스킬에 참고 문서 `references/auth.md` 가 있습니다.
  **팩토리의 키.** 레이어는 공용 발송 도메인도 공용 Google 클라이언트도 갖지 않습니다. 팩토리는 service key 로 `PUT /v1/settings/auth`
  (SDK `settings.auth.get` · `set`)에 Resend 의 키 · 보내는 주소 · 이름과 Google 클라이언트의 ID · 비밀을 넣습니다. 팩토리마다 한 벌이고,
  칸을 `null` 로 보내면 지우고 보내지 않은 칸은 그대로입니다. 비밀은 어떤 답 · 기록 · 오류에도 돌아오지 않고, 레이어의 기록(control database 의 `factory_settings`)에
  봉인한 글로만 있습니다(XChaCha20-Poly1305, 조직과 칸을 함께 묶어 다른 조직의 줄에 옮겨 붙이면 풀리지 않음, 열쇠는 `ORBITAL_SEAL_KEY`).
  열쇠가 없는 레이어에서는 넣는 길이 409 입니다. 에이전트의 토큰에는 이 길이 없습니다(404). 열쇠를 바꿀 때는 옛 열쇠(`ORBITAL_SEAL_KEY_PREVIOUS`)를 함께 주고
  한 번 띄우면 옛 열쇠로만 풀리는 줄(설정 · 금고 · 운영의 신원 열쇠 · 레이어가 만든 비밀)을 새 열쇠로 다시 봉인해 적고 줄의 수를 찍습니다([런북](runbook/봉인의-열쇠-바꾸기.md)).
  키가 없으면 `email_link` · `google` 을 선언한 release 는 운영에 오르지 못하고, 프리뷰는 섭니다. 오른 뒤 키를 지우면 메일은 나가지 않고(답은 같은 202),
  Google 의 시작 주소는 404 이며, 다음 승격은 막힙니다.
  **메일(Resend).** 운영의 router 는 그 인스턴스의 팩토리 키와 보내는 주소로 보냅니다. 글은 레이어의 기본 글(앱의 이름 · 링크 · 15분, text 와 html)이고,
  같은 링크를 두 번 보내지 않게 링크의 해시에서 지은 `Idempotency-Key` 를 싣습니다. 보내지 못해도 링크 요청의 답은 같고, router 의 기록에는
  `MAIL <갈래> <상태>` 만 남깁니다. **프리뷰의 router 는 메일을 보내지 않습니다**(앞에서는 프리뷰도 메일함에 쌓았습니다).
  개발용 메일함(`ORBITAL_DEV_MAIL=outbox`, `ORBITAL_HOME/outbox.jsonl`)은 명시해 켠 레이어에서만 메일 키를 대신합니다.
  **Google 로그인**(`methods = ["email_link", "google"]`, 운영에만). 앱의 화면이 `/_orbital/auth/google/start?next=…` 로 보내면 router 가 브라우저의
  표식을 심고 레이어가 서명한 `state`(인스턴스 · 운영 · `next` · 표식의 해시 · `nonce` 의 해시 · 10분)를 실어 Google 로 보냅니다.
  콜백은 레이어의 주소 하나(`/v1/auth/google/callback`, 바깥 주소는 `ORBITAL_PUBLIC_URL`)이고, 팩토리의 키로 `code` 를 바꿔 받은 `id_token` 을
  core 가 판정합니다(`iss` · `aud`(여럿이면 `azp`) · `exp` · `nonce` · `email_verified`). 통과하면 그 인스턴스에 한 번 쓰는 표(60초, 해시로만)를 적고
  router 의 `/_orbital/auth/google/finish` 로 보내며, router 는 요청한 브라우저에서 한 번만 받아 이메일 링크와 같은 규칙으로 들입니다.
  Google 의 계정(`sub`)으로 먼저 찾고, 없으면 같은 이메일의 사용자에 수단을 더하고(`login` 의 `google` 줄), 처음 오는 이메일은 초대가 있어야 합니다.
  위조하거나 만료된 `state` 로는 콜백이 Google 을 부르지도 표를 적지도 않습니다(400). 앱의 SDK 는 `googleSignInUrl(next)` 입니다.
- **남은 일.** 실제 Resend 와 실제 Google 에 붙어 보기(팩토리의 키가 있어야 합니다. 테스트는 가짜 서버로 잽니다).
  선언에 앱의 이름을 적는 칸(지금 메일의 글은 인스턴스가 속한 app 의 이름을 씁니다).
  HTTPS 종단 · 인증서 · DNS · 사용자 정의 도메인(하위 도메인은 `Host` 로 가르기까지만 있고, 테스트는 `127.0.0.1` 의 한 포트에 `Host` 를 실어 잽니다).
  실제 브라우저는 Chromium 158 로 쟀습니다: `http://127.0.0.1` 의 운영에서도 `__Host-orbital-session` 을 받아 싣고, 다른 origin 의 화면이 보낸 로그아웃 · 링크 요청은
  `Origin` 으로 403 입니다([실제 프레임워크에서 본 것](실제-프레임워크에서-본-것.md)). Firefox · Safari 와 하위 도메인의 이름으로는 재지 않았습니다. WebSocket(router 가 `Upgrade` 를 지웁니다). 서비스마다 재우지 않게 하는 선언.
  깨우는 동안 요청은 깨우는 문을 기다립니다(깨우는 시간의 두 배까지, 상한까지). 깨운 첫 요청은 앱이 뜨는 시간만큼 늦습니다.
  레이어 전체의 연결 수에는 아직 상한이 없습니다(깨우기를 기다리는 것만 묶었습니다).
  세션 조회의 캐시(거둔 세션이 다음 요청부터 끊기는 규칙이 먼저입니다).
  MCP 의 인가에서 남은 것: metadata 문서를 실제 네트워크로 받아 오는 길은 재지 않았습니다(테스트는 가짜 가져오기). 토큰 폐기(RFC 7009) · 조회(RFC 7662)의 주소,
  scope 를 `mcp` 보다 잘게 나누기, 기밀 클라이언트, IPv6 주소로 적힌 metadata 문서(지금은 받지 않습니다).
  동적 등록의 한도는 인스턴스마다라서, 한 인스턴스를 두드리는 쪽을 주소마다 가르지 않습니다. 본보기 스캐폴드는 아직 `[auth.mcp]` 를 선언하지 않아 동의 화면은 본보기로만 있습니다.
  `orbital_auth` 의 주인 역할은 제 표에 쓰는 권한을 가집니다(외래 키의 검사와 `ON DELETE CASCADE` 가 주인으로 돌기 때문). 선언에서 `[auth]` 를 빼면 남는 주인 역할은 표를 가진 채라 `DROP ROLE` 이 되지 않을 것입니다(추측, 재지 않았습니다. `stale_roles` 는 찾기만 합니다).
  링크 요청의 답은 같지만, 초대된 쪽이 DB 에 한 줄 더 쓰는 만큼의 시간 차는 재지 않았습니다.
- **결정.** [메일과 Google 은 팩토리의 키로 한다](decisions/2026-11-25-메일과-Google-은-팩토리의-키로-한다.md)

## 리허설과 되돌리기

- **되는 것.** 리허설(`Admin::rehearse`): 운영 DB 를 복제한 사본에 마이그레이션을 돌리고 통과 여부 · 걸린 시간 · 멈춘 자리 · SQLSTATE · 표마다의 행 수만 돌려줍니다.
  사본은 만들자마자 아무도 접속하지 못하게 막고 끝나면 지웁니다. 되돌릴 지점(`mark` · `restore` · `forget`): 승격 직전의 DB 를 떠 두고, 돌아갈 때 이름을 바꿔 운영 자리에 놓습니다.
- **남은 일.** 복제하는 동안 proxy 가 요청을 붙잡기(지금은 운영 DB 의 문을 잠깐 닫고 붙어 있는 연결을 끊은 뒤 복제합니다. `quiesce` · `resume`). 잠금 시간 재기.
  XFS 에서의 복제 시간 재기. 앞의 코드와도 맞는 마이그레이션(열을 더하기만 하는 것)인지 가려 승인 카드에 적기.
- **결정.** [PostgreSQL 은 가장 높은 버전을 쓴다](decisions/2026-11-25-PostgreSQL-은-가장-높은-버전을-쓴다.md)

## 코드 저장

- **되는 것.** 인스턴스마다 레이어 안에 git 이력을 둡니다(`SourceStore`). 스캐폴드의 한 버전에서 갈라지고 그 기준점을 기억합니다.
  git 이 바로 붙는 길(smart HTTP v0: `…/git/info/refs`, `git-upload-pack`, `git-receive-pack`)로 받고 올립니다. 길의 판정(`git::route`)은 core 가 합니다.
  받기에는 `main` 과 열린 rollout 의 `update` 만 보이고 레이어가 안에서 쓰는 ref(`refs/orbital/**`)는 이름으로도 식별자로도 받지 못합니다.
  올리기는 git 과 묶음(git bundle)의 두 길이 한 자리를 지납니다: 받는 ref 는 `main` 하나이고 앞으로만 간다는 판정(`git::judge_push`)을 core 가 하고,
  객체는 격리한 폴더에 받아(`index-pack --strict`) 닿는 객체가 모두 있는지와 앞으로 가는지를 본 뒤에야 저장소로 옮깁니다(`ingest`).
  깨진 pack · 너무 큰 요청 · 받지 않는 ref 는 저장소에 아무것도 남기지 않고, 까닭은 `git push` 에 그대로 보입니다. 저장소의 훅은 어느 git 명령에서도 돌지 않습니다.
  git 이 줄여(gzip) 보낸 받기 요청은 풀어서 받고, 풀린 크기가 상한을 넘으면 그 자리에서 풀기를 멈춥니다(실제 `git` 의 줄인 요청과 압축 폭탄으로 잽니다).
  요청 본문은 상한(`upload_limit`, 기본 64MiB)까지 받고 한 바이트라도 넘으면 413 입니다. 파일 3194 개 · 이력 21MiB 의 저장소를 올리는 데 1.8초, 받는 데 1.1초입니다.
  commit 하나에서 선언 · 권한 표 · 마이그레이션 · 씨앗 데이터를 읽어 검증하고(`assemble`), 인스턴스와 commit 에서 release 의 식별자를 짓습니다.
  스캐폴드의 새 commit(업데이트)을 받아 두고(`fetch_upstream`), 인스턴스의 `main` 에 기계적으로 합치며(`merge`), release 가 업데이트를 담는지 판정합니다(`descends`).
  받기의 답(pack)은 다 만들지 않고 `git upload-pack` 의 출력을 그대로 흘려 보냅니다(조각 전송). 첫 출력 전에 git 이 거절하면(`ERR`) 422 로 답합니다.
  객체를 주고받는 `POST` 는 그 길의 git 의 `Content-Type`(`application/x-git-…-request`)만 받고, 아니면 415 입니다(브라우저의 폼이 닿지 못합니다).
  `merge` · `newest_upstream` · `descends` · `fetch_upstream` 을 `orbital-source` 의 테스트가 직접 잽니다(충돌 · 이미 담음 · 그사이 옮겨진 `main` · 위쪽이 여럿).
- **남은 일.** 프로토콜 v2 와 진행 표시(side-band). 얕은 저장소에서 올리기(지금은 받지 않습니다). 묶음의 길은 SDK 의 묶음 테스트와 레이어의 테스트가 쓰는 동안 남깁니다.
  요청 본문은 상한까지 메모리에 모읍니다(`tiny_http` 가 본문을 다 받은 뒤 넘깁니다). 흘려 보내기 시작한 뒤에 git 이 실패하면 받는 쪽은 끊긴 pack 으로 압니다.
  큰 저장소에서 메모리가 줄어든 정도는 재지 않았습니다. 상한을 넘는 올리기에 git 은 `HTTP 413` 만 보입니다.
- **결정.** [코드는 묶음으로 주고받고 프리뷰는 따로 선 인스턴스다](decisions/2026-11-25-코드는-묶음으로-주고받고-프리뷰는-따로-선-인스턴스다.md),
  [에이전트는 팩토리의 도구와 git 만 쓰고 레이어를 직접 부르지 않는다](decisions/2026-11-25-에이전트는-팩토리의-도구와-git-만-쓰고-레이어를-직접-부르지-않는다.md)

## 빌드와 프리뷰

- **되는 것.** release 를 그 commit 에서 직접 빌드합니다. 에이전트가 올린 빌드 결과는 받지 않습니다. 프리뷰(`Layer::preview`)는 뜻 없는 식별자로
  database 와 역할을 따로 세워 마이그레이션을 처음부터 돌리고, 씨앗 데이터를 넣고, 권한을 세워 권한 검사를 돌린 뒤 서버를 띄워 주소를 돌려줍니다.
  결과에는 어긋난 것, 운영과 견준 권한 변화의 문장, 승격을 막는 것이 함께 옵니다. 서버 서비스마다 proxy 가 하나 서고, 앱에는 그 주소와 레이어가 만든 비밀, 그 단계의 밖에서 넣는 비밀([비밀](#비밀))만 건넵니다.
  실행기는 갈아 끼우는 자리(`Runner`)이고 개발용 실행기(`LocalRunner`)가 있습니다. 환경을 비우고, 명령이 낳은 프로세스까지 한 묶음으로 멈춥니다.
  프리뷰와 승격은 서버가 실제로 뜨는 것을 본 뒤에 끝나고, 그 뒤로는 요청이 없으면 자고 첫 요청에 깹니다([로그인](#로그인)의 router).
  빌드에는 레이어의 운영자가 정한 환경(`ORBITAL_BUILD_ENV` 에 적은 이름: 레지스트리 · 프록시 · CA 묶음)만 더 건네고, 서버와 적합성 테스트에는 건네지 않습니다.
  `ORBITAL_` · `PG` 로 시작하는 이름과 `PATH` · `HOME` 은 받지 않습니다. 빌드의 홈(`~/.npm` 같은 캐시)은 인스턴스마다 `ORBITAL_HOME/caches/<인스턴스>` 에 따로 두고
  빌드 폴더 밖이라 서버에 실리지 않습니다. 빌드는 레이어의 자물쇠 밖에서 돌아 한 인스턴스의 빌드가 다른 요청을 막지 않고, 같은 인스턴스의 빌드만 한 줄로 섭니다.
  프리뷰나 승격이 서면 떠 있지 않은 release 의 빌드 폴더를 걷고, 인스턴스를 지우면 빌드 폴더 · 캐시 · 기록을 걷습니다.
  빌드와 서버의 로그를 돌려줄 때 레이어의 폴더 경로는 `<레이어>` 로 가립니다.
  최상위 `[build] command` 는 서비스의 빌드보다 먼저 저장소에서 한 번 돌고(같은 실행기 · 환경 · 홈), 실패하면 서비스의 빌드는 돌지 않습니다(로그 `build`).
  서버 서비스에는 듣는 주소로 `HOST` · `HOSTNAME`(`127.0.0.1`)을 건넵니다. `next start` 는 둘 다 읽지 않아 본보기가 `-H 127.0.0.1` 을 적고, 테스트가 앱이 loopback 에서만 듣는지 봅니다.
  **일정.** `orbitald` 가 분이 바뀔 때마다 운영의 인스턴스 가운데 때가 된 일정을 router 를 거쳐 `POST` 로 부르고 `x-orbital-schedule` 을 싣습니다(자는 서비스는 깨웁니다).
  사람의 신원은 싣지 않고, 프리뷰는 부르지 않으며, 놓친 때는 한 번만 부르고, 부르기 전에 다음 때를 적어 같은 때를 두 번 부르지 않습니다. 실패와 시간 초과
  (`ORBITAL_SCHEDULE_TIMEOUT`, 기본 10분)는 적고 다시 부르지 않습니다. 팩토리는 `production.get` 의 `schedules` 에서 역할 · 다음 때 · 마지막 실행을 봅니다.
  일정에 `role` 을 적으면 사람 없이 그 역할만 실린 서명된 신원(수명은 제한 시간)을 함께 싣습니다. `[auth]` 를 선언한 인스턴스에서 역할 제한 정책을 지나
  그 역할의 「모든 행」 권한으로 읽고 씁니다(역할 없는 일정은 같은 연결이어도 한 행도 보지 못합니다). 일정이 생기거나 역할이 바뀌면 승인 카드의 권한 변화
  맨 앞에 「이번 변경으로 일정 … 이 `역할` 역할로 돕니다」가 섭니다. 본보기 `hr-nest-vite` 의 급여 일이 `payroll_admin` 으로 이달의 명세를 만듭니다.
  실제 프레임워크로 잰 것과 구멍은 [실제 프레임워크에서 본 것](실제-프레임워크에서-본-것.md)에 있습니다(`npm run test:frameworks`).
- **남은 일.** 격리하는 실행기. 개발용 실행기는 이 기계의 프로세스로 돌리고 **격리하지 않습니다**(기획안 11절의 0번이 정합니다).
  그래서 인스턴스마다 캐시와 빌드 폴더의 자리는 따로지만 한 인스턴스의 빌드가 다른 인스턴스의 폴더를 읽고 쓰는 것을 막지 못하고,
  `-H 127.0.0.1` 없이 띄운 `next start` 처럼 모든 주소에서 듣는 앱을 막지 못합니다.
  일정의 시간대 · 손으로 한 번 부르기 · 실패를 팩토리에 알리는 길.
- **결정.** [일정은 레이어가 부르고 그 경로는 밖에서 닿지 못한다](decisions/2026-11-25-일정은-레이어가-부르고-그-경로는-밖에서-닿지-못한다.md)

## 비밀

- **되는 것.** 선언의 `[secrets] external` 에 이름만 적은 비밀을 사람이 넣고, 앱의 서버 서비스가 같은 이름의 환경 변수로 받습니다. 끝 기준은
  「에이전트가 값을 한 번도 보지 않고 운영에 오른다」입니다. 값은 인스턴스와 단계(프리뷰 · 운영)마다 따로이고 서로 넘어가지 않습니다(프리뷰의 값은 에이전트가 본다고 봅니다).
  **금고**(control database 의 `vault_value`, (인스턴스, 단계, 이름)마다 한 줄)에 봉인한 글로만 둡니다. 봉인은 조직 · 인스턴스 · 단계 · 이름을 묶어, 다른 자리에 옮겨 심으면 풀리지 않습니다.
  열쇠(`ORBITAL_SEAL_KEY`)가 없으면 값을 넣지 못하고(409, 무엇을 고칠지 알림), 밖에서 넣는 비밀을 선언한 release 는 운영에 오르지 못합니다.
  **들어오는 길은 둘입니다.** service key 로 `PUT /v1/instances/{id}/secrets/{name}`(`{stage, value}`, 지우기는 `DELETE …?stage=`)와,
  **입력 표**: service key 로 `POST …/secrets/{name}/entries`(`{stage}`) → `{url, ticket, expires_at}`. 표는 난수 32바이트이고 sha256 으로만 두며,
  인스턴스 · 이름 · 단계 하나에 묶이고 10분 안에 한 번 씁니다. 사람의 브라우저가 고정된 주소(`POST /v1/secret-entries`)에 `Authorization: Bearer <표>` 를 실어
  `{value}` 를 레이어에 바로 보냅니다. 표를 경로에 싣지 않아 레이어 앞의 프록시가 남기는 접근 기록에 남지 않습니다(경로에 표를 적은 앞의 모양은 404).
  이 길은 쿠키를 보지 않고 표만 보며 CORS 를 엽니다(`*`, 자격 증명 없이, 사전 요청이 `authorization` 머리말을 받음). 본문이 이름이나 단계를 바꾸면 거절합니다.
  **나가는 길은 없습니다.** `GET …/secrets` 는 이름마다 `{name, declared, requested?, preview: {set, set_at?}, production: {set, set_at?}}` 만 돌려줍니다.
  값의 한도는 core 가 판정합니다(비어 있지 않음 · 64 KiB · NUL 없음). 오류 문구는 본문을 되풀이하지 않습니다(JSON 의 오류 · 틀린 이름도).
  **요청.** 작업의 토큰(`secrets_request`, SDK 의 `Work.secrets.request`)이나 service key 로 `POST …/secrets/{name}/request`(`{reason}`, 500자). 그 인스턴스의 release 가 선언한 이름만 받고,
  아니면 「`[secrets] external` 에 적고 프리뷰를 세운 뒤」라고 알립니다. 토큰은 목록을 보고 요청만 합니다. 넣기 · 지우기 · 입력 표는 403(core 의 `SecretsWrite`)입니다.
  **앱에 잇기.** 프리뷰는 프리뷰의 칸을, 운영은 운영의 칸을 서버 서비스를 띄울 때마다 금고에서 읽어 넣습니다. 빌드와 마이그레이션에는 넣지 않습니다.
  프리뷰는 값이 없어도 서고 `missing_secrets` 로 알립니다. 운영은 하나라도 빠지면 승격하지 못합니다(`Blocker::SecretMissing`). 실패한 승격의 되돌리기와
  관리 서버가 다시 뜰 때도 같은 판정을 지나 값 없이 세우지 않습니다. 값을 넣거나 바꾸면 그 단계의 서버를 재워 다음 요청이 새 값으로 깹니다.
  지금 운영이 쓰는 비밀의 운영 값은 지우지 못합니다(409). 인스턴스를 지우면 그 값 · 요청 · 입력 표도 지웁니다.
  승인 카드에 설 기다리는 release 에는 이번 변경으로 앱이 새로 받는 비밀의 이름(`new_secrets`)이 실립니다. SDK 는 `secrets.list` · `request` · `set` · `remove` · `entry` 입니다.
  **봉인의 열쇠를 바꾸기.** 새 열쇠와 옛 열쇠(`ORBITAL_SEAL_KEY_PREVIOUS`)를 함께 주고 띄우면 옛 열쇠로만 풀리는 줄을 새 열쇠로 다시 봉인해(임시 파일에 쓰고 옮김)
  줄의 수를 찍고, 어느 열쇠로도 풀리지 않는 줄은 건드리지 않고 이름만 알립니다. 마친 뒤에는 옛 열쇠 없이 뜹니다([런북](runbook/봉인의-열쇠-바꾸기.md)).
- **남은 일.** 금고를 파일에서 DB 로 옮기기.
  밖으로 나가는 네트워크의 제한(승인된 운영의 코드가 값을 밖으로 보내는 것은 막지 못합니다). 요청을 거두는 길. 정적 서비스에 비밀을 건네기.
  값을 바꾸는 순간 깨우는 중이던 프로세스는 바뀌기 전의 값을 읽을 수 있습니다(첫 요청이 끝나면 곧바로 재우는 것을 테스트가 잽니다. 그 첫 요청 하나는 옛 값으로 답합니다).
- **결정.** [비밀은 단계마다 따로 넣고 입력 표로 레이어에 바로 보낸다](decisions/2026-11-25-비밀은-단계마다-따로-넣고-입력-표로-레이어에-바로-보낸다.md)

## rollout

- **되는 것.** 끝 기준은 「한 곳이 실패하면 나머지가 멈추고, 적합성 테스트를 통과한 곳만 운영에 오른다」입니다.
  rollout 은 `{앱, 업데이트 commit, change, 물결}` 이고, 업데이트가 인스턴스마다 어디까지 갔는지를 갖고 관문을 지킵니다. **레이어는 에이전트를 돌리지 않습니다.**
  포크를 고치는 에이전트는 팩토리(밀기)나 고객(당기기)의 플랫폼에서 돌고, 팩토리가 인스턴스 하나로 좁혀 연 작업을 거쳐 들어옵니다. 업데이트는 git 에서 `update` 로 보입니다.
  「적용됐다」의 뜻은 하나입니다. release 의 commit 이 업데이트 commit 을 조상으로 담습니다. 담지 않은 release 는 rollout 과 무관하게 오르내립니다.
  **상태와 판정**(core 의 `rollout`): `waiting` → `applied` → `previewed` → `passed` → `promoted`, 어디서든 `failed{까닭}`(권한 검사 · 적합성 테스트 · 승격 뒤 되돌려짐).
  인스턴스 하나가 실패하면 rollout 이 멈추고(`halted`), 멈춘 동안에는 어느 인스턴스도 이 업데이트를 담은 release 를 올리지 못합니다(이미 오른 곳은 그대로).
  팩토리가 다시 열면(`resume`) 실패한 곳은 `waiting` 부터 고친 release 로 다시 지납니다. 거두면(`cancel`) 아직 오르지 않은 곳은 그 자리에 남고 어떤 사건도 받지 않습니다.
  모두 오르면 끝납니다(`done`). 앞 물결이 모두 오르기 전에는 뒤 물결이 오르지 못합니다. 이 업데이트를 담은 release 는 rollout 의 `change` 로만 오르고,
  승인자는 지금의 `Change::approver` 그대로입니다(기능 업데이트는 고객, 법 · 보안 · 핵심 패키지는 팩토리). 속성 테스트가 사건의 임의 순서로
  「멈춘 rollout 에서는 새 승격이 없다」, 「적합성 테스트를 통과하지 않은 인스턴스는 승격에 닿지 못한다」, 「뒤 물결은 앞 물결이 모두 오른 뒤에만 오른다」를 잽니다.
  **합치기.** `apply` 는 인스턴스의 `main` 에 업데이트를 `git merge` 의 판정으로 합칩니다. 충돌하면 인스턴스를 건드리지 않고 충돌한 파일의 이름만 돌려줍니다.
  그때 에이전트는 받은 저장소의 `origin/update` 를 합쳐 풀어 올리고, 올린 commit 이 업데이트를 담으면 적용된 것입니다.
  **적합성 테스트**(`[conformance] run` · `files`, 폴더는 저장소 안의 상대 경로). 명령과 폴더는 인스턴스가 아니라 위쪽에서 가져옵니다.
  release 가 담은 가장 새 위쪽 commit 의 선언을 읽고 빈 자리에 그 폴더만 놓아 돌리므로, 에이전트가 테스트를 고치거나 지우거나 옆에 무엇을 끼워 넣어도 소용없습니다. 인스턴스는 프리뷰의 주소로만 잽니다.
  위쪽이 선언했으면 모든 프리뷰에서 돌고, 통과하지 못하면(실패 · 돌지 않음 · 제한 시간 120초 초과) 승격을 요청하지도 오르지도 못합니다.
  빌드와 같은 실행기로 환경을 비워 돌리고 프리뷰의 주소(`ORBITAL_PREVIEW_URL`)만 건넵니다. 결과는 통과 여부 · 걸린 시간 · 출력의 끝(4000자)만 프리뷰의 답(`conformance`)에 남습니다.
  **범위.** 만들기 · 합치기 · 다시 열기 · 거두기는 service key 만 합니다(core 의 `RolloutManage`). 에이전트의 토큰은 자기 인스턴스의 진행
  (`GET /v1/instances/{id}/rollout`: rollout · 업데이트 commit · change · 멈췄는지 · 상태)만 봅니다. 다른 앱의 인스턴스는 넣지 못하고,
  다른 팩토리의 rollout 은 없는 것으로 답합니다. 한 인스턴스는 같은 앱의 열린 rollout 하나에만 듭니다.
  HTTP 는 `POST /v1/apps/{app}/rollouts` · `GET /v1/rollouts/{id}` · `POST …/instances/{instance}/apply` · `…/resume` · `…/cancel`, SDK 는 `rollouts.create` · `get` · `apply` · `resume` · `cancel` 입니다.
  기다리는 release 에는 어느 rollout 의 것인지(`rollout`)가 실립니다. rollout 은 레이어의 기록에 있어 관리 서버가 다시 떠도 남습니다.
  업데이트를 담은 release 의 프리뷰에서 권한 검사가 어긋나면 그 인스턴스가 `failed{access_check_failed}` 가 되고 rollout 이 멈추는 것을 서버 테스트가 잽니다.
- **남은 일.** 물결을 자동으로 넓히기(지금은 팩토리가 물결을 정하고, 앞 물결이 모두 올라야 뒤 물결이 오를 수 있게 될 뿐입니다). 실패 몇 개까지 견디는 문턱.
  적합성 테스트는 인스턴스의 코드를 부르므로 실행기의 격리에 기대고, 개발용 실행기는 격리하지 않습니다. 프리뷰에서 통과한 것이 운영에서의 통과를 보장하지 않습니다.
  운영이 선 뒤 상태를 오래 지켜보는 일(지금은 승격 직후 서버가 뜨는지만 봅니다). 업데이트 하나를 여러 앱에 걸쳐 미는 것. 팩토리의 본보기에는 아직 rollout 의 도구가 없습니다.
  끝난 rollout 의 업데이트(`origin/update`)는 묶음에 남습니다(거두면 뺍니다).
- **결정.** [rollout 은 진행과 관문만 갖고 적합성 테스트는 위쪽의 것으로 돌린다](decisions/2026-11-25-rollout-은-진행과-관문만-갖고-적합성-테스트는-위쪽의-것으로-돌린다.md)

## 백업과 복구

- **되는 것.** 끝 기준은 「복구 훈련이 사람 손 없이 통과한다」입니다. 실제 고객의 데이터는 이것이 통과한 뒤에 받습니다.
  도구는 PostgreSQL 의 것만 씁니다(`orbital-backup`). 백업을 두는 곳은 갈아 끼우는 자리(`Store`)이고 구현은 이 기계의 폴더(`LocalStore`, `ORBITAL_BACKUP_DIR`) 하나입니다.
  **백업 한 벌**은 기반 백업(`pg_basebackup`, WAL 포함) + 그 뒤에 보관한 WAL(운영 클러스터의 `archive_command`) + 코드 저장소의 묶음
  (`records.tar`: `sources` · `apps`)입니다. 레이어의 기록은 운영 클러스터 안의 control database 에 있어 기반 백업과 WAL 에 함께 들고, 그래서 되살린 시점의 DB 와
  그 시점의 기록이 같은 때의 것입니다(봉인한 글은 봉인한 그대로). 봉인의 열쇠 · service key · 토큰의 열쇠는 넣지 않습니다. 운영의 신원 열쇠는 기록에는 봉인한 글로,
  인스턴스의 database(`orbital.instance.signing_key`, 레이어의 스키마)에는 신원의 검증 함수가 쓰는 평문으로 있어, 그 database 와 함께 백업에 듭니다.
  `orbitald` 는 보관이 꺼진 클러스터로는 뜨지 않고 `postgresql.conf` 에 적을 줄을 알립니다.
  **시점 복구**는 정한 시각으로 옆에 따로 세운 클러스터에만 합니다. 그 클러스터는 Postgres 의 사용자만 들어가는 폴더의 유닉스 소켓에서만 듣고 TCP 를 듣지 않으며
  WAL 을 보관하지 않습니다. 운영 클러스터를 덮어쓰는 길은 없습니다. 「이 시각까지 보관됐다」는 표시(`Seal`)는 commit 하나를 적고 WAL 을 넘겨
  보관 폴더에 닿은 것을 본 뒤에 적습니다. 되살릴 수 있는지는 core 가 판정합니다(`judge_restore`: 기반 백업이 없음 · 가장 오랜 기반 백업보다 앞섬 ·
  보관이 닿지 않음 · 기반 백업에서 표시까지 빠진 WAL 조각). `pg_ctl -w` 는 복구가 실패해도 「떴다」고 답할 수 있어, 접속해 복구가 끝났는지를 직접 봅니다.
  **인스턴스 하나 되살리기**(`POST /v1/instances/{id}/restore` `{at}`, service key 만, SDK `instances.restore`): 옆에 그 시점을 되살리고 →
  그 인스턴스의 database 를 운영 클러스터의 옆 이름에 다시 세워 권한 검사를 지나고(`backup::rebuild`) → 서버를 재우고 → 지금의 운영 DB 를 되돌릴 지점으로
  남기고 → 이름을 바꿔 넣습니다. 다음 요청이 되살린 DB 로 깹니다. **앱의 정의와 행은 관리 권한으로 되풀이하지 않습니다.** 레이어의 것(database · 스키마 ·
  `orbital` · `orbital_auth`)은 새 인스턴스처럼 레이어의 계획(`Names::staged`)으로 세우고, 앱의 스키마는 마이그레이션 역할이 소유자가 되어
  `pg_restore --no-owner --no-acl` 로 풀며, `orbital_auth` 는 행만 인증 역할로 표마다 `COPY` 해 넣습니다. 권한은 지금 release 의 권한 표대로 다시 세웁니다.
  관리 주소는 명령에 환경 변수로 건네고, 덤프는 주인만 읽게 만들어 어떻게 끝나든 지웁니다.
  다른 인스턴스의 database 와 역할은 그대로이고, `orbital_auth`(사용자 · 세션)는 그 시점의 것이 됩니다. 코드와 금고는 되살리지 않습니다.
  답은 시점 · 걸린 시간 · 표의 수 · 되돌릴 지점의 이름뿐입니다. 에이전트의 토큰은 어떤 능력으로도 이 길에 닿지 못하고(`Action::RestoreInstance`, 속성 테스트),
  다른 팩토리의 인스턴스는 없는 것과 같은 404 입니다. 옆에 되살리고 다시 세우는 긴 부분은 레이어의 자물쇠 밖(따로 연 관리 연결)에서 돌고 바꿔 넣는 순간만 쥐어,
  한 인스턴스를 되살리는 동안 다른 인스턴스의 요청은 기다리지 않습니다. 같은 인스턴스는 한 번에 하나만 되살리고(409), 그사이 운영이 바뀌었으면 바꿔 넣지 않습니다.
  **되살리기를 무르기**(`POST /v1/instances/{id}/restore/undo`, service key 만, SDK `instances.undoRestore`): 되살릴 때 남긴 되돌릴 지점으로 돌아갑니다.
  지점은 하나라 한 번만 무르고, 그 사이 승격이 있었으면(지점이 그 승격의 것으로 바뀌었으면) 까닭과 함께 409 입니다.
  **복구 훈련**(`drill`): ① 훈련 전용 database(`orbital_drill`)에 표식을 적고, 인스턴스마다의 지문(스키마의 해시 · 표마다의 행 수)과 역할을 뜬 뒤 시점 T 를
  잡고 T 뒤에 표식을 하나 더 적는다 ② WAL 을 넘겨 보관을 확인한다 ③ 옆에 T 로 되살린다 ④ 클러스터가 뜨는지, T 앞의 표식이 있고 뒤의 것이 없는지,
  인스턴스마다 database · 지문 · 역할이 T 의 것과 같은지, 옆의 control database 가 읽히고 그 운영 인스턴스의 목록이 T 의 것과 같은지, 코드 저장소의 묶음이 풀리는지 본다 ⑤ 인스턴스 하나를 되살리기와 같은 절차로 운영 클러스터의
  임시 database 에 다시 세워 지문을 견주고 지운다(인스턴스가 없으면 훈련 전용 database 의 행을 옮긴다) ⑥ 옆의 클러스터와 파일을 지운다 ⑦ control database 의 `drill` 표에 적는다(통과 여부 · 확인마다의 결과 · 복구 시간 ·
  잃을 수 있는 구간 · 실패의 갈래). 기록에는 이름과 숫자만 남습니다. 판정은 core 의 `judge_drill` 이고 확인이 하나라도 어긋나면 실패입니다(속성 테스트).
  `orbitald` 는 하루마다 기반 백업을 뜨고(`ORBITAL_BACKUP_EVERY`) 7일마다 훈련을 돌립니다(`ORBITAL_DRILL_EVERY`, 실패하면 한 시간 뒤 다시).
  관리 서버가 여럿이면 기반 백업과 훈련은 차례(advisory lock)를 잡은 하나만 돌리고, 다른 것은 409 로 답하거나(부른 경우) 건너뜁니다(주기).
  `orbitald drill` 은 한 번만 돌리고(차례를 잡지 못하면 돌리지 않습니다), 실패하면 0 이 아닌 코드로 끝납니다. 저장소의 `drill` 워크플로가 매주 그 절차(`scripts/drill-local.sh`)와 끝 기준의 테스트를 돌립니다.
  **새 고객의 관문.** 마지막으로 통과한 훈련이 여드레를 넘겼거나 한 번도 통과하지 않았으면 낡은 것입니다(core 의 `freshness`). 켠 레이어
  (`ORBITAL_REQUIRE_DRILL=1`)는 그동안 새 인스턴스를 409 로 거절하고, 이미 선 인스턴스의 프리뷰와 승격은 막지 않습니다. 팩토리는 `GET /v1/backup`
  (SDK `backup.get`)에서 `{fresh, last_passed_at?, last_drill?}`(숫자와 참 · 거짓)만 봅니다.
  **보관.** 14일(`ORBITAL_BACKUP_KEEP_DAYS`)이 지난 기반 백업과 거기에만 딸린 WAL 을 지우고 마지막 기반 백업은 언제나 남깁니다(core 의 `prune`, 속성 테스트).
  백업의 테스트는 다른 테스트가 함께 쓰는 클러스터를 건드리지 않고 테스트마다 자기 클러스터를 세웁니다(WAL 조각 1MB). CI 에서는 건너뛰지 않습니다.
  사람이 따라 할 절차는 [복구 런북](runbook/복구.md)에 있습니다.
- **남은 일.** pgBackRest(압축 · 증분 · 병렬). 백업을 다른 곳(오브젝트 저장소 · 다른 기계)에 두는 `Store`. 기록까지 과거로 되돌려 운영을 다시 세우는
  재해 복구의 전체(지금은 런북의 사람 손 절차이고, 훈련은 옆의 control database 가 읽히고 인스턴스의 목록이 맞는 것까지만 잽니다).
  코드 저장소의 묶음은 기반 백업을 뜬 기계의 것뿐입니다(다른 기계에 놓인 인스턴스의 저장소는 들지 않습니다). 대기 서버.
  되살릴 release 고르기(그 시점 뒤의 마이그레이션은 되살린 DB 에 없습니다). 이름을 바꿔 넣는 동안 그 인스턴스는 잠깐 내려갑니다. 앱이 정의한 함수는 행을 넣는 동안 소유자의 권한으로 다시 돌아, 부작용이 있으면 한 번 더 남습니다. 훈련의 지문은 T 앞뒤로 뜬 두 지문이 같을 때
  그 시점의 것으로 보므로 그 사이 몇 밀리초의 쓰기로 거짓 실패할 수 있습니다(추측, 재지 않았습니다). 운영 기계에서 pgBackRest 와 견준 복구 시간은 재지 않았습니다.
- **결정.** [복구는 옆에 되살려 옮기고 훈련이 통과해야 새 고객을 받는다](decisions/2026-11-25-복구는-옆에-되살려-옮기고-훈련이-통과해야-새-고객을-받는다.md)

## 관리 서버와 CLI

- **되는 것.** 관리 서버(`orbitald`)의 HTTP API. 팩토리의 서버는 service key 로 스캐폴드를 올리고, 인스턴스를 세우고, 작업을 열고, 승인받은 release 를 올립니다.
  **에이전트는 레이어를 직접 부르지 않습니다.** 작업의 토큰은 팩토리의 서버 안에만 있고, 그 토큰으로 프리뷰를 세우고 로그를 읽고(`GET …/previews/logs`),
  씨앗 사용자로 들어가고, 리허설을 돌리고, 승격을 요청하고, git 의 길을 엽니다. 운영을 바꾸는 길은 토큰 쪽에 없습니다.
  git 의 길은 토큰을 `Bearer` 로도, git 의 자격 도우미가 보내는 `Basic` 의 비밀번호로도 받고, 자격이 없으면 401 과 `WWW-Authenticate: Basic` 으로 답합니다.
  service key 로는 열지 않습니다(403). 토큰은 요청마다 판정해, 만료되면 진행 중인 clone 의 다음 요청부터 거절합니다. 요청 본문의 상한은 `upload_limit`(기본 64MiB)입니다.
  토큰은 서버가 서명하고(`token`), 범위는 core 가 판정합니다. 다른 인스턴스와 다른 팩토리의 것은 없는 것과 같은 답으로 돌려줍니다.
  운영에 올리기(`Layer::promote`): core 의 승격 규칙을 지난 뒤, 직전의 DB 를 되돌릴 지점으로 떠 두고, 마이그레이션을 돌리고, 권한을 세워 검사하고, 서버를 띄웁니다.
  중간에 깨지면 앞의 모습으로 돌립니다(운영에서만 뜨지 않는 서버를 올려, 앞의 release 와 앞의 DB 로 돌아가는 것을 쟀습니다).
  CLI(`orbital`)는 선언 파일을 검사하는 `check` · `plan` · `diff` 만 있고 레이어에 닿지 않습니다. 에이전트에게 주던 명령은 걷었습니다.
  팩토리의 로그인 설정(`GET` · `PUT /v1/settings/auth`)은 [로그인](#로그인)에 적었습니다.
  팩토리의 서버는 SDK(`sdk/typescript`, `@harmony/orbital/server`)로 같은 API 를 부릅니다. 승인 화면에 세울 것(기다리는 release,
  권한이 어떻게 바뀌는지의 문장, 돌 마이그레이션)을 읽고, 사람이 승인하면 올립니다. `works.open` 은 작업(`Work`)을 돌려주고, 작업의 함수
  (`preview` · `previewLogs` · `previewSignIn` · `rehearse` · `requestPromotion` · `rollout` · `secrets`)와 git 이어 주기(`git.relay`: 길 셋만 받고,
  밖에서 온 `Authorization` · 쿠키 · `Git-Protocol` 은 버리고, 본문은 스트림으로 넘긴다)는 작업의 토큰으로만 부릅니다.
  SDK 의 테스트는 실제 관리 서버에 붙어, 팩토리의 git 원격을 흉내 낸 작은 서버를 거쳐 실제 `git` 으로 한 바퀴를 돕니다(줄인 받기 요청과 git 이 실어 보낸 `Authorization` 을 버리는 것까지).
  SDK 는 `npm pack` 으로 묶이고(`prepack` 이 `dist/` 에 JavaScript 와 타입을 짓는다), 새 폴더에 깐 묶음에서 `/app` · `/server` 가 import 됩니다. 워크스페이스는 `orbital-source` 조건으로 소스(.ts)를 씁니다.
  앱에는 프리뷰인지 운영인지를 `ORBITAL_STAGE` 로 알립니다. 작업을 여는 답에는 작업의 식별자(`session`)가 함께 오고, `DELETE …/sessions/{작업}` 이 그 작업을 닫습니다([토큰](#토큰)).
- **남은 일.** 관리 서버가 다시 뜨면 기록에서 이 기계에 놓인 운영 중인 인스턴스의 router 를 자는 채로 다시 세워 첫 요청에 깨웁니다. 빌드한 폴더가 없으면 router 만 먼저 세워 그 인스턴스에
  503 과 `Retry-After` 로 답하고, 빌드는 레이어의 자물쇠 밖(뒤의 스레드)에서 해 끝나면 같은 주소에서 듣기를 멈추지 않고 섭니다. 승격도 빌드 폴더가 없으면 자물쇠 밖에서 먼저 빌드합니다.
  **프리뷰는 되살리지 않고**(다시 세우면 됩니다), 앞의 관리 서버가 세운 프리뷰의 database 는 기록(`preview`)으로 찾아 걷습니다. 기준 도메인이 없는 레이어도
  운영의 router 가 듣던 포트를 기록에 두고 다시 잡아 주소가 바뀌지 않습니다(잡지 못하면 새 포트를 잡고 기록을 고칩니다).
  새 서버를 먼저 띄우고 요청을 돌리기(지금은 승격하는 동안 운영이 내려갔다 뜹니다). 요청의 기록과 한도.
  기획안 9절의 SDK 모양 가운데 아직 없는 것: 인스턴스에 팩토리 쪽 식별자를 붙이기(`ref`), 토큰에 누구의 작업인지 적기(`actor`).
- **결정.** [코드는 묶음으로 주고받고 프리뷰는 따로 선 인스턴스다](decisions/2026-11-25-코드는-묶음으로-주고받고-프리뷰는-따로-선-인스턴스다.md)

## 기록과 기계

- **되는 것.** **레이어의 기록은 control database 에 있습니다.** 관리 연결(`ORBITAL_PG`)의 클러스터 안에 레이어 전용 database 하나(`ORBITAL_CONTROL_DB`, 기본
  `orbital_control`)를 두고 스키마 `orbital` 에 표를 둡니다: `machine`(관리 서버의 기계) · `app`(스캐폴드와 그 저장소가 있는 기계) · `instance`(놓인 기계 ·
  release · 운영 · 프리뷰 · 승격 요청, 몸은 jsonb) · `schedule`((인스턴스, 일정)마다 다음 때와 마지막 실행) · `rollout` · `factory_settings`(조직마다) ·
  `vault_value`((인스턴스, 단계, 이름)마다 봉인한 글) · `secret_request` · `secret_entry`(sha256 으로만) · `revoked_work` · `drill` · `migration`.
  인스턴스를 지우면 그 줄들이 외래 키로 함께 지워집니다. 줄을 고칠 때는 그 줄을 잠그고(`FOR UPDATE`) 읽어 고친 뒤 한 트랜잭션으로 적어, 두 관리 서버가
  같은 줄을 동시에 고쳐도 한쪽을 잃지 않습니다. 일정은 「다음 때가 그대로일 때만」 옮기는 한 줄의 `UPDATE` 로 잡아 같은 때를 두 번 부르지 않습니다.
  인스턴스의 database 와 섞지 않고 `PUBLIC` 의 접속을 걷어, 인스턴스의 어떤 역할도 이 database 에 붙지 못합니다(실제 역할로 붙어 보는 테스트).
  **마이그레이션**은 번호 붙은 SQL(`crates/orbital-server/migrations/`)을 실행 파일에 넣어 두고 뜰 때 적용하지 않은 것만 차례로 적용합니다(advisory lock 으로
  두 관리 서버가 동시에 떠도 한 번). 무엇을 돌릴지는 core 의 `control::pending` 이 판정하고(빠진 번호 · 같은 번호 · 모르는 번호 · 내용이 바뀐 것은 거절),
  적용한 것의 내용(sha256)이 바뀌었으면 뜨지 않고 알립니다. **봉인**은 그대로입니다. 금고 · 팩토리의 설정 · 운영의 신원 열쇠 · 레이어가 만든 비밀은
  봉인한 글로만 줄에 있고(운영의 것은 조직 · 인스턴스 · 칸에 묶는 `orbital/production/v1`), 값은 SQL 의 글자가 아니라 매개변수로만 넘깁니다.
  봉인의 열쇠가 없는 레이어는 개발용 모양이라 운영의 신원 열쇠와 레이어가 만든 비밀을 평문으로 적고 뜰 때 그렇다고 알리며, 열쇠를 준 뒤 처음 뜨면 평문이던 칸을 봉인합니다.
  **옛 파일에서 옮기기.** control database 가 비어 있고 `ORBITAL_HOME` 에 옛 기록 파일(`registry.json` · `settings.json` · `vault.json` · `revoked.json` ·
  `drills.jsonl`)이 있으면 처음 뜰 때 한 트랜잭션으로 옮기고 `*.imported` 로 이름을 바꿉니다. 하나라도 실패하면 아무것도 적지 않고 뜨지 않습니다.
  **기계와 놓인 자리.** 관리 서버는 뜰 때 자신을 기계(`ORBITAL_MACHINE`, 기본 `local`)로 적고, 세운 인스턴스는 그 기계에 놓입니다(앱의 저장소도 받은 기계의 것).
  파일로 남는 것(코드 저장소 · 빌드 폴더 · 캐시 · 로그 · 개발용 메일함 · 토큰의 열쇠 파일)과 떠 있는 프로세스가 그 기계에만 있어서입니다.
  그 인스턴스의 저장소 · 빌드 · 프로세스에 닿는 일(묶음과 git · 프리뷰 · 리허설 · 승격의 요청과 승격 · 되살리기와 무르기 · 업데이트 합치기 · rollout 만들기 · 지우기)은
  놓인 기계만 하고, 다른 기계는 아무것도 하지 않고 **421**(`{"error": "misplaced", "machine": "<놓인 기계>"}`, SDK 의 `OrbitalError.machine`)로 답합니다.
  기록과 인스턴스의 DB 에만 닿는 일(작업 열고 닫기 · 운영의 모습 · 사용자와 초대 · 팩토리의 설정 · 비밀의 목록 · 요청 · 값 · 입력 표 · rollout 보기와 다시 열기 · 거두기 ·
  Google 의 콜백 · 백업의 모습)은 어느 기계에서나 됩니다. 어느 일이 어느 쪽인지는 core 의 `placement` 한곳에 있습니다. 운영의 주소와 선언은 기록에 두어 코드 저장소 없이 답합니다.
  다른 기계에서 비밀의 값을 바꾸면 놓인 기계에 control database 로 알려(`LISTEN`/`NOTIFY`, 이름만) 그 기계가 서비스를 재웁니다. 다시 뜰 때는 제 기계에 놓인 운영만 되살리고,
  일정은 그 인스턴스가 떠 있는 기계만 부릅니다. 기반 백업과 복구 훈련은 여러 관리 서버 가운데 하나만 돌립니다([백업과 복구](#백업과-복구)).
  프로세스 안의 자물쇠는 메모리(떠 있는 프리뷰 · 운영 · router)만 지키고, 기록의 정합성은 DB 의 트랜잭션이 지킵니다.
  **기계의 이름 하나에는 관리 서버가 하나만 뜹니다.** 뜰 때 그 이름의 advisory lock 을 쥐고, 같은 이름으로 하나 더 띄우면 5초 기다려 본 뒤 뜨지 않고
  까닭을 알립니다(기본 이름 `local` 로 둘을 띄우면 같은 운영을 둘이 되살리게 됩니다). 알림을 듣던 연결이 끊기면 다시 붙고, 끊긴 사이의 알림을 놓쳤으므로
  그 기계의 서버 서비스를 모두 재워 다음 요청이 지금의 값으로 깨게 합니다. **다시 뜰 때는 운영을 먼저 세웁니다.** 앞의 관리 서버가 세워 둔 프리뷰의 database 는 운영의 router 를 모두 세운 뒤에 뒤에서 걷습니다(하나에 0.5초쯤 걸려, 먼저 걷으면 프리뷰의 수만큼 운영이 늦게 섭니다). 그 전에 인스턴스를 지우면 기록에 이름으로 남은 프리뷰의 database 도 함께 걷습니다.
  **기록을 읽지 못한 것은 「없다」가 아닙니다.** 인스턴스의 기록을 읽지 못하면
  404 가 아니라 500 이고, rollout 의 기록을 읽지 못하면 승격하지 않고, 금고를 읽지 못하면 서비스를 비밀 없이 띄우지 않습니다(503).
- **남은 일.** 다른 기계에 놓인 인스턴스의 요청을 그 기계로 넘겨 주기(지금은 421 과 기계의 이름으로 답합니다). DB 클러스터 여럿(인스턴스의 database 를 여러 클러스터에
  두기). 코드 저장소를 여러 기계가 나눠 쓰기(그래야 기계를 옮기거나 잃은 기계의 인스턴스를 다른 기계가 이어 받습니다). 기계가 죽었는지 알아보기(`seen_at` 은 뜰 때만 적습니다).
  한 기계의 관리 서버를 겹쳐서 바꿔 띄우기(지금은 내리고 띄웁니다. 운영의 router 를 관리 서버의 프로세스에서 떼어야 합니다).
  rollout 의 인스턴스가 여러 기계에 놓였으면 만들지 못하고(421), 거둘 때 다른 기계의 저장소에 담아 둔 업데이트는 빼지 못합니다(다음 rollout 이 덮습니다).
  옛 열쇠 없이 봉인의 열쇠를 바꾸면 운영의 신원 열쇠가 풀리지 않아 승격과 되살리기가 409 로 멈춥니다(인스턴스의 database 에 있는 열쇠로 되찾는 길은 아직 없습니다).
- **결정.** [기록은 control database 에 두고 인스턴스는 놓인 기계가 돌린다](decisions/2026-11-26-기록은-control-database-에-두고-인스턴스는-놓인-기계가-돌린다.md)

## 팩토리의 본보기

- **되는 것.** `examples/factory-todo` 가 팩토리 하나를 에이전트 플랫폼의 앱으로 세웁니다. service key 와 레이어의 주소는 팩토리 서버의 환경 변수에만 있고,
  고객은 앱에 연결한 계정(OAuth 의 주체)이며, 고객마다 인스턴스 하나를 스캐폴드 v1 에서 세워 그 짝을 팩토리의 파일에 둡니다.
  에이전트는 레이어의 주소도 토큰도 받지 않습니다. `workspace_open` 은 팩토리의 git 원격(`<팩토리>/git/<작업>`)과 그 원격에만 쓰는 두 시간짜리 자격
  (`fgit_…`)을 돌려주고, 레이어의 작업(`source · preview · rehearse · secrets_request`)은 팩토리의 메모리에만 둡니다(`src/works.ts`). 팩토리의 git 의 길은
  그 자격을 확인해 `git.relay` 로 이어 주고, MCP 의 토큰으로는 열리지 않으며, git 의 자격으로는 `/mcp` 가 열리지 않습니다.
  모델이 부르는 작업의 도구: `preview`(주소 · 어긋난 것 · 권한의 변화 · 적합성 테스트 · 빠진 비밀), `preview_logs`, `preview_sign_in`, `rehearse`,
  `promotion_request`. 그리고 `promotion_show`(승인 카드: 기다리는 release, 권한이 바뀌는 문장, 실행될 마이그레이션),
  `promotion_approve`(화면 전용 `ui.visibility: ["app"]`, 카드가 보인 release 하나에만 묶인 한 번 쓰는 표), `production_status`. 비밀의 도구 둘: `secret_request`(모델에게 보임: 이름과 까닭 → 레이어에 요청을 적고 입력 카드를 돌려줌)와
  `secret_entry_open`(화면 전용: 카드가 불러 입력 표의 주소와 표를 `_meta` 로만 받음). 카드는 단계마다 칸을 두고, 값은 카드가 레이어의 주소로 표를 머리말에 실어 바로 보냅니다
  (카드의 CSP `connectDomains` 에 레이어의 바깥 주소, 팩토리의 `ORBITAL_PUBLIC_URL`). 스킬 `orbital-dev` 와 참고 문서 `references/auth.md` · `secrets.md` 를
  함께 훅 없는 ZIP 하나로 묶습니다(`src/pack.ts`). 스킬은 이 앱의 도구와 평범한 `git` 만 쓰라고 말하고(자격은 명령 한 번의 머리말이나 자격 도우미로),
  설치할 명령은 없습니다. 테스트(`npm run test:factory`)는 실제 `orbitald` 와 PostgreSQL 에 붙어 OAuth 로 연결하고 MCP client 와 실제 `git` 으로
  한 바퀴를 돌며, 도구의 답과 팩토리의 로그에 레이어의 주소 · 토큰 · service key 가 실리지 않는 것을 잽니다.
- **남은 일.** 하모니에 붙여 실물로 돌리기와 클로드에 올리기. 본보기의 로그인은 계정 이름을 적는 칸 하나라 실제 로그인으로 바꿔야 합니다.
  OAuth 의 토큰 · 승인의 표 · 열린 작업과 git 의 자격은 팩토리 프로세스의 메모리에만 있어서(디스크에 두지 않습니다), 팩토리가 다시 뜨면 플랫폼은 다시 연결하고
  에이전트는 작업을 다시 엽니다. `workspace_open` 을 다시 부르면 그 고객의 앞 작업을 레이어에서 닫고 그 git 의 자격도 끊습니다. 그때 자격이 통하지 않는 git 에는 403 과 글로 「`workspace_open` 을 다시 불러 `git remote set-url origin <새 원격>` 으로 바꾸라」고 답하고
  (git 이 `remote: …` 로 보입니다), 받던 폴더에서 원격만 바꿔 이어서 올리는 것을 테스트가 잽니다.
  코드가 팩토리의 서버를 거쳐 가므로 팩토리가 그 통로를 운영합니다(팩토리의 도메인으로 레이어에 바로 붙는 길은 아직 없습니다).
