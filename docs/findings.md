# 실물에서 본 것

테스트가 아니라 실제 기계와 실제 네트워크에서 본 것을 근거(실측 · 문서 · 추측)와 함께 적습니다. 추측이 줄어드는 것이 진척입니다.

## GCP 서울의 VM 에서 실행기 후보와 레이어를 재다 (2026-11-26, 실측)

`asia-northeast3-a` 의 `n2-standard-4`(Intel Cascade Lake, 4 vCPU · 16GB, Ubuntu 26.04 · 커널 7.0)에 중첩 가상화를 켜고, 디스크 둘(부트 pd-balanced 30GB,
데이터 pd-ssd 40GB 를 XFS 로)을 붙였습니다. 앱은 `create-next-app` 의 Next.js 16.4 를 `output: "standalone"` 으로 지은 서버(68MB)이고, 첫 응답은
동적 페이지(`/now`, `force-dynamic`)가 200 을 준 때까지입니다. 시간은 모두 VM 안에서 2ms 간격으로 두드려 쟀습니다. 측정이 끝나고 VM · Cloud Run · 이미지 저장소를 지웠습니다.

### 실행기: Next.js 서버가 첫 응답을 주기까지

| 어떻게 띄우나 | 첫 응답 | 근거 |
|---|---|---|
| 맨 프로세스(`node server.js`) | 818~827ms (3회) | 실측 |
| Docker `runc` | 716~740ms (5회) | 실측 |
| gVisor `runsc`(systrap) | 1317~1330ms (5회). 뜬 뒤 메모리 58MB | 실측 |
| gVisor `runsc --platform=kvm` | 1556~1598ms (5회). 중첩 가상화 안에서는 systrap 보다 느리다 | 실측 |
| Firecracker 1.18 첫 부팅(커널 6.1 + `node server.js`, 2 vCPU · 1GB) | 2006~2121ms (3회) | 실측 |
| Firecracker 스냅숏 복원(데운 메모리 파일) | 236~240ms (4회). 그 가운데 복원 API 22~27ms, 연결 3ms, 나머지 약 190ms 는 앱이 첫 요청을 그리는 몫 | 실측 |
| Firecracker 스냅숏 복원(페이지 캐시를 비운 뒤) | 710ms (1회), 복원 API 82ms | 실측 |
| Firecracker 스냅숏 만들기 | 7.7초. 메모리 파일이 1GB 그대로다(pd-balanced 에 쓰기) | 실측 |

- **GCP 서울의 N2 에 중첩 가상화가 된다.** `--enable-nested-virtualization` 으로 만든 VM 에 `/dev/kvm` 이 있고 `kvm_intel` 이 올라온다. 기획안 13절의
  「GCP 서울은 공식 목록에서 확인하지 못했다」는 이것으로 풀렸다(실측).
- 스냅숏을 서버가 한 번 응답한 뒤에 떴는데도 복원 뒤 첫 요청에 약 190ms 가 든다. 메모리 파일을 필요할 때 읽어 오는(page fault) 몫으로 보인다(추측).
  메모리를 미리 올리거나 메모리를 줄이면 줄어들 것이다(재지 않았다).
- gVisor 의 KVM 플랫폼은 중첩 가상화 안에서 이득이 없다. 맨 VM(베어메탈)에서는 다를 수 있다(추측).

### PostgreSQL 18 의 database 복제(XFS, `file_copy_method = clone`)

PostgreSQL 18.6(배포판), `shared_buffers = 2GB`, `src` 는 `pgbench -s 100`(1.5GB), 다른 인스턴스 자리의 `busy` 는 `-s 50`(755MB) 입니다.

| 본 것 | 근거 |
|---|---|
| 쉬는 클러스터에서 1.5GB database 복제는 104~106ms(3회)이고 디스크는 11MB 만 는다. 같은 일을 `file_copy_method = copy` 로는 6.3초, `STRATEGY wal_log` 로는 6.1초 | 실측 |
| **다른 database 에 쓰기 부하**(`pgbench -c 8`, 약 4,500 tps)가 있으면 복제가 1.8~1.9초로 는다. `FILE_COPY` 가 앞에 거는 checkpoint 가 클러스터 전체의 더러운 페이지를 쓰기 때문이다. 그동안 다른 인스턴스의 tps 가 1~2초 동안 1/4~1/6 로 떨어지고 지연이 1.7ms 에서 6~11ms 로 뛴다 | 실측(pgbench `-P 1`) |
| **원본에 쓰기 부하**가 있는 채로 레이어의 순서대로(`quiesce`: 닫기 → 연결 끊기 → 복제 → 열기) 하면 운영 DB 가 닫혀 있는 시간이 4.5~4.8초다. 닫기와 끊기는 72~75ms, 나머지는 checkpoint 다 | 실측(3회) |
| 닫기 **전에** 문을 연 채로 `CHECKPOINT` 를 먼저 돌리면(4.6~5.7초 걸린다) 닫혀 있는 시간이 300~468ms 로 준다 | 실측(3회) |

### 대조군: 같은 서버를 Cloud Run 서울에

같은 이미지를 Artifact Registry 서울에 올려 Cloud Run(`asia-northeast3`, 1 vCPU · 512MiB, 최소 0 · 최대 1)에 세우고 VM 에서 불렀습니다.

| 본 것 | 근거 |
|---|---|
| 배포 · 설정 변경 직후의 첫 요청 320~436ms(3회), 처음 배포 직후 940ms(1회). 뒤의 요청은 60~68ms(TLS 39ms 포함) | 실측 |
| **17분 쉰 뒤의 첫 요청은 1.54초**(1회, 0으로 내려간 뒤 새 인스턴스). 서울 VM 에서 부른 값이라 거리는 거의 없다 | 실측 |
| 값은 vCPU 초당 $0.000024, GiB 초당 $0.0000025, 요청 100만 개에 $0.40 이다(요청 기반 과금, 기본 등급). 서울의 등급과 값은 확인하지 못했다 | 문서 |

### 레이어: VM 에 `orbitald` 를 세워 밖에서 한 바퀴

같은 VM 에 PostgreSQL 18(`scripts/pg-local.sh`, 데이터는 XFS)과 `orbitald` 를 띄우고, 앞에 Caddy 2.6 을 두어 TLS 를 끝냈습니다. 도메인은 사지 않고
`sslip.io`(이름에 IP 를 넣으면 그 IP 로 풀리는 공용 DNS)를 썼습니다. 관리 서버는 `https://api.<IP>.sslip.io`, 기준 도메인은 `<IP>.sslip.io` 이고,
인스턴스의 주소마다 Caddy 가 처음 요청 때 Let's Encrypt 인증서를 받습니다(on-demand TLS). `ORBITAL_SLEEP_AFTER=60` 으로 재웠습니다.
팩토리의 걸음은 서울 밖의 기계(이 저장소의 작업 컨테이너)에서 SDK 로, 에이전트의 걸음은 VM 안에서 `orbital` CLI 로 했습니다.

| 본 것 | 근거 |
|---|---|
| **한 바퀴가 돈다.** 스캐폴드 올리기 0.81 · 인스턴스 세우기 0.71 · 토큰 0.18 · 받기 0.11 · 올리기 0.05 · 프리뷰 0.53 · 리허설 0.03 · 승격 요청 0.04 · 기다리는 release 0.90 · 승격 1.33초 | 실측(`remote-lap.ts`) |
| **인스턴스의 하위 도메인이 밖에서 `https` 로 닿는다.** `https://<인스턴스>.<IP>.sslip.io/health` 가 고친 버전(`version: 2`)으로 답한다. 처음 요청은 인증서를 받느라 5.5초, 뒤로는 서울 밖에서 0.6~1.0초(거리의 몫) | 실측 |
| 자는 서버를 router 에서 바로 깨우면 첫 응답이 163ms 이고, VM 안에서 Caddy 를 거쳐 깨우면 252ms 다(각 1회). 깨어 있으면 router 에서 1ms, Caddy 를 거쳐 15ms | 실측 |
| **깨운 서버가 다시 잠들지 않은 때가 있었다.** 승격 직후 Caddy 를 거쳐 깨운 서버가 5분 넘게 떠 있었고(`ORBITAL_SLEEP_AFTER=60`), 재시작 뒤에도 한 번 더 그랬다. 그 뒤 같은 모양으로 다섯 번(router 로만, Caddy 를 거쳐 한 번 · 세 번, 서울 밖과 VM 에서 함께, `/` 와 `/cards`) 해 보니 모두 60초 뒤에 내려갔다. 살려 둔 연결만으로는 재현되지 않았고 까닭은 찾지 못했다 | 실측(재현 안 됨), 까닭 모름 |
| `orbitald` 를 다시 띄우면 운영의 router 가 자는 채로 다시 서고 첫 요청에 고친 버전으로 깬다 | 실측 |
| PostgreSQL 과 `orbitald` 를 함께 내렸다 올려도 운영 DB 에 넣은 행이 남고 앱이 답한다 | 실측 |
| 작업 컨테이너의 프록시는 TLS 를 가로채지만 Let's Encrypt 인증서를 단 레이어에는 SDK(`NODE_USE_ENV_PROXY=1`)로 붙었다. CLI 는 VM 안에서만 돌렸다 | 실측 |
| Ubuntu 26.04 의 `nodejs`(22.22)는 TypeScript 를 벗겨 내는 기능 없이 지어져 `remote-lap.ts` 를 돌리지 못한다. nodejs.org 의 24 로 돌렸다 | 실측 |

### 그래서

- **실행기는 Firecracker 스냅숏 복원을 기본 길로 삼을 만합니다.** 첫 응답이 약 240ms 로 Cloud Run 이 0 에서 깨는 시간(1.54초)의 6분의 1 이고,
  맨 프로세스(820ms)보다도 짧습니다. 스냅숏이 없을 때(배포 직후, 기계 이동)의 느린 길은 약 2초이고 gVisor 는 1.3초입니다. 직접 짓는 쪽으로 기울지만,
  스냅숏의 크기(지금 1GB, 만드는 데 7.7초)와 네트워크 · 디스크를 인스턴스마다 나누는 일은 아직 짓지 않았습니다(추측).
- **GCP 서울도 후보입니다.** N2 의 중첩 가상화로 Firecracker 가 돕니다. 다만 중첩이라 맨 VM 보다 느릴 수 있고, AWS 의 같은 기능과는 견주지 않았습니다.
- **리허설은 checkpoint 를 먼저 돌린 뒤 닫아야 합니다(고쳤습니다).** 잴 때의 `quiesce` 는 닫은 뒤 복제했으므로 쓰기가 몰리는 운영 DB 는 4~5초 닫혀 있습니다. 먼저 `CHECKPOINT` 를
  돌리면 0.3~0.5초로 줄어듭니다. 복제의 checkpoint 는 같은 클러스터의 다른 인스턴스도 1~2초 느리게 합니다.
- **재우기에 새는 곳이 있을 수 있습니다.** 깨운 서버가 내려가지 않은 것을 두 번 봤지만 재현하지 못했습니다. 처리 중인 요청의 수(`in_flight`)가 어떤 갈래에서 줄지 않는 것으로 보이며(추측), 계속 서 있는 레이어에서 재운 횟수와 떠 있는 서버 수를 세어 두면 다시 잡힐 것입니다.
- **도메인은 아직 사지 않아도 됩니다.** `sslip.io` 와 Caddy 의 on-demand TLS 로 인스턴스마다의 `https` 주소가 섭니다. 실제 고객을 받기 전에는 우리 도메인과
  와일드카드 인증서로 바꿉니다.

### 재는 데 쓴 길

- 작업 컨테이너에서는 SSH(22번)가 막혀 있어, VM 의 시작 스크립트로 작은 대리인을 띄우고 명령은 인스턴스 메타데이터(`cmd`)로 보내고 결과는 guest attribute 로 받았다. Google API 만 쓴다.
- 바이너리와 소스는 Artifact Registry 의 generic 저장소로 옮겼고, 이미지는 VM 의 Docker 에서 지어 Artifact Registry 로 밀었다. VM 에 건넨 열쇠는 1시간짜리 access token 이고 쓰고 나서 메타데이터에서 지웠다.
- VM 은 약 1시간 떠 있었다. 값은 n2-standard-4 와 디스크 70GB 로 1달러 아래로 본다(추측, 청구서는 보지 않았다).

### 재지 않은 것

- 사람이 로그인해 운영의 앱에 들어가는 길(로그인 링크 · `__Host-` 쿠키). 이번에는 DB 에 행을 직접 넣어 재시작 뒤에 남는지만 봤습니다.
- VM 을 통째로 다시 켠 뒤. `orbitald` 와 PostgreSQL 을 서비스로 등록하지 않았습니다.
- AWS Lambda 대조군과 AWS 서울의 중첩 가상화.
- 인스턴스 여럿이 한 VM 에서 동시에 깰 때, 스냅숏을 디스크가 아닌 메모리에 둘 때.


## Vercel Sandbox 에 레이어를 세워 한 바퀴 (2026-11-26, 실측)

Vercel 의 서울(`icn1`) sandbox 하나(4 vCPU · 8GB)에 PostgreSQL 과 `orbitald` 를 띄우고, 관리 서버를 sandbox 의 바깥 주소(`https://…vercel.run`)로 열었습니다.
팩토리의 걸음(스캐폴드 올리기 · 인스턴스 세우기 · 토큰 내기 · 승격)은 다른 기계에서 SDK 로, 에이전트의 걸음(받기 · 올리기 · 프리뷰 · 리허설 · 승격 요청)은
`orbital` CLI 로 그 바깥 주소에 붙어 했습니다. 걸음은 `sdk/typescript/test/remote-lap.ts` 에 있습니다.

| 본 것 | 근거 |
|---|---|
| **한 바퀴가 돈다.** 스캐폴드 v1 에서 인스턴스를 세우고, 고친 commit 을 올려 프리뷰를 세우고, 승격을 요청해 승인하면 운영의 앱이 고친 버전으로 답한다 | 실측 |
| sandbox 는 Ubuntu 26.04 · 커널 6.18 · glibc 2.43 이고, 다른 리눅스(glibc 2.39)에서 지은 `orbitald` · `orbital` 이 그대로 돈다 | 실측 |
| PostgreSQL 은 배포판의 18 이 `apt-get install postgresql` 로 23초 안에 깔린다. 19 는 PGDG 저장소를 더해야 한다(해 보지 않았다) | 실측 |
| 디스크는 XFS(64GB)이고 `file_copy_method = clone` 이 된다. 1.9GB 의 database 를 `CREATE DATABASE … STRATEGY file_copy` 로 복제하는 데 69ms 이고 디스크는 늘지 않는다 | 실측 |
| 밖에서 SDK 로 부른 걸음은 하나에 0.5~0.8초다(스캐폴드 올리기 0.79 · 인스턴스 세우기 0.70 · 토큰 0.53 · 승격 0.78). 부른 쪽이 서울 밖이라 대부분은 거리의 몫이다 | 실측 |
| sandbox 안에서 바깥 주소로 부른 에이전트의 걸음은 받기 0.15 · 올리기 0.05 · 프리뷰 0.29 · 승격 요청 0.05초다 | 실측 |
| 운영의 앱은 router 를 거쳐 1~5ms 에 답하고, 모르는 `Host` 는 404 다 | 실측(sandbox 안에서 `Host` 를 실어) |
| **인스턴스의 주소는 밖에서 닿지 않는다.** sandbox 의 바깥 주소는 포트마다 정해진 이름 하나(`sb-….vercel.run`)라 `<인스턴스>.<기준 도메인>` 의 `Host` 가 오지 않고, router 는 404 로 답한다 | 실측 |
| **혼자 빌드한 `orbital` 은 `https` 주소에 붙지 못했다.** `ureq` 의 TLS 를 `orbital-server` 와 `orbital-router` 만 켜서, 함께 빌드하면 들고 `cargo build -p orbital-cli` 만 하면 빠졌다. 테스트는 늘 함께 빌드해 보지 못했다. CLI 가 스스로 켜게 고쳤다 | 실측(`strings` 로 두 빌드를 견줌) |
| `orbital` 은 `HTTPS_PROXY` 와 `SSL_CERT_FILE` 을 읽지 않는다. TLS 를 가로채는 프록시 뒤의 sandbox 에서는 레이어에 닿지 못한다 | 실측(프록시 뒤의 기계에서 「닿지 못했습니다」) |
| 개발용 실행기라 `orbitald` 와 앱의 서버(`node server.js`)가 같은 기계에서 같은 사용자(root)로 돈다. 앱의 코드가 레이어의 기록과 DB 의 관리 주소에 닿는다 | 실측(`ps`) |

### 그래서

- **Vercel Sandbox 는 한 바퀴를 돌려 보는 자리로는 충분하고, 계속 서 있는 레이어의 자리로는 모자랍니다.** sandbox 는 정한 시간이 지나면 내려가고(이번에는 45분),
  다시 뜨면 `orbitald` 와 PostgreSQL 을 누가 띄워 줘야 하며, 인스턴스마다의 하위 도메인을 줄 길이 없습니다.
- `orbitald` 는 지금 모양으로 Vercel 함수가 되지 못합니다. 기록을 파일에 두고(`ORBITAL_HOME`), router 와 DB proxy 가 오래 떠 있는 TCP 를 듣고,
  `git` 과 앱의 프로세스를 직접 띄우기 때문입니다. Vercel 에 계속 세우려면 기록을 DB 로 옮기는 일(지도의 남은 일), 앞에서 `Host` 를 정해 넘겨 주는 문,
  sandbox 를 실행기로 쓰는 어댑터가 먼저입니다. 이 셋의 크기는 재지 않았습니다(추측).
- 복제가 69ms 라는 것은 리허설과 되돌릴 지점이 database 의 크기에 거의 매이지 않는다는 뜻입니다. 다만 쓰기가 몰리는 동안의 복제와 잠금 시간은 재지 않았습니다.

### 재지 않은 것

- 운영의 앱에 사람으로 들어가는 길(로그인 링크 · `__Host-` 쿠키). 인스턴스의 주소가 `https` 로 밖에 서야 잴 수 있습니다.
- 재웠다가 깨우는 시간. 기본 5분을 기다리지 않았습니다.
- sandbox 가 내려갔다가 스냅숏에서 다시 뜬 뒤 PostgreSQL 의 데이터와 레이어의 기록이 온전한지.
- 격리. 개발용 실행기는 격리하지 않으므로 이번 한 바퀴는 격리에 기대는 규칙(적합성 테스트 · 빌드)을 재지 못합니다.
