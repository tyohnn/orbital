# 복구 런북

레이어의 운영자가 실제로 따라 하는 절차입니다. 왜 이렇게 정했는지는
[결정](../decisions/2026-11-25-복구는-옆에-되살려-옮기고-훈련이-통과해야-새-고객을-받는다.md)에 있습니다.

## 자동으로 되는 것과 사람이 할 것

| 일 | 누가 |
|---|---|
| WAL 보관(조각이 찰 때마다 `<ORBITAL_BACKUP_DIR>/wal` 로 복사) | Postgres(`archive_command`) |
| 기반 백업(하루에 한 번)과 보관 기간이 지난 것 지우기(14일, 마지막 것은 남김) | `orbitald` |
| 복구 훈련(7일에 한 번, 실패하면 한 시간 뒤 다시)과 기록(control database 의 `orbital.drill`). 관리 서버가 여럿이면 차례를 잡은 하나만 | `orbitald` |
| 훈련이 낡은 동안 새 인스턴스를 받지 않기(`ORBITAL_REQUIRE_DRILL=1`) | `orbitald` |
| 인스턴스 하나를 지난 시점으로 되살리기 | 팩토리의 서버가 부른다(`POST /v1/instances/{id}/restore`). 레이어가 끝까지 한다 |
| 처음 켤 때의 설정, 열쇠 지키기 | 사람 |
| 훈련이 실패했을 때 까닭을 보고 고치기 | 사람 |
| 클러스터 전체를 되살려 레이어를 다시 세우기(재해 복구) | 사람. 아래 절차를 따른다 |

## 처음 켤 때

1. 백업을 둘 폴더를 정합니다(`ORBITAL_BACKUP_DIR`). 지금은 같은 기계의 폴더이므로, 기계를 잃으면 백업도 잃습니다.
2. 운영 클러스터의 `postgresql.conf` 에 적고 클러스터를 다시 띄웁니다. `orbitald` 는 보관이 꺼져 있으면 적을 줄을 그대로 알리고 뜨지 않습니다.
   ```
   wal_level = replica
   archive_mode = on
   archive_command = 'test ! -f ''<폴더>/wal/%f'' && cp %p ''<폴더>/wal/%f'''
   archive_timeout = 300        # 쓰기가 적어도 5분마다 조각을 넘긴다. 잃을 수 있는 구간이 이만큼으로 줄어든다
   ```
3. `orbitald` 에 `ORBITAL_BACKUP_DIR` 을 주고 띄웁니다. 뜨자마자 첫 기반 백업을 뜨고 첫 훈련을 돌립니다.
4. 실제 고객을 받기 전에 `ORBITAL_REQUIRE_DRILL=1` 을 켭니다. 훈련이 통과하기 전까지 새 인스턴스는 409 로 거절됩니다.
5. **열쇠는 백업에 들지 않습니다.** `ORBITAL_SEAL_KEY` · `ORBITAL_SERVICE_KEYS` · `ORBITAL_OPERATOR_KEY` · `ORBITAL_TOKEN_KEY` 는 백업과 다른 곳(비밀 관리 도구)에 따로 둡니다.
   기록에 둔 service key 는 값이 아니라 sha256 으로 control database 와 함께 백업에 듭니다. 그래서 팩토리의 열쇠는 되살린 뒤에도 그대로 통합니다.
   봉인의 열쇠를 잃으면 백업을 되살려도 금고 · 팩토리의 키 · 운영의 신원 열쇠(기록의 것) · 레이어가 만든 비밀이 풀리지 않습니다.
   운영의 신원 열쇠는 인스턴스의 database(`orbital.instance.signing_key`)에도 평문으로 있어 그 database 와 함께 백업에 듭니다. 백업 폴더는 기록과 같은 무게로 지킵니다.

## 훈련이 실패했을 때

control database 의 마지막 훈련을 봅니다(`psql "$ORBITAL_PG" -d orbital_control -c "SELECT body FROM orbital.drill ORDER BY id DESC LIMIT 1"`). 기록에는 이름과 숫자만 있습니다. `failure.kind` 로 갈라 봅니다.

| `failure` | 뜻 | 볼 것 |
|---|---|---|
| `step: base_backup` | 기반 백업을 뜨지 못했다 | 디스크의 빈 자리, `pg_basebackup` 이 복제 연결을 받는지(`pg_hba.conf` 의 `replication`), 도구의 버전이 클러스터와 같은지 |
| `step: mark` | 운영 클러스터에 표식을 적지 못했다 | 관리 주소(`ORBITAL_PG`)로 붙는지, `orbital_drill` database 가 있는지 |
| `step: seal` | WAL 을 넘겼는데 60초 안에 보관 폴더에 닿지 않았다 | `SELECT * FROM pg_stat_archiver` 의 `failed_count`, `archive_command` 의 경로와 권한, 디스크 |
| `refused: missing_wal` | 기반 백업에서 그 시점까지 이어질 WAL 조각이 보관 폴더에 없다 | 적힌 조각의 이름. 누가 지웠는지 본다. 새 기반 백업을 뜨면(`orbitald` 가 다음 날 뜨거나, 다시 띄우면 곧바로) 그 뒤로는 되살릴 수 있다. 빠진 조각 앞의 시점은 되살리지 못한다 |
| `refused: no_backup` · `before_oldest_backup` · `beyond_archive` | 되살릴 시점을 덮는 것이 없다 | 기반 백업의 폴더(`<폴더>/base`)와 보관의 표시(`<폴더>/seal.json`) |
| `recovery: target_not_reached` · `wal_missing` · `did_not_start` | 옆의 클러스터가 서지 못했다 | 다시 돌리며 옆의 폴더(`<폴더>/restore/…/log`)를 본다. 이 기록은 훈련이 끝나면 지워진다 |
| `checks` | 확인이 어긋났다(`failed` 에 무엇이) | `fingerprint` 면 그 인스턴스의 database 가 되살린 것과 다르다. 훈련하는 동안 쓰기가 몰렸으면 다시 돌린다. 되풀이되면 그 인스턴스로 아래의 「인스턴스 하나」 절차를 프리뷰에서 시험한다 |
| `step: clean` | 옆의 클러스터나 파일이 남았다 | `<폴더>/restore` 를 보고 남은 Postgres 프로세스를 멈춘다. 다음에 레이어가 뜨면 끝난 프로세스의 것은 걷는다 |

고친 뒤 `orbitald drill` 로 한 번 돌립니다. 통과하면 0 으로 끝나고 기록 한 줄을 찍습니다. 관리 서버가 떠 있어도 함께 돌릴 수 있습니다.

```
ORBITAL_HOME=… ORBITAL_PG=… ORBITAL_BACKUP_DIR=… orbitald drill
```

## 인스턴스 하나를 되살리기

고객이 「어제 오후 3시로 돌려 달라」고 하면 팩토리의 서버가 부릅니다. 사람은 시점만 정합니다.

```
POST /v1/instances/{id}/restore   {"at": <유닉스 초>}      (service key 만. SDK 는 instances.restore(id, { at }))
```

- 레이어가 하는 일: 보관을 확인한다 → 옆에 그 시점의 클러스터를 세운다 → 운영 클러스터의 옆 이름(`i_<인스턴스>_rs_…`)에 그 database 를
  다시 세우고 권한 검사를 지난다 → 옆의 클러스터를 걷는다 → 서버를 재운다 → 지금의 운영 DB 를 되돌릴 지점으로 남긴다 → 이름을 바꿔 넣는다.
  답에는 시점 · 걸린 시간 · 표의 수 · 되돌릴 지점의 이름이 옵니다. 검사에 걸리면(409) 운영은 건드리지 않은 채입니다.
- 다시 세울 때 앱의 정의와 행은 관리 권한으로 풀지 않습니다(앱의 스키마는 마이그레이션 역할로, 로그인의 행은 인증 역할로). 손으로 되살릴 때도
  **덤프를 관리 역할로 `pg_restore` 하지 않습니다.** 앱이 정의한 함수가 그 권한으로 돕니다.
- 되살아나는 것은 DB 뿐입니다. 사용자와 세션도 그 시점의 것이 됩니다(그 뒤에 들어온 사람은 다시 로그인합니다). 코드(release)와 비밀은 지금의 것 그대로입니다.
- 그 시점 뒤에 마이그레이션이 돌았으면 되살린 DB 에는 그 표가 없습니다. 되살린 뒤 앱이 깨지면 지금은 사람이 판단합니다.
- 옆에 되살리고 다시 세우는 긴 부분은 레이어의 자물쇠 밖에서 돌아 다른 인스턴스의 요청을 막지 않습니다. 바꿔 넣는 짧은 순간만 쥡니다.
  같은 인스턴스를 겹쳐 되살리면 409 이고, 되살리는 동안 운영이 바뀌었으면(승격 · 지우기) 바꿔 넣지 않고 409 로 알립니다.
- **되살리기를 무르기**: 팩토리의 서버가 `POST /v1/instances/{id}/restore/undo`(service key 만, SDK 는 `instances.undoRestore(id)`)를 부르면
  되살리기 직전의 DB(답의 `restore_point`)로 돌아갑니다. 되돌릴 지점은 하나라 한 번만 무릅니다. 되살린 뒤 승격이 있었으면 지점이 그 승격의 것으로
  바뀌어 무르지 못하고(409, 까닭이 문장으로 옵니다), 그때는 원하는 시점으로 다시 되살립니다.
- 거절되면(409) 까닭이 문장으로 옵니다. 가장 오랜 기반 백업보다 앞선 시점, 보관이 닿지 않는 시점, 빠진 WAL 조각이 있습니다.

## 클러스터 전체를 되살릴 때(재해 복구)

운영 클러스터의 기계나 디스크를 잃었을 때입니다. 아직 자동이 아닙니다. 모든 인스턴스가 내려가 있는 동안 합니다.

1. `orbitald` 를 멈춥니다. 남은 운영 클러스터가 있으면 멈추고 그 데이터 폴더는 지우지 말고 옆으로 옮겨 둡니다.
2. 되살릴 시점을 정합니다. `<폴더>/seal.json` 의 `at` 과 `<폴더>/wal` 의 마지막 조각이 보관된 끝입니다. 시점을 덮는 기반 백업은
   `<폴더>/base/*/backup.json` 의 `finished_at` 이 그 시점보다 앞선 것 가운데 가장 새 것입니다.
3. 새 기계에 같은 버전의 PostgreSQL 을 깔고, 그 기반 백업의 `data` 를 새 데이터 폴더로 복사합니다(주인은 postgres, 0700).
4. 새 데이터 폴더의 `postgresql.auto.conf` 에 `restore_command = 'cp <폴더>/wal/%f %p'`, `recovery_target_time = '<시점>'`,
   `recovery_target_action = 'promote'` 를 적고 `recovery.signal` 을 만든 뒤 띄웁니다. 복구가 끝나면 `pg_is_in_recovery()` 가 거짓이 됩니다.
   **보관 폴더를 새 클러스터의 `archive_command` 가 같은 이름으로 덮지 않게**, 새 기반 백업을 뜨기 전까지 보관은 새 폴더로 돌립니다.
5. **기록까지 되돌리기.** 레이어의 기록은 클러스터 안의 control database(`orbital_control`)에 있으므로 4 에서 그 시점의 것으로 함께 되살아났습니다.
   DB 와 기록이 같은 시점의 것이라 따로 맞출 것이 없습니다. 코드 저장소만 DB 밖에 있습니다. 그 기반 백업의 `records.tar` 를 새 `ORBITAL_HOME` 에 풉니다
   (`sources` · `apps`). 코드 저장소는 기반 백업을 뜬 때의 것이라 그 뒤에 올린 commit 이 없을 수 있습니다. 기록의 release 가 가리키는 commit 이 저장소에 없으면
   그 인스턴스는 되살아나지 않습니다(`orbitald: 운영 … 를 되살리지 못했습니다`). 팩토리가 그 commit 을 다시 올리게 합니다.
   `records.tar` 에는 그 백업을 뜬 기계에 놓인 인스턴스의 저장소만 있습니다. 관리 서버가 여럿이면 기계마다 자기 백업 폴더의 묶음을 씁니다.
6. 열쇠를 다시 넣습니다. `ORBITAL_SEAL_KEY` 와 `ORBITAL_SERVICE_KEYS` 는 백업에 없으므로 따로 지킨 것을 씁니다. 토큰의 열쇠(`ORBITAL_TOKEN_KEY` 를 주지 않았으면
   `token.key`)가 새로 생기면 앞에서 낸 에이전트의 토큰은 모두 무효가 됩니다.
   **기록을 앞 시점으로 되살렸으면, 그 시점 뒤에 거둔 service key 가 다시 살아 있습니다.** 팩토리마다 열쇠의 목록(`GET /v1/keys`)을 보고 거뒀던 것을
   다시 거두게 합니다. 그 시점 뒤에 만든 조직과 낸 열쇠는 없으므로 운영자가 다시 만들거나 냅니다.
7. `orbitald` 를 같은 `ORBITAL_MACHINE` 으로 띄웁니다. 기록에서 그 기계에 놓인 운영 중인 인스턴스의 router 를 다시 세우고, 빌드한 폴더가 없으면 다시 빌드합니다.
   기계의 이름이 다르면 아무것도 되살리지 않습니다(다른 기계의 것으로 봅니다).
8. 곧바로 `orbitald drill` 을 돌려 통과하는지 봅니다. 새 기반 백업이 생기고 그 뒤로 시점 복구가 다시 됩니다.
