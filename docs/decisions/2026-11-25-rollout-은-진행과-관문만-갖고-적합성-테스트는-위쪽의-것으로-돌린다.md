# rollout 은 진행과 관문만 갖고 적합성 테스트는 위쪽의 것으로 돌린다

- 날짜: 2026-11-25
- 상태: 정함(기획안 11절의 7번 「rollout: 포크 셋에 업데이트 하나를 밀기와 당기기로」)
- 근거: `crates/orbital-server/tests/rollout.rs`, `crates/orbital-core/src/rollout.rs` 와 `crates/orbital-core/tests/props.rs` 의 `rollout` 테스트 이름

## 결정

팩토리가 스캐폴드(위쪽)에 낸 업데이트 하나를 고객마다 갈라진 인스턴스 셋에 들인다. 끝 기준은 **한 곳이 실패하면 나머지가 멈추고, 적합성 테스트를 통과한 곳만 운영에 오른다**이다.

| 무엇 | 어떻게 |
|---|---|
| rollout 의 모양 | `{앱, 업데이트 commit, change, 물결}`. 인스턴스마다 `waiting` → `applied` → `previewed` → `passed` → `promoted`, 어디서든 `failed{까닭}` |
| 「적용됐다」 | release 의 commit 이 업데이트 commit 을 조상으로 담는다(git 의 조상 판정). 담지 않은 release 는 rollout 과 무관하게 오르내린다 |
| 합치기 | 레이어가 `git merge` 의 판정으로 기계적으로 합친다. 충돌하면 인스턴스를 건드리지 않고 충돌한 파일의 이름만 돌려준다. 에이전트는 묶음의 `origin/update` 를 합쳐 풀어 올린다 |
| 적합성 테스트 | `[conformance] run` · `files`. 명령과 폴더를 release 가 담은 가장 새 위쪽 commit 에서 가져와, 빈 자리에 그 폴더만 놓고 돌린다(인스턴스의 트리는 놓지 않는다). 위쪽이 선언했으면 모든 프리뷰에서 돈다 |
| 실행 | 빌드와 같은 실행기로 환경을 비워 돌리고, 프리뷰의 주소(`ORBITAL_PREVIEW_URL`)만 건넨다. 120초가 넘으면 멈추고 실패로 적는다. 통과 여부 · 걸린 시간 · 출력의 끝만 남긴다 |
| 멈춤 | 한 인스턴스가 실패하면(적합성 테스트 · 권한 검사 · 승격 뒤 되돌려짐) rollout 전체가 멈춘다. 팩토리가 service key 로 다시 열어야 이어지고, 실패한 곳은 처음부터 다시 지난다 |
| 물결 | 앞 물결이 모두 오르기 전에는 뒤 물결이 이 업데이트를 담은 release 를 올리지 못한다 |
| 밀기와 당기기 | 같은 기계다. rollout 의 `change` 로만 오르고, 승인자는 `Change::approver` 가 정한다(기능 업데이트는 고객, 법 · 보안 · 핵심 패키지는 팩토리) |
| 범위 | 만들기 · 합치기 · 다시 열기 · 거두기는 service key 만 한다. 토큰은 자기 인스턴스의 진행만 본다. 한 인스턴스는 같은 앱의 열린 rollout 하나에만 든다 |

## 왜

- **레이어가 에이전트를 돌리지 않는 까닭: 고치는 일과 지키는 일을 가른다.** 포크마다 코드를 고치는 에이전트는 팩토리(밀기)나 고객(당기기)의 플랫폼에서 이미 돌고,
  레이어에는 인스턴스 하나로 좁힌 토큰으로 들어온다. 레이어가 에이전트까지 돌리면 모델 · 비용 · 대화의 기록을 레이어가 갖게 되고, 「Orbital 은 host 를 모른다」가 깨진다.
  레이어가 가진 것은 git 의 사실과 관문이다. 그래서 rollout 은 진행을 적고, 관문을 지키고, 실패하면 멈추는 것까지만 한다.
- **「조상으로 담는다」가 적용의 뜻인 까닭: 어떻게 들였든 같은 사실을 본다.** 레이어가 합쳤든, 에이전트가 충돌을 풀어 합쳤든, 업데이트 위에서 다시 고쳤든
  release 의 commit 이 업데이트를 조상으로 담으면 그 업데이트가 들어 있다. 파일을 견주거나 에이전트의 말을 믿으면 고친 방법마다 판정이 달라진다.
  담지 않은 release 를 rollout 과 무관하게 두는 것도 같은 까닭이다. 고객의 급한 요청이 rollout 이 멈춘 동안 막히면 안 된다.
- **테스트를 위쪽에서 가져오는 까닭: 고치는 쪽이 시험지를 고치지 못하게 한다.** 포크의 에이전트는 포크의 파일을 모두 고칠 수 있다. 테스트를 포크에서 읽으면
  테스트를 지우거나 `exit 0` 으로 바꿔 통과시킬 수 있다. 선언(`run`)과 폴더(`files`)를 모두 위쪽의 commit 에서 읽고, 빈 자리에 그 폴더만 놓아 돌린다.
  포크의 트리를 함께 놓으면 포크가 `node_modules` 나 설정 파일, 테스트 폴더에 끼워 넣은 파일로 테스트의 프로세스를 바꿀 수 있어 놓지 않는다.
  포크는 프리뷰의 주소로만 잰다. 「release 가 담은 가장 새 위쪽 commit」을 쓰므로, 업데이트를 담은 release 는 업데이트의 테스트를, 아직 담지 않은 release 는 앞 버전의 테스트를 받는다.
- **멈춤을 넓게 거는 까닭: 한 곳의 실패는 업데이트의 잘못일 수 있다.** 실패가 그 포크의 사정인지 업데이트의 잘못인지 레이어는 가리지 못한다.
  가리지 못하는 동안 나머지를 계속 올리면 잘못된 업데이트가 퍼진다. 그래서 사람(팩토리)이 보고 다시 열기 전에는 아무도 새로 오르지 않는다. 이미 오른 곳은 내리지 않는다.
- **판정은 core 의 순수한 함수다.** 사건(적용 · 프리뷰 · 검사 · 승격 · 되돌려짐 · 다시 열기 · 거두기)을 받아 다음 상태나 거절의 까닭을 돌려준다.
  순서가 문제인 규칙이라 속성 테스트를 사건의 임의 순서로 돌린다. git 의 판정 · 실행 · 기록은 어댑터와 관리 서버에 둔다.

## 알려진 한계

- **적합성 테스트는 밖에서만 잰다.** 테스트의 자리에는 위쪽의 폴더만 있어, 포크의 파일을 읽어 확인하는 테스트(선언에 무엇이 적혔는지, 어느 패키지 버전인지)는
  쓰지 못한다. 필요해지면 포크의 트리를 코드가 아닌 자료로(읽기 전용 경로로) 건네는 길을 더한다. 테스트가 의존성을 쓰려면 그 폴더 안에 있어야 한다.
- **테스트의 프로세스는 격리되지 않는다.** 위쪽이 쓴 명령이 레이어의 기계에서 돈다. 지키는 것은 실행기의 격리이고, 개발용 실행기(`LocalRunner`)는 격리하지 않는다.
- **프리뷰에서 통과한 것이 운영에서의 통과를 보장하지 않는다.** 프리뷰는 씨앗 데이터의 DB 이고 운영의 데이터와 키가 다르다. 운영에서 걸러 주는 것은
  승격 직후의 상태 확인(서버가 뜨는지)뿐이고, 되돌려지면 그 인스턴스를 실패로 적어 멈춘다.
- **물결을 자동으로 넓히지 않는다.** 앞 물결이 모두 올라야 뒤 물결이 오를 수 있게 될 뿐, 오르는 것은 늘 사람의 승인이다. 실패를 몇 개까지 견디는 문턱도 없다.
- **승격 직후의 상태 확인만 본다.** 운영이 선 뒤 오류율을 지켜보다 멈추는 일은 없다.
- 업데이트 하나는 앱 하나의 것이다. 여러 앱에 같은 변경을 미는 것은 앱마다 rollout 을 만든다.
- 테스트의 출력은 끝 4000자만 남긴다. 테스트가 프리뷰의 답을 찍으면 그 안의 씨앗 데이터가 실린다(프리뷰의 것이라 에이전트가 본다고 본다).

## 아직 정하지 않은 것

- 팩토리의 본보기에 rollout 의 길(도구)을 두는 모양. 지금은 HTTP 와 SDK(`rollouts`, 작업의 `rollout()`)에만 있다.
- 끝난 rollout 의 업데이트를 묶음에서 빼는 때. 지금은 거둘 때만 뺀다.
