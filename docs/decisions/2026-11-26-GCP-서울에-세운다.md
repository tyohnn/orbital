# GCP 서울에 세운다

- 날짜: 2026-11-26
- 상태: 정했다(사람의 결정)
- 근거: [`findings.md`](../findings.md) 「GCP 서울의 VM 에서 실행기 후보와 레이어를 재다」, [Orbital 기획안](https://claude.ai/artifact/R9fEaCArNwVN1aWt9WPdzY) 13절

## 결정

레이어의 기계는 GCP 서울(`asia-northeast3`)에서 빌린다. 기획안이 제안했던 AWS 서울은 접는다.

## 왜

- **GCP 서울에서 필요한 것이 다 돈다는 것을 쟀다.** N2 VM 에 중첩 가상화를 켜면 `/dev/kvm` 이 서고, 그 안에서 Firecracker 스냅숏 복원으로
  Next.js 서버가 약 240ms 에 첫 응답을 준다. XFS 위 PostgreSQL 18 의 database 복제(`file_copy_method = clone`)도 된다(실측).
- **같은 VM 에 레이어를 세워 밖에서 한 바퀴를 돌렸다.** 인스턴스마다의 `https` 하위 도메인, 재우고 깨우기, 재시작 뒤의 데이터까지 봤다(실측).
- AWS 서울의 같은 기능은 발표만 확인했고 재지 않았다. 잰 쪽을 고른다.

## 그래서 지키는 것

- 빌리는 것은 기계(VM · 디스크 · 네트워크 · object storage)뿐이라는 [앞의 결정](2026-11-25-독립-제품으로-세우고-기계만-빌린다.md)은 그대로다.
  Cloud Run 은 대조군으로 쟀을 뿐 실행기로 쓰지 않는다.
- 실행기는 갈아 끼우는 자리(`Runner`)로 남긴다. 클라우드의 API 는 어댑터에만 둔다.

## 아직 정하지 않은 것

- 실행기를 Firecracker 로 직접 지을지. 기획안은 스냅숏 복원을 기본 길로 제안한다(0번의 숫자).
- 중첩 가상화 VM 과 맨 VM(베어메탈) 가운데 무엇을 쓸지. 이번 숫자는 중첩 가상화의 것이다.
- 도메인. 우선 `sslip.io` 로 재 봤고, 실제 고객을 받기 전에 우리 도메인과 와일드카드 인증서로 바꾼다.
