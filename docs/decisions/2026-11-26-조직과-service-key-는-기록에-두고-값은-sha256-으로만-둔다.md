# 조직과 service key 는 기록에 두고 값은 sha256 으로만 둔다

- 날짜: 2026-11-26
- 상태: 제안(구현하며 정했다. 사람의 확인이 남았다. 특히 아래 「테스트 이름」의 목록과 HTTP 의 모양)
- 근거: `crates/orbital-core/src/organization.rs` 와 그 예시 테스트, `crates/orbital-core/tests/props.rs` 의 `organization`,
  `crates/orbital-server/migrations/0003_organizations.sql`, `src/records/organizations.rs`, `src/layer/organizations.rs`, `src/http.rs` 의 `operator`,
  `crates/orbital-server/tests/organizations.rs`, `tests/machines.rs` 의 기록의 service key 테스트, `sdk/typescript/test/keys.test.ts`

## 결정

1. **조직은 기록(control database)에 둔다.** 새 마이그레이션 `0003` 이 `orbital.organization`(식별자 · 사람이 읽는 이름 · 종류 `live`/`test` · 만든 때 · 닫은 때)과
   `orbital.service_key`(식별자 · 조직 · sha256 · 사람이 붙인 이름 · 만든 때 · 거둔 때 · 마지막으로 쓴 때)를 더한다. 조직의 식별자는 코드가 쓰는 조직의
   이름(`OrganizationId`)과 같은 글자이고 `Ident` 로 검증한다(영문 소문자로 시작, 소문자 · 숫자 · 밑줄 24자).
2. **운영자의 열쇠(`ORBITAL_OPERATOR_KEY`, 기록 밖)로만 조직을 만든다.** 운영자의 길은 `/v1/operator/organizations` 아래 다섯이다.
   만들기(첫 열쇠를 함께 낸다) · 목록 · 하나(인스턴스와 살아 있는 열쇠의 수) · 열쇠 내기(잠긴 조직을 되찾는 길) · 닫기. 운영자의 열쇠로는 조직의 일
   (인스턴스 · 앱 · 승격 · 비밀 · 사용자 · 설정 · 열쇠의 목록과 거두기 · git)을 하지 못한다(403). service key 와 작업의 토큰은 운영자의 길을 열지 못한다(403).
   운영자의 열쇠를 주지 않은 레이어에는 그 길이 없다(404). 운영자의 열쇠는 32자 이상이고 `sk_` · `orb1.` 로 시작하지 않으며 설정의 service key 와 같지 않다(뜨지 않는다).
   **운영자는 열쇠를 거두지 않는다.** 급할 때는 조직을 닫는다. 거두는 길을 하나(조직의 열쇠)로 두어 「누가 거뒀나」가 늘 그 조직이다.
3. **열쇠의 값은 레이어가 갖지 않는다.** 값은 `sk_live_` · `sk_test_` 뒤에 난수 32바이트의 hex 다. 낼 때의 답 한 번에만 싣고, 기록에는 sha256(hex)만 둔다.
   목록 · 오류 · 로그 · 관리 서버의 폴더에는 값도 그 일부도 없다(테스트가 control database 의 모든 줄 · 받은 모든 답 · 관리 서버들의 폴더를 훑는다).
   목록에는 식별자 · 이름 · 머리말(종류) · 만든 때 · 거둔 때 · 마지막으로 쓴 때만 싣는다. 끝 네 글자 같은 값의 조각도 싣지 않는다.
4. **열쇠를 바꾸는 길은 「새 열쇠를 내고, 옛 열쇠를 거둔다」이다.** `POST /v1/keys`(값은 이 답에만) · `GET /v1/keys` · `DELETE /v1/keys/{id}`.
   둘은 거두기 전까지 함께 산다. 다른 조직의 열쇠 식별자는 없는 식별자와 같은 404 다. 이미 거둔 것을 다시 거두면 아무것도 바꾸지 않고 200 이다.
5. **살아 있는 마지막 열쇠는 거두지 못한다(409).** 거두면 그 조직이 스스로 잠기고, 되찾으려면 운영자가 나서야 한다. 새 열쇠를 먼저 내고 옮긴 뒤에 거둔다.
   열쇠가 새어 급하게 끊어야 하면 새 열쇠를 내고 옛 것을 거두는 두 요청이면 되고, 새어 나간 열쇠를 쥔 쪽도 어차피 열쇠를 더 낼 수 있으므로 「마지막을 거두기」가
   막는 공격은 없다. 운영자가 열쇠를 낼 수 있어(`POST /v1/operator/organizations/{id}/keys`) 잃어버린 조직도 되찾는다.
6. **요청마다 기록을 본다. 짧게 기억하지 않는다.** 거둔 열쇠와 닫힌 조직의 열쇠는 어느 관리 서버에서든 다음 요청부터 401 이다(닫은 작업과 같은 규칙).
   넘겨받은 요청(`x-orbital-forwarded-by`)도 놓인 기계가 처음처럼 다시 판정한다. 기록을 읽지 못하면 「없는 열쇠」(401)가 아니라 500 이다.
7. **설정의 열쇠(`ORBITAL_SERVICE_KEYS`)는 그대로 받는다.** 기록의 열쇠와 함께 살고 같은 조직 이름을 가리킬 수 있다. 그 조직이 기록에 있으면 그 종류를 따르고,
   기록에서 닫혔으면 설정의 열쇠도 받지 않는다(그래서 설정의 열쇠도 요청마다 조직의 줄 하나를 읽는다). 기록에 없는 조직은 운영의 조직으로 보고, 열쇠를 더 내지 못한다(409).
   `ORBITAL_SERVICE_KEYS` 는 이제 없어도 뜬다.
8. **시험용 조직(`test`)은 인스턴스의 수에만 상한이 있다**(`ORBITAL_TEST_INSTANCE_LIMIT`, 기본 10, 넘으면 409 와 「지우거나 운영의 조직에서 세운다」).
   그 밖의 관문(메일 · 복구 훈련 · 권한 · 승격 · 비밀)은 종류를 받지 않는다. 종류가 들어가는 판정은 core 의 `judge_key` · `judge_new_instance` · `judge_issue` 셋뿐이다.
9. **조직을 닫으면 그 조직의 열쇠는 어디서 왔든 받지 않는다.** 인스턴스가 남아 있으면 닫지 않고, 남은 인스턴스의 식별자와 「먼저 지운다」를 알린다(409).
   인스턴스 세우기와 조직 닫기는 같은 조직의 advisory lock(트랜잭션 동안)으로 한 줄로 서서, 닫는 사이에 인스턴스가 생기거나 두 관리 서버가 함께 상한을 넘지 않는다.
10. **마지막으로 쓴 때는 분 단위로 뭉친다.** 받아들인 기록의 열쇠는 그 분의 시작으로 `used_at` 을 적되, 이미 그 분이 적혀 있으면 적지 않는다(한 열쇠에 분마다 한 번).
   적지 못해도 요청은 막지 않는다(읽기는 됐다).
11. **판정은 core 의 순수 함수다.** `organization::{judge_key, judge_revoke, judge_issue, judge_new_instance, judge_close, check_label, used_at}`.
   sha256 · 난수 · 시계는 관리 서버가 한다. 조직과 열쇠의 일은 기록에만 닿으므로 `placement` 의 `Errand::Organization` 은 `Anywhere` 다.
12. SDK(`@harmony/orbital/server`)에는 조직의 열쇠 셋(`keys.create` · `keys.list` · `keys.revoke`)만 둔다. 운영자의 일은 팩토리가 쓰는 것이 아니라 SDK 에 없다.

**열쇠가 새어 나갔을 때.** 새어 나간 열쇠를 쥔 쪽은 열쇠를 더 내고 주인의 열쇠를 거둘 수 있어, 주인이 하나씩 거두는 동안 새로 내며 버틸 수 있다.
그래서 운영자의 열쇠 내기에 `revoke_others` 를 둔다. 조직의 줄을 잠그고 한 트랜잭션에서 그 조직의 살아 있는 열쇠를 모두 거두고 새 열쇠 하나만 남긴다.
조직을 닫는 길은 인스턴스가 남아 있으면 쓰지 못하므로(고객이 있는 조직), 이것이 되찾는 길이다. service key 로는 이 길을 열지 못한다.

## HTTP 의 모양

| 길 | 열쇠 | 답 |
|---|---|---|
| `POST /v1/operator/organizations` `{ id, name, kind: "live"\|"test", label? }` | 운영자 | `{ organization: { id, name, kind, created_at }, key: { id, label, key, created_at } }` · 있으면 409 |
| `GET /v1/operator/organizations` | 운영자 | `{ organizations: [ { id, name, kind, created_at, closed_at? } ] }` |
| `GET /v1/operator/organizations/{id}` | 운영자 | `{ id, name, kind, created_at, closed_at?, instances, keys }` |
| `POST /v1/operator/organizations/{id}/keys` `{ label, revoke_others? }` | 운영자 | `{ id, label, key, created_at, revoked }`(`revoked` 는 함께 거둔 열쇠의 수) · 없으면 404 · 닫혔으면 409 |
| `POST /v1/operator/organizations/{id}/close` | 운영자 | `{ organization }` · 인스턴스가 남았으면 409 |
| `POST /v1/keys` `{ label }` | service key | `{ id, label, key, created_at }` |
| `GET /v1/keys` | service key | `{ keys: [ { id, label, prefix, created_at, revoked_at, used_at } ] }` |
| `DELETE /v1/keys/{id}` | service key | 그 열쇠 한 줄(위의 모양) · 다른 조직의 것이면 404 · 마지막이면 409 |

거둔 열쇠와 닫힌 조직의 열쇠는 `401` `unauthorized` 에 까닭을 싣는다(「거둔 service key 입니다…」, 「닫힌 조직의…」). 이 글은 그 열쇠를 가진 쪽만 본다.

## 왜

- **값을 갖지 않는다.** 레이어가 값을 가지면(평문이든 봉인이든) control database 와 그 백업을 읽는 쪽이 모든 팩토리의 운영을 바꿀 수 있다. sha256 만 두면
  기록이 새어도 열쇠가 되지 않는다. 열쇠는 난수 256비트라 sha256 을 거꾸로 찾거나 사전으로 맞히지 못하고, 그래서 느린 해시(bcrypt · argon2)가 필요 없다.
  봉인(`ORBITAL_SEAL_KEY`)과 달리 레이어가 값을 다시 쓸 일이 없으므로 풀 수 있는 모양으로 둘 까닭이 없다.
- **견주는 시간.** 설정의 열쇠는 sha256 끼리 견주고, 기록의 열쇠는 sha256 을 색인으로 찾는다. 견주기가 일찍 끝나는 만큼 새는 것은 「보낸 값의 해시가 기록의
  해시와 앞에서 몇 글자 맞는가」뿐이고, 해시의 앞을 맞혀도 그 해시가 될 값을 찾지 못하므로 시간으로 열쇠를 맞혀 가지 못한다. 그래서 상수 시간 견주기를 따로 두지 않았다.
  운영자의 열쇠도 sha256 끼리 견준다.
- **요청마다 읽는다.** 짧게 기억하면 거둔 열쇠가 그 시간 동안 다른 관리 서버에서 통하는 창이 생긴다. 열쇠가 새어 거두는 때가 가장 빨라야 하는 때다.
  잰 값(아래 「값」)이 요청 하나에 비해 작아 창을 두지 않았다.
- **운영자의 열쇠를 좁힌다.** 운영자의 열쇠는 모든 조직을 만들고 닫는다. 이 열쇠로 조직의 일까지 되면 새어 나갔을 때 모든 팩토리의 운영이 열린다.
  조직의 일을 못 하게 두면 운영자의 열쇠로 할 수 있는 가장 나쁜 일은 조직을 닫는 것(인스턴스가 남은 조직은 닫히지 않는다)과 그 조직에 열쇠를 더 내는 것이다.
  뒤의 것은 조직의 일을 여는 길이 되므로 운영자의 열쇠는 기록 밖에 두고 기록에 남기지 않는다(남은 일 참고).
- **설정의 열쇠를 남긴다.** 개발과 지금의 테스트 수백 개가 설정의 열쇠로 돈다. 기록의 열쇠로 옮기는 길(같은 이름으로 조직을 만들고, 기록의 열쇠로 바꾼 뒤 설정에서 지운다)이 있으면 된다.
- **닫힌 조직은 설정의 열쇠도 막는다.** 「닫으면 그 조직의 열쇠를 모두 받지 않는다」를 열쇠가 어디서 왔는지에 따라 다르게 두면, 운영자가 설정을 함께 고치기를 잊은 때 닫힌 조직이 계속 돈다.

## 값

- **요청마다 기록을 한 번 더 읽는다.** 기록의 열쇠는 sha256 의 색인 하나로 조직과 함께 읽고(조인), 설정의 열쇠는 조직의 줄 하나를 읽는다.
  같은 기계의 PostgreSQL 에 붙어 잰 열쇠 판정 한 번(`Layer::caller`, 2000번의 평균)은 release 빌드에서 설정의 열쇠 0.14ms · 기록의 열쇠 0.23ms · 모르는 열쇠 0.21ms 이고,
  debug 빌드에서 0.3–0.4ms 다(앞에는 메모리의 견주기라 1µs 아래). `GET /v1/keys` 한 번은 release 에서 0.36–0.48ms 다. 인스턴스의 기록 하나를 읽는 데 0.16ms 가 들므로
  service key 의 요청마다 그만큼이 한 번 더 든다. 다른 클러스터에 붙으면 왕복 시간만큼 는다. 느려지면 짧게 기억하기보다 연결과 준비된 문장을 먼저 줄인다.
- **기록을 앞 시점으로 되살리면 그 뒤에 거둔 열쇠가 다시 산다.** sha256 이 control database 와 함께 백업에 들기 때문이다. 런북(`docs/runbook/복구.md`)의 6에 다시 거두는 절차를 적었다.
- 설정의 열쇠만 쓰던 레이어도 이제 control database 가 내려가면 service key 의 길이 모두 500 이다. 앞에도 그 길의 거의 모든 일이 기록을 읽었다.
- 마지막으로 쓴 때는 분 단위라 「방금 쓴 열쇠인가」는 1분 안에서 가리지 못한다.
- 시험용 조직의 상한은 세운 인스턴스의 수만 센다. 프리뷰 · 빌드 · 요청의 양은 재지 않는다(계량이 오면 함께 정한다).

## 아직 정하지 않은 것

- 사람의 가입 · 로그인 · 구성원과 대시보드(이번에 짓지 않았다). 열쇠마다 누가 냈는지(`actor`)도 그때 적는다.
- 운영자의 열쇠를 돌려 바꾸는 길(지금은 환경 변수를 바꿔 다시 띄운다)과, 운영자의 일을 기록에 남기기(감사 기록).
- 열쇠마다 권한을 좁히기(읽기만 · 인스턴스 하나만). 지금 service key 는 그 조직의 모든 일을 한다.
- 시험용 조직을 운영의 조직으로 바꾸기, 닫은 조직을 다시 열기와 지우기.
- 열쇠의 만료 기한.
