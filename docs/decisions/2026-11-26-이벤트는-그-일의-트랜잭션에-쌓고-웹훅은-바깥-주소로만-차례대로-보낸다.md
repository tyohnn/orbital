# 이벤트는 그 일의 트랜잭션에 쌓고 웹훅은 바깥 주소로만 차례대로 보낸다

- 날짜: 2026-11-26
- 상태: 제안(구현하며 정했다. 사람의 확인이 남았다. 특히 아래 「테스트 이름」의 목록, 이벤트의 종류와 몸, HTTP 의 모양)
- 근거: `crates/orbital-core/src/event.rs` · `webhook.rs` 와 그 예시 테스트, `crates/orbital-core/tests/props.rs` 의 `event` · `webhook`,
  `crates/orbital-server/migrations/0004_events.sql`, `src/records/events.rs`, `src/layer/events.rs`, `src/webhook.rs`,
  `crates/orbital-server/tests/events.rs`, `sdk/typescript/test/events.test.ts`
- 기획의 문장: 「승격 요청, 승격, 실패, rollout 의 진행을 서명해서 보낸다. 지금은 팩토리가 물어봐야 안다」

## 결정

1. **이벤트는 기록(control database)의 `orbital.event` 에 쌓는다**(마이그레이션 `0004`). 한 줄은 id(차례) · 조직 · 종류 · 인스턴스(있으면) · 몸(jsonb) · 생긴 때다.
   어느 관리 서버가 일을 했든 같은 표에 쌓인다. 인스턴스와 조직은 외래 키가 아니다. 지운 인스턴스의 이벤트(`instance.deleted` 까지)와
   설정(`ORBITAL_SERVICE_KEYS`)에만 있는 조직의 이벤트도 남는다. 30일(core 의 `event::RETENTION`)이 지나면 걷는다.
2. **이벤트는 그 일을 적는 트랜잭션 안에서 쌓는다.** 인스턴스의 줄을 고치는 `update_instance_noting`, rollout 의 줄을 고치는 `update_rollout`,
   인스턴스를 세우는 `insert_instance_checked`, 지우는 `remove_instance`, 비밀의 요청을 적는 `Vault::request` 가 같은 트랜잭션에 쌓는다.
   고친 것이 commit 될 때만 이벤트가 남고, 이벤트를 쌓지 못하면 고친 것도 적지 않는다. 그래서 일어나지 않은 일의 이벤트는 나가지 않는다.
   예외는 하나다. **되돌려진 승격(`promotion.failed`)** 은 운영을 앞의 모습으로 돌린 것이라 고칠 줄이 없어, 되돌린 바로 뒤에 따로 쌓는다(아래 「값」).
3. **한 조직의 이벤트는 그 조직의 advisory lock(트랜잭션 동안)을 쥐고 쌓는다.** 그래서 조직 안에서는 id 의 차례가 commit 의 차례와 같고,
   「`after` 뒤의 것」을 읽은 쪽이 나중에 더 작은 id 가 끼어드는 것을 보지 않는다(차례대로 보내기의 바탕). 조직이 다르면 서로 기다리지 않는다.
4. **종류와 몸은 core 의 `event::Body` 가 정한다.** 갈래마다 칸을 타입으로 정해 두어 값이 들어갈 칸이 없다(아래 표).
   rollout 의 이벤트는 고치기 전과 뒤의 rollout 을 견주는 순수 함수(`rollout_notes`)가 낸다. 인스턴스마다의 진행이 먼저이고 rollout 의 상태가 뒤다.
5. **물어보는 길**: `GET /v1/events?after=<id>&limit=<n>`(service key). 자기 조직의 것만 id 의 차례로, 기본 100 · 상한 500. 판정은 core 의 `event::page`.
6. **웹훅은 조직마다 주소 하나**다. `PUT /v1/settings/webhook {url}` 로 걸고 `DELETE` 로 뗀다. 걸 때 레이어가 서명의 비밀(`whsec_` + 난수 32바이트의 hex)을
   만들어 **그 답에 한 번만** 싣고, 기록에는 조직에 묶어 봉인한 글로 둔다(`orbital/webhook/v1`). 봉인의 열쇠가 없는 레이어에서는 걸지 못한다(409).
   비밀을 바꾸려면 다시 건다. 다시 봉인(`ORBITAL_SEAL_KEY_PREVIOUS`)의 대상이다. 처음 걸면 그 뒤에 생긴 이벤트부터 보내고(밀린 것은 목록으로 받는다),
   다시 걸면 보낸 자리를 그대로 두어 밀린 것이 새 주소로 새 비밀의 서명과 함께 간다.
7. **서명**: `orbital-signature: t=<유닉스 초>,v1=<hex(HMAC-SHA256(비밀, "<t>.<본문>"))>`. 본문은 이벤트 하나의 JSON(`{id, type, created_at, organization, instance?, data}`)이고
   목록의 한 줄과 같은 모양이다. `orbital-event-id` · `orbital-event-type` 도 싣는다. SDK 의 `verifyWebhook` 이 `timingSafeEqual` 로 견주고 시간차(기본 300초)를 넘으면 거절한다.
8. **전달은 적어도 한 번, 조직마다 차례대로.** 보낼 때가 된 웹훅의 줄 하나를 `FOR UPDATE SKIP LOCKED` 로 잠그고 그 조직의 다음 이벤트 하나를 보낸 뒤
   결과를 적고 commit 한다. 2xx 가 아니거나 닿지 못하면 core 의 `after_failure` 가 다음 때를 정한다: 30초 · 2분 · 10분 · 1시간 · 6시간, 그 뒤로 6시간마다,
   처음 실패에서 하루가 되는 때를 넘기지 않게 마지막 시도를 그때로 당기고 그때도 실패하면 그 이벤트를 그만두고(`abandoned`) 뒤의 것으로 넘어간다.
   앞의 것이 끝나기(보냈거나 그만뒀다) 전에는 뒤의 것을 보내지 않는다. 받는 쪽은 `id` 로 겹침을 거른다.
9. **밖으로 나가는 요청의 대상을 가둔다(SSRF).** 주소의 글은 core 의 `webhook::judge_url`(`https://` 만, 사용자 이름 · 조각 · 빈칸 없음, 호스트는 DNS 의 이름이나 IP,
   숫자뿐인 이름과 8 · 16 진수의 IP 표기는 받지 않음), 풀어 나온 IP 는 `judge_resolved`(**모두** 바깥이어야 한다)가 판정한다. 관리 서버는 이름을 풀어
   판정한 **그 주소에만** 붙는다(ureq 의 이름 풀기 자리에서 판정한 주소만 돌려준다. TLS 의 이름과 `Host` 는 원래 호스트). 걸 때와 **보낼 때마다** 판정한다.
   리다이렉트는 따라가지 않고, 프록시를 쓰지 않으며, 연결은 5초 · 전체는 10초(`Options::webhook_timeout`), 답의 본문은 읽지 않고 버린다.
   개발용 레이어(`ORBITAL_DEV_WEBHOOK=private`, `Options::dev_webhooks`)만 `http://` 와 loopback · 사설 · CGNAT · ULA 를 받고, 뜰 때 한 줄로 알린다.
   그때도 link-local(메타데이터 주소) · 멀티캐스트 · IPv4 를 품은 IPv6 는 받지 않는다. 이름 풀기는 `webhook::Resolve` 로 갈아 끼운다(테스트).
10. **어느 관리 서버든 한다.** 이벤트를 보고 웹훅을 거는 일은 기록에만 닿는다(`placement` 의 `Errand::Events` 는 `Anywhere`). 보내는 일도 관리 서버마다
    뒤의 스레드가 1초마다(`Options::webhook_every`) 하고 레이어가 내려가면 멈춘다. 봉인의 열쇠가 없는 레이어는 웹훅을 걸 수 없어 띄우지 않는다.
    테스트는 스레드를 끄고 `Layer::deliver_due` 를 바로 부른다.
11. 운영자 키와 작업의 토큰으로는 이벤트를 보지도 웹훅을 걸지도 못한다(403, 토큰은 core 의 `Action::Events` 가 「service key 로만」이라 판정한다).

## 종류와 몸

| 종류 | 생기는 자리 | `instance` | `data` |
|---|---|---|---|
| `promotion.requested` | 승격 요청을 적는 트랜잭션 | 그 인스턴스 | `release` · `commit` |
| `promotion.succeeded` | 운영을 적는 트랜잭션 | 그 인스턴스 | `release` · `commit` · `previous_release` · `change` · `approved_by` · `migrations`(수) · `rollout` |
| `promotion.failed` | 되돌린 바로 뒤(따로) | 그 인스턴스 | `release` · `commit` · `previous_release` · `migrated`(참 · 거짓) · `rollout` |
| `rollout.advanced` | rollout 의 줄을 고치는 트랜잭션 | 그 인스턴스 | `rollout` · `app` · `update` · `instance` · `progress`(`{state, reason?}`) · `tally` |
| `rollout.halted` | 〃 | 없음 | `rollout` · `app` · `update` · `failed`(`[{instance, reason}]`) · `tally` |
| `rollout.resumed` · `rollout.completed` · `rollout.cancelled` | 〃 | 없음 | `rollout` · `app` · `update` · `tally` |
| `secret.requested` | 요청을 적는 트랜잭션 | 그 인스턴스 | `name` |
| `instance.created` | 인스턴스를 적는 트랜잭션 | 그 인스턴스 | `app` · `version` |
| `instance.deleted` | 인스턴스를 지우는 트랜잭션 | 그 인스턴스 | `app` |

`tally` 는 `{waiting, applied, previewed, passed, promoted, failed}` 의 수다. 비밀의 값 · 운영 데이터의 행 · 로그의 글 · 토큰 · 열쇠 · Postgres 의 오류 문구는 싣지 않는다.
비밀을 요청한 까닭(`reason`)은 에이전트가 적은 글이라 싣지 않는다(요청의 줄과 `GET …/secrets` 에만 있다).

## HTTP 의 모양

| 길 | 열쇠 | 답 |
|---|---|---|
| `GET /v1/events?after=&limit=` | service key | `{ events: [이벤트], next, has_more }` · 질의가 틀리면 422 |
| `GET /v1/settings/webhook` | service key | `{ webhook: null \| { url, created_at, delivery } }` |
| `PUT /v1/settings/webhook` `{ url }` | service key | `{ webhook, secret }` · 주소가 틀리거나 안쪽이면 422 · 봉인의 열쇠가 없으면 409 |
| `DELETE /v1/settings/webhook` | service key | `{ removed }` |

`delivery` 는 `{ delivered_through, pending, next_at, failures, last_attempt_at, last_status, last_error, delivered_at, abandoned, last_abandoned }` 이다.
`last_error` 는 `refused_address` · `unresolved` · `unreachable` · `timed_out` · `status`(3xx 포함) · `unsealed` 가운데 하나이고, 받은 답의 본문은 싣지 않는다.
주소가 안쪽으로 풀려 걸지 못할 때 무엇으로 풀렸는지는 알리지 않는다(레이어 안쪽의 이름을 알아내는 길이 되지 않게).
SDK 는 `events.list` · `webhook.get` · `set` · `remove` 와 `verifyWebhook`(`OrbitalWebhookError` 의 `malformed` · `stale` · `mismatch`)이다.

## 왜

- **같은 트랜잭션에 쌓는다.** 일을 먼저 적고 이벤트를 따로 쌓으면 그 사이에 죽을 때 이벤트가 빠지고, 이벤트를 먼저 쌓으면 일이 깨질 때 없던 일이 알려진다.
  레이어의 기록이 이미 줄마다 「잠그고 읽어 고친 뒤 한 트랜잭션으로 적는다」라서, 그 트랜잭션에 한 줄을 더하는 것이 가장 싸고 정확하다(outbox 의 모양).
- **보내는 쪽은 줄을 잠근 채로 보낸다.** 「누가 보내는 중인가」를 시계로 정하는 임대(lease)는 관리 서버의 시계가 어긋나면 둘이 함께 보낸다. 줄의 잠금은
  관리 서버가 죽으면 연결이 끊겨 바로 풀리고, `SKIP LOCKED` 라 다른 관리 서버는 기다리지 않고 다른 조직을 보낸다. 값으로, 보내는 동안(10초 안) 그 조직의
  웹훅을 걸고 떼는 요청이 기다린다.
- **조직마다 차례대로.** 팩토리가 「승격됨」 뒤에 「요청함」을 받으면 화면이 거꾸로 선다. 앞의 것이 실패하면 뒤의 것도 기다리게 했다. 대신 받는 쪽이
  오래 죽어 있으면 하루에 한 이벤트씩 그만두며 밀린다(아래 「아직 정하지 않은 것」).
- **이름 풀기와 연결 사이에 틈을 두지 않는다.** 「풀어 보고 괜찮으면 URL 로 보낸다」는 보낼 때 다시 풀어 다른 주소로 붙는다(DNS rebinding).
  판정한 주소를 연결에 그대로 쓰면 틈이 없다. ureq 가 리다이렉트 등으로 다른 이름을 풀려 해도 우리의 풀이는 늘 처음 판정한 호스트만 푼다.
- **값을 싣지 않는 것을 타입으로 막는다.** 몸이 자유로운 JSON 이면 누군가 편해서 오류 문구나 로그를 넣는다. 칸을 core 의 enum 으로 정해 두면 새 칸을 더하는 일이
  core 의 리뷰를 지난다.

## 값

- **이벤트가 빠질 수 있는 자리.** ① `promotion.failed` 는 되돌린 뒤 따로 쌓으므로 그 사이에 관리 서버가 죽거나 기록에 닿지 못하면 빠진다(로그에 한 줄만 남는다).
  ② 웹훅은 30일이 지나 걷힌 이벤트와 하루 동안 보내지 못해 그만둔 이벤트를 보내지 않는다(그만둔 것은 `abandoned` · `last_abandoned` 로 보이고 목록으로 받는다).
  ③ 처음 걸기 전과, 뗀 뒤 다시 걸기 전에 생긴 이벤트는 웹훅으로 가지 않는다(목록에는 있다). ④ control database 를 지난 시점으로 되살리면 id 가 다시 쓰여
  받는 쪽이 `id` 로 거르다 새 이벤트를 버릴 수 있다(되살린 뒤에는 받는 쪽의 기억을 비워야 한다. 런북에 아직 없다).
- **겹쳐 갈 수 있는 자리.** ① 보낸 뒤 결과를 commit 하기 전에 관리 서버가 죽거나 DB 가 끊기면 다른 관리 서버가 같은 이벤트를 다시 보낸다.
  ② 받는 쪽이 처리하고도 10초 안에 2xx 를 주지 못하면 실패로 보고 다시 보낸다. 그래서 받는 쪽은 `id` 로 거른다.
- **한 관리 서버는 조직 넷까지 함께 보낸다**(보내는 스레드 넷, 스레드마다 보내는 동안 기록의 연결 하나를 쥔다). 느리게 답하는 받는 쪽 하나가 다른 조직의 전달을 붙들지 못한다. 느린 받는 쪽이 넷을 넘으면 그만큼 늦는다. 같은 조직 안에서는 여전히 차례대로다.
- 이벤트를 쌓는 조직의 차례(advisory lock)는 트랜잭션이 끝날 때까지 쥔다. 한 조직의 일이 많으면 그 조직의 쓰기끼리 잠깐 줄을 선다(다른 조직과는 서지 않는다).
- 보내는 스레드는 관리 서버마다 1초에 한 번 control database 에 묻는다(보낼 것이 없으면 질의 하나). 걷기는 한 시간에 한 번이다.
- `promotion.succeeded` 와 그 rollout 의 `rollout.advanced` 는 다른 줄의 트랜잭션이라 사이에 다른 이벤트가 낄 수 있다. 차례는 commit 의 차례다.
- 이벤트의 `instance` 는 인스턴스를 지운 뒤에도 30일 동안 남는다. 「인스턴스를 지우면 그 줄이 모두 지워진다」는 이벤트의 기록 밖에서만 참이다.

## 아직 정하지 않은 것

- 오래 닿지 않는 주소를 멈추기(지금은 하루에 한 이벤트씩 그만두며 밀린다). 팩토리에게 「웹훅이 멈췄다」를 알리는 길.
- 조직마다 여러 주소, 종류를 골라 받기, 같은 조직의 다른 이벤트를 나란히 보내기.
- 지난 이벤트를 다시 보내 달라는 길(지금은 목록으로 받는다). 되살린 control database 와 id 의 겹침.
- 서명의 비밀 둘을 겹쳐 두고 돌려 바꾸기(지금은 다시 걸면 바로 바뀐다. SDK 는 머리말에 `v1` 이 여럿이어도 받는다).
- 팩토리의 본보기(`examples/factory-todo`)에 받는 길을 두는 것. 본보기는 에이전트 플랫폼의 MCP 앱이라 승인 카드가 승격 요청을 이미 물어 보고, 받는 길을 둘 자연스러운 화면이 아직 없어 두지 않았다.
- 서명된 신원 · 토큰의 열쇠처럼, 기계 사이에서 서명을 확인하는 일(mTLS)과 함께 밖으로 나가는 요청의 망 제한(egress proxy).
