# 대시보드는 공개 API 위에 짓고 이력은 따로 쌓는다

- 날짜: 2026-11-26
- 상태: 제안(구현하며 정했다. 사람의 확인이 남았다. 특히 「운영의 로그」의 경계, 아래 「테스트 이름」의 목록과 HTTP 의 모양)
- 근거: `crates/orbital-core/src/listing.rs` · `fleet.rs` · `history.rs` 와 그 예시 테스트, `crates/orbital-core/tests/props.rs` 의 `listing` · `fleet`,
  `crates/orbital-server/migrations/0005_dashboard.sql`, `src/records/dashboard.rs`, `src/layer/dashboard.rs`, `src/http.rs`,
  `crates/orbital-server/tests/dashboard.rs`, `tests/backup.rs` 의 이력 테스트, `crates/orbital-pg/tests/auth.rs` 의 연결된 클라이언트,
  `sdk/typescript/test/dashboard.test.ts`
- 기획의 문장: 「대시보드는 공개 API 위에 짓는다. 목록 · 이력 · 이벤트의 API 가 빠진 곳이 바로 드러나고, 팩토리가 같은 것을 제 화면에 넣을 수 있다」

대시보드의 화면과 사람의 로그인은 이번에 짓지 않았다. 화면이 올라설 조회 API 만 지었다. 모든 길은 service key 로만 열린다.

## 화면마다 답하는 길

| 화면 | 보이는 것 | 앞에서 답하던 길 | 이번에 더한 길 | 아직 빠진 것 |
|---|---|---|---|---|
| 함대 | 인스턴스 목록, 갈라진 버전, 운영의 release, 마지막으로 오른 때, 실패한 곳 | 없음(인스턴스를 하나씩 알아야 했다) | `GET /v1/instances?after=&limit=` | 자는지 깨어 있는지는 목록에 없다(아래 4) |
| 인스턴스 하나 | release 의 이력, 요청과 승인, 권한의 변화, 리허설의 숫자, 되돌린 기록 | `GET …/production`(지금의 것만) · `GET …/promotion-request`(기다리는 것만) · 이벤트(30일) | `GET /v1/instances/{id}` · `GET …/history?after=&limit=` · `GET …/production/services` | 이 기능 전에 오른 것의 이력(기록이 없다) |
| 로그 | 빌드와 서버의 로그 | 프리뷰의 로그만(`GET …/previews/logs`, 토큰) | `GET …/production/logs?lines=`(service key 만) | 로그를 날짜로 고르기 · 흘려 보기 · 검색 |
| 사용자와 로그인 | 사용자, 업무 역할, 연결된 MCP 클라이언트 | `GET …/users` | `GET …/oauth-grants` | 사용자 하나의 세션 목록 |
| 설정 | service key, Resend 와 Google 의 키(넣었는지만), 도메인 | `GET /v1/keys` · `GET /v1/settings/auth` · `GET /v1/settings/webhook` · 운영의 주소(`GET …/production` 의 `services[].url`) | `GET /v1/organization` | 사용자 정의 도메인(아직 없는 기능) |
| rollout | 업데이트가 어디까지 올랐고 어디서 멈췄는지 | `GET /v1/rollouts/{id}`(식별자를 알아야 했다) | `GET /v1/rollouts?after=&limit=` | 앱으로 거르기 |
| 사용량과 비용 | 인스턴스마다 | — | — | 계량이 없다(범위 밖) |

## 결정

1. **목록은 쪽으로 나눠 SQL 에서 자른다.** 함대(`GET /v1/instances`)와 rollout(`GET /v1/rollouts`)의 차례는 (만든 때, 식별자)이고, 쪽의 표식은
   마지막 줄의 `<만든 때>.<식별자>` 다(`next`). `limit` 은 기본 100 · 상한 500. 판정은 core 의 `listing::page` 다.
   표식은 자기 조직의 줄에서만 지어지고 질의는 언제나 조직으로 거르므로, 다른 조직의 표식(식별자)을 넣어도 자기 조직의 그 자리 뒤가 나올 뿐이다.
   **전역의 차례 번호를 표식으로 쓰지 않았다.** 번호의 틈으로 다른 조직이 그사이 몇을 만들었는지가 새기 때문이다.
   만든 때를 모르는 앞의 인스턴스(이번 마이그레이션 전에 선 것)는 0 으로 보고 맨 앞에 선다. 답의 `created_at` 은 `null` 이다.
2. **함대의 한 줄은 기록만으로 짓는다.** 어느 관리 서버든 답하고, 인스턴스의 몸을 풀지 않고(봉인을 열지 않는다) 필요한 칸만 SQL 로 읽는다.
   `{ id, app, version, machine, created_at, production: { release, promoted_at } | null, promotion_requested, preview, last_promotion: { release, at, outcome } | null }`.
   `last_promotion` 은 이력의 마지막 승격 줄이고 `outcome` 은 `promoted` · `rolled_back` 이다. 「실패한 곳」은 `outcome = rolled_back` 이다.
   `preview` 는 기록에 프리뷰의 database 가 적혀 있는가다(다시 뜬 관리 서버가 걷기 전의 것도 참이다).
3. **release 의 이력은 새 표(`orbital.release_history`)에 그 일의 트랜잭션에서 쌓는다.** 운영을 적는 트랜잭션(승격 · 되살리기 · 무르기)에
   한 줄을 더하고, 되돌려진 승격은 이벤트와 함께 한 트랜잭션에 쌓는다(인스턴스의 줄을 잠근다). 이벤트의 표는 30일 뒤에 걷히므로 이력으로 쓰지 않는다.
   줄의 번호(`n`)는 인스턴스마다 1 부터 차례대로이고 `after` 는 이 번호다. 인스턴스를 지우면 외래 키로 함께 지워진다.
   **보관의 상한은 인스턴스마다 500 줄**이다(core 의 `history::KEEP`). 넘으면 같은 트랜잭션에서 오랜 것부터 걷는다. 승격은 사람이 승인하는 일이라
   500 번에 닿기 어렵고, 줄마다 권한 변화의 문장이 들어 상한 없이 두면 한 인스턴스가 기록을 키운다.
4. **이력의 한 줄**은 core 의 `history::Entry` 가 정한다. 갈래는 `promoted` · `rolled_back` · `restored` · `restore_undone` 이다.
   승격의 줄: `release` · `commit` · `previous_release` · `change` · `approved_by` · `approver`(팩토리가 붙인 이름표, 없으면 `null`) ·
   `requested_at` · `requested_by`(요청한 작업의 식별자) · `access_findings`(권한 검사의 어긋남 수) · `rehearsal`(`passed` · `failed` · `not_run` · `not_needed`) ·
   `rehearsed`(리허설의 숫자: 걸린 시간 · 멈춘 마이그레이션의 이름 · SQLSTATE · 표마다의 행 수) · `conformance` · `migrations`(돈 수) ·
   `changes`(권한 변화의 문장: 승인 카드에 보이던 것과 같은 `describe` 의 문장과 일정의 문장) · `rollout`. 되돌려진 줄은 여기에 `migrated` 를 더한다.
   되살리기의 줄: `release` · `to`(되살린 시점). 무르기의 줄: `release`. 모든 줄에 `n` · `kind` · `at` 이 있다.
   ❌ 값(비밀 · 행 · 로그의 글 · Postgres 의 문구)을 싣지 않는다. 칸이 타입으로 정해져 있어 들어갈 자리가 없다.
5. **승인한 사람의 이름표.** 승격의 요청 본문에 `approver`(선택, 80자 안, 제어 문자 없음)를 받아 이력에만 둔다. 레이어는 그 뜻을 모른다.
   이메일 대신 팩토리 쪽의 식별자를 넣기를 권한다(이력은 지우지 않는 한 남는다). 요청한 때와 요청한 작업은 승격의 요청을 받을 때 인스턴스의 몸에 적는다.
6. **운영의 로그(`GET …/production/logs?lines=`)는 service key 로만 보고, 놓인 기계가 답한다.** — 제안, 사람의 확인이 남았다(아래 「경계」).
7. **서비스마다의 상태(`GET …/production/services`)는 놓인 기계가 답한다.** `awake` · `asleep` · `building` · `static` · `stopped`(기록에는 운영이 있는데
   이 기계에 떠 있지 않다). 판정은 core 의 `fleet::service_state` 다. **함대의 목록에는 넣지 않았다.** 목록은 어느 기계든 기록만으로 답해야 하고,
   상태는 놓인 기계의 메모리에만 있다. 넣으려면 줄마다 기계를 불러야 하거나(500 줄에 500 번), 깨고 잘 때마다 기록에 적어야 한다(요청이 오갈 때마다 쓰기).
   화면은 인스턴스 하나를 열 때 이 길을 부른다. 다른 기계의 인스턴스면 그 기계로 넘겨져 답한다(새 `Errand::ProductionLive`, `Placed`).
8. **연결된 MCP 클라이언트(`GET …/oauth-grants`)** 는 운영의 `orbital_auth` 의 살아 있는 승인마다 `{ id, client_id, client_name, client_kind, user, scope, created_at, last_token_at }` 이다.
   토큰 · 코드의 값과 해시는 싣지 않는다. `last_token_at` 은 그 승인으로 마지막으로 토큰을 받은(코드를 바꾸거나 refresh 한) 때다. access 토큰을 쓸 때마다
   적지 않는 까닭은 MCP 의 요청마다 인스턴스의 DB 에 쓰기가 생겨서다. access 토큰이 한 시간이라, 쓰는 클라이언트는 한 시간 안에 한 번은 새로 받는다. 인스턴스의 DB 에만 닿으므로 어느 기계든 한다(`Errand::Users`).
9. **조직의 모습(`GET /v1/organization`)** 은 `{ id, name, kind, created_at, recorded, instances, instance_limit }` 이다. 관리 서버의 설정에만 있는 조직은
   `recorded: false` · `name: null` · `kind: "live"` 다. `instance_limit` 은 시험용 조직에만 있다.
10. **기록을 읽지 못한 것을 「없다」로 답하지 않는다.** 목록 · 이력 · 조직의 모습은 기록을 읽지 못하면 빈 목록이나 404 가 아니라 500 이다.
11. 운영자의 열쇠는 이 길들을 열지 못한다(403). 작업의 토큰은 운영의 로그 · 상태를 두드리면 core 가 「service key 로만」이라 답하고(403),
    그 밖의 길은 토큰 쪽에 없다(404). 프리뷰의 로그(`GET …/previews/logs`)는 앞처럼 토큰에 열려 있다.

## 운영의 로그의 경계

「값은 레이어 밖으로 나가지 않는다」와 부딪히는 자리다. 운영의 로그는 앱이 찍은 글이라 고객의 데이터(이메일 · 행의 조각 · 오류에 실린 값)가 섞일 수 있다.
그래도 길을 둔 까닭은 둘이다. ① 운영에서 무엇이 깨졌는지 팩토리가 알 길이 없으면 고치지 못한다. 앞에는 사람이 기계에 들어가 파일을 읽어야 했다.
② 앱은 팩토리가 만든 것이고 그 로그를 찍는 것도 팩토리의 코드다. 팩토리의 서버가 이미 운영을 바꾸는 열쇠(service key)를 쥐고 있어 이 길이 넓히는 범위는
「팩토리가 제 앱이 찍은 글을 본다」에 그친다.

- **켜야 나간다**: 서버가 찍은 로그(`production-<서비스>`)는 레이어의 운영자가 명시해 켠 레이어(`ORBITAL_PRODUCTION_LOGS=service_key`)에서만 내준다.
  기본은 꺼짐이고, 꺼진 레이어의 답은 `server_logs: false` 와 빌드의 로그뿐이다(빌드는 운영의 데이터와 비밀 없이 돈다). 「값은 나가지 않는다」의 기본을 바꾸지 않고,
  이 길을 열지는 사람이 정한다. 개발용 메일함 · 개발용 웹훅과 같은 모양이다.
- **누가**: service key 만. 작업의 토큰(에이전트)은 어떤 능력으로도 닿지 못한다(core 의 `Action::ProductionLogs` 는 「service key 로만」). 운영자의 열쇠도 열지 못한다.
  프리뷰의 로그와 달리 에이전트에게 돌려주지 않는 것이 이 길의 경계다. 팩토리가 이 글을 에이전트에게 넘기는 것은 팩토리의 판단이다(본보기는 넘기지 않는다).
- **얼마나**: 서비스마다 끝의 `lines` 줄(기본 200 · 상한 1000)이고 한 줄은 2000 자에서 자르며 자른 줄의 수를 알린다. 파일의 끝에서 상한만큼만 읽는다.
- **무엇을 가리고**: 레이어의 폴더 경로를 `<레이어>` 로 가린다(프리뷰의 로그와 같다). 앱이 찍은 값은 가리지 못한다. 레이어는 그 글의 뜻을 모른다.
- **어디서**: 놓인 기계가 파일에서 읽는다. 기록(control database)에는 로그를 두지 않는다. 이벤트 · 웹훅 · 이력에도 싣지 않는다.

## HTTP 의 모양

| 길 | 열쇠 | 답 |
|---|---|---|
| `GET /v1/instances?after=&limit=` | service key | `{ instances: [줄], next, has_more }` · 질의가 틀리면 422 |
| `GET /v1/instances/{id}` | service key | 줄 하나 · 다른 조직의 것은 404 |
| `GET /v1/instances/{id}/history?after=&limit=` | service key | `{ history: [이력의 줄], next, has_more }` |
| `GET /v1/instances/{id}/production/logs?lines=` | service key | `{ release, server_logs, logs: [{ name, text, clipped }] }` · 운영이 없으면 409 |
| `GET /v1/instances/{id}/production/services` | service key | `{ release, services: [{ name, kind, state }] }` · 운영이 없으면 409 |
| `GET /v1/instances/{id}/oauth-grants` | service key | `{ grants: [...] }` · `[auth]` 가 없으면 422 · 운영이 없으면 409 |
| `GET /v1/organization` | service key | `{ id, name, kind, created_at, recorded, instances, instance_limit }` |
| `GET /v1/rollouts?after=&limit=` | service key | `{ rollouts: [rollout], next, has_more }` |
| `POST /v1/instances/{id}/promotions` | service key | 본문에 `approver`(선택)를 더했다 |

`next` 는 목록이면 표식의 글(처음부터 비었으면 `null`), 이력이면 번호다. `has_more` 가 참이면 `after=<next>` 로 이어 받는다.

## 테스트 이름(계약)

core 의 예시 테스트:
- `listing.rs`: `쪽의_표식은_만든_때와_식별자로_적고_다시_읽으면_같다` · `쪽의_질의는_표식의_모양이_맞고_limit_이_1에서_500_사이일_때만_받는다`
- `fleet.rs`: `서비스의_상태는_정적이면_static_빌드_중이면_building_깨어_있으면_awake_아니면_asleep_이고_떠_있지_않으면_stopped_이다` ·
  `로그의_줄_수는_1에서_1000_사이만_받고_적지_않으면_200줄이다` · `긴_줄은_상한에서_글자의_경계로_자르고_자른_것을_알린다`
- `history.rs`: `이력의_한_줄은_이름과_숫자와_권한_변화의_문장만_싣는다` · `보관의_상한을_넘은_줄은_오랜_것부터_걷는다` · `승인한_사람의_이름표는_비거나_길거나_제어_문자가_들면_받지_않는다`

core 의 속성 테스트(`props.rs` 의 `listing` · `fleet`):
- `어떤_표식이든_글로_적었다_읽으면_같다`
- `점이_없거나_때가_수가_아니거나_식별자에_없는_글자가_든_표식은_받지_않는다`
- `어떤_줄이든_자른_줄은_상한의_글자_수를_넘지_않고_원래_줄의_머리다`

관리 서버(`tests/dashboard.rs`, 실제 PostgreSQL · 관리 서버 둘 · 실제 HTTP):
- `함대의_목록은_자기_조직의_인스턴스만_만든_차례로_쪽을_나눠_주고_다른_조직의_표식으로는_아무것도_엿보지_못한다`
- `함대의_한_줄은_갈라진_버전과_만든_때와_운영의_release_와_오른_때와_기다리는_요청과_프리뷰를_싣고_다른_조직의_인스턴스는_없는_것과_같다`
- `승격과_되돌려진_승격이_이력에_차례대로_쌓이고_승인과_요청과_검사와_리허설의_숫자와_권한의_변화를_싣되_값은_싣지_않는다`

## 왜

- **화면이 공개 API 위에 선다.** 화면만을 위한 길을 따로 두면 팩토리는 같은 것을 제 화면에 넣지 못하고, 빠진 길이 화면 안에 숨는다.
- **이력은 이벤트와 다르다.** 이벤트는 「일어난 것을 알리는」 것이라 30일 뒤에 걷고 몸이 짧다. 이력은 「인스턴스가 어떻게 지금이 되었나」를 묻는 것이라
  오래 두고, 승인 카드에 보이던 문장까지 함께 둔다. 같은 트랜잭션에 쌓아 일어나지 않은 승격이 이력에 남지 않는다.
- **번호는 인스턴스마다.** 전역 번호(이벤트의 `id`)를 표식으로 내면 틈으로 다른 조직의 일의 양이 보인다. 인스턴스의 줄을 잠근 트랜잭션에서
  `max(n) + 1` 로 지어 겹치지 않는다.
- **상태는 놓인 기계에.** 깨고 자는 일은 요청마다 일어난다. 그때마다 기록에 쓰면 고객의 요청이 control database 의 쓰기를 기다린다.

## 값

- 이 기능 전에 오른 운영은 이력이 없고 `promoted_at` 이 `null` 이다. 앞의 이벤트(30일 안)를 이력으로 옮기지 않았다.
- 함대의 목록은 줄마다 이력의 마지막 승격 줄을 하나 찾는다(색인 `(instance, n)`). 잰 값은 아래 「잰 것」에 있다.
- 운영의 로그는 놓인 기계가 내려가 있으면 502(`machine_unreachable`)다. 서비스의 상태도 같다.
- 이력의 `approver` 는 팩토리가 준 글이다. 사람의 이메일을 넣으면 인스턴스를 지울 때까지 남는다.

## 잰 것

조직의 인스턴스 500개(이력 2500 줄)와 다른 조직의 인스턴스 500개를 넣고 `GET /v1/instances` 를 HTTP 층에 바로 넣어 잰 평균이다(같은 기계의 PostgreSQL,
debug 빌드, `tests/dashboard.rs` 의 `조직의_인스턴스_500개에서_한_쪽을_읽는_시간을_잰다`). 한 쪽 100줄: 첫 쪽 5–7ms · 가운데 쪽 4.5–5.2ms. 한 쪽 500줄: 17–21ms.
질의의 계획은 색인 `instance_listing`(조직, 만든 때, 식별자)으로 101 줄에서 멈춘다(`Index Scan … Limit`). release 빌드나 다른 기계의 클러스터로는 재지 않았다.

## 아직 정하지 않은 것

- 로그를 기록 밖의 저장소로 모으기(기계를 잃으면 로그도 잃는다), 날짜로 고르기, 흘려 보기.
- 대시보드의 사람 로그인과 구성원. 열쇠마다 권한을 좁히기(읽기만 열쇠가 있으면 대시보드는 그것을 쓴다).
- 계량(사용량과 비용).
