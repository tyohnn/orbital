# 기록은 control database 에 두고 인스턴스는 놓인 기계가 돌린다

- 날짜: 2026-11-26
- 상태: 제안(구현하며 정했다. 사람의 확인이 남았다)
- 근거: `crates/orbital-server/src/records.rs` · `migrations/`, `crates/orbital-core/src/placement.rs` · `control.rs`,
  `crates/orbital-server/tests/records.rs` 와 `tests/backup.rs` 의 「기록과 여러 관리 서버」의 테스트 이름. 넘겨 주기(12)는 `src/forward.rs` · `http.rs` 의 `settle`,
  `orbital-router` 의 `Hosts::relay`, `tests/machines.rs` 의 테스트 이름과 core 의 속성 테스트(`tests/props.rs` 의 `placement`)

## 결정

1. **레이어의 기록은 관리 서버의 파일이 아니라 control database 에 둔다.** 관리 연결(`ORBITAL_PG`)의 클러스터 안에 레이어 전용 database 하나
   (`ORBITAL_CONTROL_DB`, 기본 `orbital_control`)를 두고 스키마 `orbital` 에 표를 둔다. 옛 파일(`registry.json` · `settings.json` · `vault.json` ·
   `revoked.json` · `drills.jsonl`)의 구현은 남기지 않는다. 처음 뜰 때 control database 가 비어 있으면 한 트랜잭션으로 옮기고 `*.imported` 로 이름을 바꾼다.
2. **인스턴스의 database 와 다른 database 이고, 인스턴스의 어떤 역할도 붙지 못한다**(`REVOKE ALL ON DATABASE … FROM PUBLIC`).
3. **상태 전체를 한 줄에 두지 않는다.** 따로 고쳐지는 것마다 줄을 둔다(기계 · 앱 · 인스턴스 · 일정 · rollout · 팩토리의 설정 · 금고의 값 · 비밀의 요청 ·
   입력 표 · 닫은 작업 · 훈련). 찾는 열은 타입을 두고 나머지 몸은 jsonb 로 두어 지금의 serde 타입을 살린다. 줄을 고칠 때는 잠그고(`FOR UPDATE`) 읽어 고친 뒤
   한 트랜잭션으로 적는다. 일정은 「다음 때가 그대로일 때만」 옮기는 한 줄의 `UPDATE` 로 잡는다.
4. **마이그레이션은 번호 붙은 SQL 을 실행 파일에 넣고, 뜰 때 적용하지 않은 것만 차례로 적용한다.** advisory lock 으로 한 줄로 서고, 적용한 것의 sha256 이
   바뀌었거나 번호가 빠졌거나 모르는 번호가 적용돼 있으면 뜨지 않는다. 판정은 core 의 `control::pending` 이다.
5. **봉인은 그대로다.** 금고 · 팩토리의 설정은 봉인한 글로만 줄에 둔다. 이번에 **운영의 신원 열쇠와 레이어가 만든 비밀도** 봉인한다(조직 · 인스턴스 · 칸을
   묶는 `orbital/production/v1`). 열쇠는 여전히 기록 밖(`ORBITAL_SEAL_KEY`)이고, 다시 봉인은 이 줄들을 한 트랜잭션으로 바꾼다.
   열쇠가 없는 레이어는 개발용 모양으로 그 둘을 평문으로 적고 뜰 때 알린다. 열쇠를 준 뒤 처음 뜨면 평문이던 칸을 봉인한다.
6. **관리 서버는 뜰 때 자신을 기계(`ORBITAL_MACHINE`)로 적고, 세운 인스턴스는 그 기계에 놓인다.** 그 인스턴스의 코드 저장소 · 빌드 · 프로세스에 닿는 일은
   놓인 기계만 하고, 다른 기계는 아무것도 하지 않고 421 과 놓인 기계의 이름으로 답한다. 어느 일이 어느 쪽인지는 core 의 `placement` 한곳에 적는다.
   다시 뜰 때는 제 기계에 놓인 운영만 되살린다.
7. **값이 바뀐 것은 어느 관리 서버가 받아도 곧 보인다.** 닫은 작업과 입력 표는 요청마다 control database 를 본다. 다른 기계에서 비밀의 값을 바꾸면 놓인 기계에
   `NOTIFY`(기계 · 인스턴스 · 단계의 이름뿐)로 알리고, 그 기계가 서비스를 재운다.
8. **기반 백업과 복구 훈련은 차례(advisory lock)를 잡은 관리 서버 하나만 돌린다.** 일정은 그 인스턴스가 떠 있는 기계만 부른다.
9. **기계의 이름 하나에는 관리 서버가 하나만 뜬다.** 뜰 때 그 이름의 advisory lock 을 쥐고 살아 있는 동안 놓지 않는다. 같은 이름으로 하나 더 띄우면
   앞의 것이 내려가기를 5초 기다려 보고, 그래도 있으면 뜨지 않고 까닭을 알린다(다른 기계라면 `ORBITAL_MACHINE` 을 다르게 준다).
10. **기록을 읽지 못한 것은 「없다」가 아니다.** 인스턴스의 기록을 읽지 못하면 404 가 아니라 500 이고, rollout 의 기록을 읽지 못하면 승격하지 않고,
   금고를 읽지 못하면 서비스를 띄우지 않는다(503). 「없다」로 넘기면 관문을 건너뛰거나 앱이 비밀 없이 뜬다.
11. **토큰의 열쇠는 기록에 두지 않는다.** 관리 서버가 여럿이면 모두 같은 `ORBITAL_TOKEN_KEY` 를 받는다(없으면 지금처럼 `ORBITAL_HOME/token.key`).
12. **다른 기계가 받은 요청은 놓인 기계로 넘겨 준다.** 관리 서버는 뜰 때 다른 관리 서버에서 닿는 자기 주소(`ORBITAL_MACHINE_URL`)와 공용 listener 의 주소
   (`ORBITAL_MACHINE_ROUTER_URL`)를 기록에 적는다(새 마이그레이션 `0002`). 관리 API 는 받은 서버가 토큰과 service key 를 판정하고 아무것도 하지 않은 뒤(`Failure::Misplaced`)
   요청을 그대로 넘기고 답을 그대로 돌려준다. 고객의 요청은 공용 listener 가 세션을 보지 않고 날것 그대로 넘긴다. 넘긴 요청에는 `x-orbital-forwarded-by` 를 붙이고,
   그런 요청은 다시 넘기지 않는다. 판정은 core 의 `placement::route` 한곳이다. 주소를 모르면 421, 닿지 못하면 502(`machine_unreachable`)다.

## 왜

- **파일과 프로세스 안의 자물쇠로는 관리 서버를 한 대만 띄울 수 있다.** 둘이 같은 파일을 읽고 쓰면 서로의 변경을 덮는다. 기록을 DB 에 두면 관리 서버가
  상태를 갖지 않게 되어 여럿을 띄울 바탕이 생긴다. 기록의 정합성은 DB 의 트랜잭션이 지키고, 프로세스 안의 자물쇠는 메모리(떠 있는 것)만 지킨다.
- **인스턴스의 database 와 섞지 않는다.** 인스턴스의 역할은 에이전트가 쓴 코드가 쓰는 연결이다. 같은 database 에 있으면 스키마의 권한 하나를 잘못 줘도
  레이어의 기록(봉인한 글 · 토큰의 장부)에 닿는다. database 를 가르고 접속을 걷으면 그 경계를 Postgres 가 지킨다. 인스턴스를 지우는 일(`DROP DATABASE`)이
  기록을 건드릴 길도 없다.
- **같은 클러스터에 둔다.** 그래서 기반 백업과 WAL 에 기록이 함께 들고, 「그 시점의 DB 와 그 시점의 기록」이 같은 때의 것이 된다. 앞의 모양에서는 기록 묶음을
  기반 백업을 뜨는 순간에 따로 떠서 WAL 로 되살린 시점과 어긋났다.
- **상태 전체를 한 줄에 두지 않는다.** 한 줄이면 모든 일이 그 줄 하나를 잠가 관리 서버를 여럿 두어도 한 줄로 선다. 금고의 값을 넣는 일이 승격을 기다리고,
  일정 하나를 적는 일이 다른 인스턴스의 프리뷰를 기다린다. 따로 고쳐지는 것마다 줄을 두면 잠금이 그 줄만큼만 걸린다.
- **놓인 기계의 규칙이 필요한 까닭은 파일로 남는 것이 있어서다.** 코드 저장소(git) · 빌드 폴더 · 캐시 · 로그 · 개발용 메일함은 그 기계의 디스크에 있고, 떠 있는
  router 와 앱의 프로세스도 그 기계의 것이다. 다른 기계가 같은 인스턴스를 빌드하거나 올리면 두 기계에 다른 운영이 선다. 그래서 그 일은 놓인 기계만 하고,
  기록과 인스턴스의 DB 에만 닿는 일(사용자 · 비밀 · 설정 · 작업)은 어느 기계든 한다. 운영의 주소와 선언은 기록에 두어 다른 기계가 코드 저장소 없이 답한다.
- **같은 이름의 관리 서버 둘을 막는다.** 둘 다 같은 인스턴스를 제 것으로 알아 같은 운영을 둘이 되살리고, 뒤의 것이 앞의 포트를 잡지 못해 기록의 포트를 고쳐 쓰고,
  같은 폴더에 둘이 빌드한다. 기본 이름(`local`)을 그대로 두고 관리 서버를 하나 더 띄우는 것이 가장 하기 쉬운 실수라, 설명에 맡기지 않고 뜨지 못하게 한다.
  프로세스가 죽으면 연결이 닫혀 이름이 바로 풀리므로 내리고 띄우는 데는 걸리지 않는다.
- **421 로 답한다.** 「그 요청을 받을 서버가 아니다」라는 HTTP 의 말 그대로다. 놓인 기계의 주소를 알면 이 답 대신 넘겨 준다(아래 12).
- **넘겨 주는 쪽이 먼저 판정하고 아무것도 하지 않은 뒤에 넘긴다.** 레이어가 「다른 기계에 놓였다」고 답하는 자리는 언제나 아무것도 바꾸기 전이다. 그래서 그 답을 받은 HTTP 층이
  요청을 넘겨도 두 기계가 한 일을 나눠 하지 않는다. 다른 팩토리의 열쇠나 다른 인스턴스의 토큰은 받은 서버가 먼저 거절해 놓인 기계에 닿지도 않는다.
- **넘겨받은 요청은 다시 넘기지 않는다.** 기록의 주소가 잘못 적혔으면(다른 기계를 가리킨다) 넘긴 요청이 기계 사이를 돈다. 한 번만 넘기면 고리가 생길 수 없다.
  이 머리말은 밖의 호출자도 붙일 수 있으므로 아무 권한도 주지 않게 했다. 붙여서 얻는 것은 「넘기지 않음」(421 이나 404)뿐이다.
- **고객의 요청은 날것으로 넘기고 신원은 놓인 기계의 router 만 붙인다.** 넘기는 쪽이 세션을 확인해 신원을 붙이면 신원이 앱에 닿는 길이 둘이 되고, 기계 사이의 머리말을 믿어야 한다.
  그래서 넘기는 쪽도 밖에서 온 `x-orbital-` 를 지우고, 받는 쪽의 router 는 고리 막기 머리말까지 지운 뒤에 자기가 확인한 신원만 싣는다.
- **연결을 맺는 시간만 짧게 둔다.** 프리뷰와 승격은 빌드와 적합성 테스트를 기다려 분 단위로 걸린다. 답을 기다리는 시간을 끊으면 놓인 기계는 일을 마쳤는데 받은 서버는 실패로 답한다.
  그래서 닿지 못한 것(연결을 맺지 못했다: 놓인 기계는 받지 못했다)과 끊긴 것(넘긴 뒤 끊겼다: 놓인 기계가 했는지 모른다)을 다른 답으로 가른다.
- **운영의 신원 열쇠와 레이어가 만든 비밀도 봉인한다.** 기록을 읽을 수 있는 쪽(이제는 control database 의 줄과 그 백업)이 그대로 읽으면, 신원의 서명을 지어
  앱에 아무 사람으로나 들어간다. 금고와 설정을 봉인하는 까닭과 같다.

## 값

- **관리 서버가 control database 에 닿지 못하면 아무 일도 못 한다.** 운영의 router 와 앱은 떠 있는 동안 그대로 돌지만, 닫은 작업 · 입력 표 · 금고의 값(깨울 때 읽는다)이
  DB 를 본다. 기록이 운영 클러스터 안에 있으므로 클러스터가 내려가면 어차피 앱도 내려간다.
- 요청마다 닫은 작업을 DB 에서 본다(한 번의 조회). 느려지면 짧게 기억한다.
- 고객의 요청을 넘길 곳은 인스턴스마다 5초 동안 기억한다. 그사이 인스턴스가 지워졌거나 기계의 주소가 바뀌면 그만큼 늦게 따라간다(지워진 인스턴스의 요청은 놓인 기계가 404 로 답한다).
  기억에 없는 곳은 한 번에 하나씩만 찾아, 모르는 하위 도메인을 쏟아붓는 요청이 기록에 붙는 연결을 늘리지 못한다.
- 열쇠가 없는 개발용 레이어는 신원 열쇠를 평문으로 적는다. 운영의 레이어는 열쇠를 줘야 한다(뜰 때 한 줄로 알린다). 더 안전한 모양(열쇠 없이는 운영에 올리지 않기)은
  지금의 테스트 대부분이 열쇠 없이 운영에 올려 크게 깨지므로 하지 않았다.
- **옛 열쇠 없이 봉인의 열쇠를 바꾸면 운영의 신원 열쇠가 풀리지 않는다.** 그 인스턴스는 승격과 되살리기가 409 로 멈추고(운영을 건드리기 전에 본다), 다시 뜰 때
  되살리지 못한다. 옛 열쇠를 함께 주고 띄우는 것이 절차다([런북](../runbook/봉인의-열쇠-바꾸기.md)).
- **신원 열쇠는 인스턴스의 database 에도 있다.** 신원의 검증 함수가 쓰려고 `orbital.instance.signing_key`(레이어의 스키마, 인스턴스의 역할은 열쇠를 읽지 못하고 함수만 부른다)에
  평문 bytes 로 두며, 그 database 와 함께 기반 백업에 든다. control database 의 봉인은 기록의 줄과 그 백업에서 바로 읽히는 것을 막을 뿐이고, 클러스터의 백업을
  가진 쪽은 인스턴스의 database 에서 읽을 수 있다. 백업을 기록과 같은 무게로 지킨다.
- 다른 기계에서 비밀을 바꾼 알림은 이름만 실어 그 단계의 서버 서비스를 모두 재운다(그 비밀을 선언했는지 보지 않는다). 다음 요청에 깬다.
- **알림을 듣던 연결이 끊기면 다시 붙고, 다시 붙을 때 그 기계에 떠 있는 서버 서비스를 모두 재운다.** 끊긴 사이의 알림은 다시 오지 않아서다.
  DB 가 한 번 흔들리면 그 기계의 앱이 다음 요청에 한 번씩 새로 깬다.
- **한 기계의 관리 서버를 겹쳐서 바꿔 띄우지 못한다**(새것을 띄우고 옛것을 내리기). 내리고 띄운다. 운영의 router 가 관리 서버의 프로세스 안에 있어
  지금도 그 사이에 운영이 끊기며, 이것은 router 를 관리 서버에서 떼어야 풀린다.
- 기계의 이름을 쥔 연결이 끊기면(DB 가 다시 떴다) 그 관리 서버는 이름을 쥐지 않은 채로 돈다. 그 사이에 같은 이름으로 하나 더 띄우면 막지 못한다.

## 아직 정하지 않은 것

- 기계 사이의 넘겨 주기를 서로 확인하기(mTLS · 서명). 지금은 관리 서버끼리만 닿는 망에 둔다고 보고, 권한은 토큰과 service key 가 정한다.
- 기계가 죽었는지 알고 그 인스턴스를 다른 기계가 이어 받기(코드 저장소를 나눠 써야 한다).
- DB 클러스터 여럿. control database 는 어느 클러스터에 두나(지금은 관리 연결의 클러스터 하나).
- service key 를 조직마다 내고 거두는 길을 control database 에 둘지.
