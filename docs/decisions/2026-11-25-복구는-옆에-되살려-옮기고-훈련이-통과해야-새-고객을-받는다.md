# 복구는 옆에 되살려 옮기고 훈련이 통과해야 새 고객을 받는다

- 날짜: 2026-11-25
- 상태: 정함(기획안 11절의 8번 「백업과 복구 훈련」)
- 근거: `crates/orbital-server/tests/backup.rs` · `crates/orbital-backup/tests/backup.rs` · `crates/orbital-core/src/backup.rs` 의 테스트 이름

## 결정

끝 기준은 **복구 훈련이 사람 손 없이 통과한다**이다. 실제 고객의 데이터는 이 번호가 끝난 뒤에 받는다.

| 무엇 | 어떻게 |
|---|---|
| 도구 | PostgreSQL 의 도구만 쓴다. 기반 백업(`pg_basebackup`), WAL 보관(`archive_command` 가 보관 폴더에 복사), 시점 복구(`restore_command` + `recovery_target_time`), database 하나 옮기기(`pg_dump` · `pg_restore`) |
| 두는 곳 | 갈아 끼우는 자리(`Store`) 하나. 구현은 이 기계의 폴더(`LocalStore`, `ORBITAL_BACKUP_DIR`) 하나다 |
| 백업 한 벌 | 기반 백업 + 그 뒤의 WAL + 레이어의 기록 묶음(`registry.json` · `settings.json` · `vault.json` · `sources` · `apps`). 금고와 설정은 봉인한 글 그대로 묶인다 |
| 클러스터 전체의 시점 복구 | 정한 시각으로 **옆에 따로 세운 클러스터**에만 되살린다. 그 클러스터는 Postgres 의 사용자만 들어가는 폴더의 유닉스 소켓에서만 듣고 TCP 를 듣지 않으며 WAL 을 보관하지 않는다 |
| 인스턴스 하나 되살리기 | 옆에 그 시점의 클러스터를 세우고, 그 인스턴스의 database 를 운영 클러스터의 옆 이름에 **레이어의 계획으로 다시 세워** 바꿔 넣는다. 앱의 정의와 행은 관리 권한으로 되풀이하지 않는다. service key 로만(`POST /v1/instances/{id}/restore` `{at}`) |
| 복구 훈련 | 표식 → 시점 T → 표식 → WAL 넘기기 → 옆에 T 로 되살리기 → 확인 → 인스턴스 하나 옮겨 보기 → 걷기 → 기록. 확인이 하나라도 어긋나면 실패다 |
| 주기 | `orbitald` 가 정한 주기로 기반 백업(`ORBITAL_BACKUP_EVERY`, 하루)과 훈련(`ORBITAL_DRILL_EVERY`, 7일)을 돌린다. 한 번만 돌리는 `orbitald drill` 도 있다 |
| 새 고객의 관문 | 마지막으로 통과한 훈련이 여드레를 넘겼거나 한 번도 통과하지 않았으면 「낡았다」. 켠 레이어(`ORBITAL_REQUIRE_DRILL=1`)는 그동안 새 인스턴스만 받지 않는다 |
| 보관 | 14일(`ORBITAL_BACKUP_KEEP_DAYS`)이 지난 기반 백업과 거기에만 딸린 WAL 을 지운다. 마지막 기반 백업은 언제나 남긴다 |
| 판정 | core 의 `backup` 이 한다. 시점을 덮는 기반 백업 고르기, 되살릴 수 있는 시점인지, 훈련의 판정, 낡았는지, 지울 것 고르기 |

## 왜

- **운영 클러스터를 덮어쓰지 않는 까닭: 클러스터는 모든 인스턴스가 함께 쓴다.** Postgres 의 시점 복구는 클러스터 단위다. 운영 자리에서 되살리면
  인스턴스 하나를 되돌리려다 다른 고객의 데이터까지 그 시점으로 돌아간다. 되살리는 도중에 깨지면 되돌아갈 자리도 없다. 옆에 세우면 운영은 그대로이고,
  무엇이든 확인한 뒤에 옮길 수 있다. 덮어쓰는 길을 만들지 않았으니 실수로 부를 수도 없다.
- **옆의 클러스터는 밖에서 닿지 않게 한다.** 그 시점의 모든 인스턴스의 데이터를 담은 사본이다. TCP 를 듣지 않고, 소켓의 폴더를 Postgres 의 사용자만 들어가게 두며,
  운영의 보관 폴더에 WAL 을 섞지 않게 보관을 끈다. 쓰고 나면 프로세스와 폴더를 걷는다. 앞에서 깨진 채로 남은 것은 다음에 레이어가 뜰 때 걷는다(세운 프로세스가 끝난 것만).
- **인스턴스 하나를 옮기는 까닭: 고객의 「어제로 돌려 달라」는 그 고객의 일이다.** database 는 인스턴스마다 하나이고 역할은 클러스터의 것이라,
  database 하나만 옮기면 다른 고객은 그대로다. 순서는 이렇다. 옆 이름(`<인스턴스>_rs_…`)에 그 database 를 다시 세우고 권한 검사를 지난다 →
  서버를 재운다 → 지금의 운영 DB 를 되돌릴 지점으로 남긴다(되살리기 자체를 무를 수 있게) → 이름을 바꿔 넣는다 → 다음 요청이 되살린 DB 로 깬다.
  세우고 검사하는 동안 운영은 그대로 돌고, 검사에 걸리면 운영은 건드리지 않는다. 사용자와 세션(`orbital_auth`)도 그 시점의 것이 된다. 코드와 금고는 되살리지 않는다.
- **덤프를 관리 권한으로 풀지 않는 까닭: 앱의 정의는 에이전트가 쓴 코드다.** `pg_restore` 는 접속한 역할로 덤프의 SQL 을 되풀이한다. 앱이 정의한 함수가
  CHECK 제약 · 인덱스의 식 · 생성 열에 걸려 있으면 행을 넣는 동안 그 역할로 돈다. 관리 역할(슈퍼유저)로 풀면 그 함수가 `COPY … TO PROGRAM` 으로
  기계의 명령까지 돌릴 수 있고, 훈련이 매주 같은 길을 쓰므로 사람이 아무것도 하지 않아도 그렇게 된다. 그래서 다시 세우는 일을 셋으로 나눈다.
  레이어의 것(database · 스키마 · `orbital` · `orbital_auth`)은 새 인스턴스를 세울 때처럼 레이어의 계획으로 세운다. 앱의 스키마는 그 인스턴스의
  마이그레이션 역할로 붙어 소유자가 되어(마이그레이션이 도는 것과 같은 권한) 정의와 행을 풀고, 덤프의 소유와 권한은 되풀이하지 않는다
  (`--no-owner --no-acl`, 권한은 권한 표대로 다시 세운다). `orbital_auth` 는 행만 인증 역할로 넣는다. 덤프로는 외래 키의 차례대로 넣지 못해
  (그 차례를 무시하는 `--disable-triggers` 는 관리 권한에만 있다) 옆의 클러스터에서 표마다 `COPY` 로 옮긴다. 관리 주소는 명령줄에 싣지 않고
  환경 변수로 건네고, 운영의 행이 평문으로 담긴 덤프는 주인만 읽게 만들어 어떻게 끝나든 지운다.
- **훈련의 실패가 새 인스턴스만 막는 까닭: 백업이 깨졌을 때 할 일은 운영을 멈추는 것이 아니다.** 이미 선 인스턴스의 배포까지 막으면 훈련 하나의 실패가
  모든 고객의 버그 수정과 보안 업데이트를 멈춘다. 그때 잃는 것이 백업이 낡아 잃을 수 있는 것보다 크다. 새 고객은 다르다. 되살릴 수 있는지 모르는 곳에
  처음 데이터를 맡기지 않는다. 여드레는 매주 도는 훈련이 한 번 늦어도 하루의 틈이 있게 잡았다.
- **열쇠를 백업에 넣지 않는 까닭: 백업을 가진 쪽이 금고를 열면 안 된다.** 봉인의 열쇠 · service key 는 처음부터 기록 밖(환경 변수)에 있고, 토큰의 열쇠
  (`token.key`)는 묶음의 이름표(`RECORDS`)에 없다. 백업이 새어도 금고와 팩토리의 설정은 봉인한 글이라 열리지 않는다. 대신 열쇠를 잃으면 백업으로 되찾지 못한다.
  열쇠는 운영자가 따로 지킨다(런북).
- **지문에는 이름과 숫자만 싣는다.** 훈련의 기록은 팩토리에게 보이는 숫자의 근거이고 오래 남는다. 스키마의 모양은 해시 하나, 표는 행의 수로만 적는다.
  권한은 실제로 갖는 것(기본값을 풀어 쓴 것)으로 견준다. 기본값과 같은 권한을 풀어 적은 표는 옮기면 `NULL` 로 돌아오는데, 그것을 다르다고 보면 훈련이 거짓으로 실패한다.
- **시점의 시각은 DB 의 시계다.** 시점 복구가 견주는 것이 commit 의 시각이라, 기반 백업의 시각과 보관의 표시도 DB 의 시계로 잰다. 「이 시각까지는 보관됐다」는
  표시는 commit 하나를 적고 WAL 을 넘긴 뒤 그 조각이 보관 폴더에 닿은 것을 보고서야 적는다. 그 시각 뒤에 commit 이 하나 있어야 Postgres 가 그 시점에 닿았음을 안다.

## 알려진 한계

- **pgBackRest 가 아니라 Postgres 의 도구다.** 기획안은 운영 기계에서 pgBackRest 를 쓴다고 적었다. 압축 · 증분 백업 · 병렬 · 보관의 검증이 없다.
  기반 백업은 매번 클러스터 전체를 뜬다.
- **백업이 같은 기계의 폴더에 있다.** 기계를 잃으면 백업도 잃는다. 다른 곳(오브젝트 저장소, 다른 기계)에 두는 것은 `Store` 를 갈아 끼울 때 한다.
- **기록까지 과거로 되돌려 운영을 다시 세우는 재해 복구의 전체는 없다.** 묶음이 풀리고 읽히는 것까지만 훈련이 잰다. 클러스터 전체를 되살린 뒤 레이어를 다시 세우는
  절차는 런북에 사람의 손으로 적었다.
- **대기 서버가 없다.** 운영 클러스터의 기계가 죽으면 기반 백업과 WAL 로 새로 세우는 동안 모든 인스턴스가 내려간다. 잃을 수 있는 구간은 마지막으로 보관된 WAL 까지다.
  보관은 WAL 조각이 찰 때 일어나므로, 쓰기가 적은 레이어에서는 그 구간이 길어질 수 있다(`archive_timeout` 은 운영자가 정한다). 훈련의 기록이 그 구간을 숫자로 남긴다.
- **되살리는 동안 그 인스턴스가 잠깐 내려간다.** 옆 이름에 다시 세우는 동안은 운영이 그대로 돌고, 되돌릴 지점을 뜨고 이름을 바꿔 넣는 동안 서버가 자고 DB 의 문이 닫힌다.
  큰 database 는 다시 세우는 데 `pg_dump` · `pg_restore` 만큼 걸린다. 그 긴 부분은 레이어의 자물쇠 밖(따로 연 관리 연결)에서 돌고 바꿔 넣는 순간만 쥐어,
  다른 인스턴스의 일은 기다리지 않는다(2026-11-26). 같은 인스턴스는 한 번에 하나만 되살리고, 그사이 운영이 바뀌었으면 바꿔 넣지 않는다.
- **앱의 정의는 마이그레이션의 권한으로 다시 돈다.** 관리 권한으로는 돌지 않지만, 앱이 정의한 함수가 행을 넣는 동안 소유자의 권한으로 다시 돈다.
  그 함수에 부작용(다른 표에 쓰기)이 있으면 되살린 DB 에 그 부작용이 한 번 더 남는다. 앱의 마이그레이션이 만들 수 없는 것(확장 · 다른 스키마의 것)은
  되살아나지 않고, `FORCE ROW LEVEL SECURITY` 를 건 표는 소유자도 정책에 걸려 행을 넣지 못할 수 있다(추측, 재지 않았다).
- **데이터베이스를 레이어의 지금 계획으로 다시 세운다.** 그 시점의 DB 가 앞 판의 레이어로 세운 것이면(검증 함수 · `orbital_auth` 의 모양이 다르면)
  다시 세운 것의 모양이 그 시점과 다르고, 훈련은 그것을 지문의 어긋남으로 알린다. `orbital_auth` 는 다시 세운 표의 열 이름으로 옮기므로 그 시점에 없던 열이 있으면 옮기지 못한다.
- **되살린 DB 와 지금의 코드가 어긋날 수 있다.** 그 시점 뒤에 돈 마이그레이션은 되살아난 DB 에 없다. 권한 검사는 지나도 앱이 없는 표를 부를 수 있다.
  어느 release 로 되살릴지 고르는 길은 아직 없다.
- **훈련의 지문은 T 앞뒤로 뜬 두 지문이 같을 때 그 시점의 모습으로 본다.** 그 사이 몇 밀리초에 commit 이 보이기 전이던 쓰기가 있으면 거짓으로 실패할 수 있다(추측, 재지 않았다).
- 되살리기를 무르는 길(`POST …/restore/undo`)은 한 번뿐이다. 되돌릴 지점이 하나라서 무른 뒤에는 다시 무르지 못하고, 그 사이 승격이 있었으면 지점이
  그 승격의 것으로 바뀌어 무르지 못한다.
