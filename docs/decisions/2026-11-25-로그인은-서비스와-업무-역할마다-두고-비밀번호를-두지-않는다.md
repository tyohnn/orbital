# 로그인은 서비스와 업무 역할마다 두고 비밀번호를 두지 않는다

- 날짜: 2026-11-25
- 상태: 제안(구현하며 정했다. 사람의 확인이 남았다)
- 근거: [Orbital 기획안](https://claude.ai/artifact/R9fEaCArNwVN1aWt9WPdzY) 5절, `crates/orbital-core/src/plan.rs` 의 테스트 이름

## 결정

인스턴스의 Postgres 역할은 세 갈래로 세운다.

| 역할 | 로그인 | 하는 일 |
|---|---|---|
| 소유자 | 못 함 | 모든 표의 주인 |
| 마이그레이션 | 레이어가 배포하는 동안만 | 소유자가 되어 스키마를 바꾼다 |
| 업무 역할의 묶음 | 못 함 | 권한 표의 권한을 갖는다 |
| 로그인 | (서비스, 업무 역할)마다 하나 | 자기 묶음의 권한만 물려받는다. 다른 역할로 바꿔 타지 못한다(`SET FALSE`) |

역할에는 비밀번호를 주지 않는다. DB 는 proxy 만 닿는 자리에서만 연결을 받고, 어느 로그인으로 들어갈지는 proxy 가 정한다.
database 의 주인은 레이어의 관리 역할이고, 인스턴스의 소유자는 선언한 스키마만 갖는다.

## 왜

- **연결 하나가 `SET ROLE` 로 역할을 갈아타는 방식을 쓰지 않는다.** 그 방식에서는 SQL 주입 한 번으로 직원의 요청이 급여 관리자가 된다.
  PostgreSQL 16 부터 멤버십마다 `SET` 을 끌 수 있어서, 로그인이 자기 묶음의 권한은 쓰되 그 역할이 되지는 못하게 한다.
- **서비스마다 로그인을 나눈다.** 모노레포의 앱마다 Postgres 사용자를 나누는 일을 사람이 손으로 하던 것을 선언의 `roles` 한 줄로 옮긴다.
  선언에 적지 않은 역할의 로그인은 아예 만들지 않으므로, 화면 서비스가 급여 관리자로 들어갈 길이 DB 에 없다.
- **비밀번호가 없으면 새어 나갈 것도 없다.** 접속 문자열을 환경 변수에 넣는 일, 복구 뒤에 다시 넣는 일이 사라진다.
- **database 를 인스턴스가 소유하지 않는다.** 소유하면 마이그레이션이 선언에 없는 스키마를 만들 수 있다.

## 값

- 역할의 수가 (서비스 × 업무 역할)만큼 는다. 역할 이름은 클러스터 전체가 함께 보므로 식별자를 머리에 달고, 식별자에는 뜻을 담지 않는다.
- 연결의 수가 는다. proxy 가 연결을 모아 쓰는 일은 아직 없다.

## 아직 정하지 않은 것

- proxy 와 DB 사이를 무엇으로 믿을지. 지금은 닿는 자리를 막는 것(소켓 · 주소)에 기댄다. 인증서로 올릴지는 운영의 모양이 서면 정한다.
