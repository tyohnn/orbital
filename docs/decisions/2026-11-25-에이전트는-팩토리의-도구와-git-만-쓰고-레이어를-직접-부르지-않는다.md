# 에이전트는 팩토리의 도구와 git 만 쓰고 레이어를 직접 부르지 않는다

- 날짜: 2026-11-25
- 상태: 제안(구현하며 정했다. 사람의 확인이 남았다)
- 근거: `crates/orbital-server/tests/git.rs`, `crates/orbital-core/src/git.rs`, `sdk/typescript/test/work.test.ts` · `lap.test.ts`,
  `examples/factory-todo/test/factory.test.ts` 의 테스트 이름
- 바꾼 것: [코드는 묶음으로 주고받고 프리뷰는 따로 선 인스턴스다](2026-11-25-코드는-묶음으로-주고받고-프리뷰는-따로-선-인스턴스다.md)의 1번(묶음만 오간다)

## 결정

1. **에이전트는 레이어의 주소도 토큰도 받지 않는다.** 팩토리의 플러그인에 든 MCP 도구(팩토리의 서버에 닿는다)와 평범한 `git` 만 쓴다.
   프리뷰 · 로그 · 씨앗 사용자로 들어가기 · 리허설 · 승격 요청은 팩토리의 도구가 하고, 팩토리의 서버가 SDK 로 레이어를 부른다.
   `orbital` CLI 는 선언 파일을 검사하는 명령(`check` · `plan` · `diff`)만 남기고 에이전트에게 주지 않는다.
2. **코드는 도구가 아니라 git 으로 오간다.** 레이어는 인스턴스마다 git 의 smart HTTP 를 받는다(`…/git/info/refs`, `…/git/git-upload-pack`,
   `…/git/git-receive-pack`). 에이전트의 git 은 팩토리의 주소(`<팩토리>/git/<작업>`)에 붙고, 팩토리의 서버가 그 요청을 레이어로 이어 준다.
3. **작업(work)은 레이어가 낸 토큰을 SDK 가 감싼 것이다.** 팩토리의 서버가 service key 로 작업을 열면, 그 작업의 함수와 git 을 이어 주는 함수
   (`git.relay`)는 모두 작업의 토큰으로만 부른다. service key 는 싣지 않는다.
4. **git 의 자격은 팩토리가 낸다.** 그 고객의 그 인스턴스 하나에서만, 레이어의 작업이 끝날 때(두 시간)까지만, 팩토리의 git 의 길에서만 통한다.
   MCP 의 토큰과 섞이지 않는다.
5. **올리는 두 길은 한 자리를 지난다.** git 으로 올리든 묶음으로 올리든 받는 ref(`main` 하나)와 앞으로만 가기는 core 의 `git::judge_push` 가
   판정하고, 객체는 격리한 폴더에 받아 검사한 뒤에야 저장소로 옮긴다(`SourceStore::ingest`). 크기 한도와 「저장소의 훅을 돌리지 않는다」도 같다.
   받기에는 `main` 과 열린 rollout 의 `update` 만 보이고, 레이어가 안에서 쓰는 ref(`refs/orbital/**`)는 보이지 않는다.
6. **레이어의 오류 문구는 어느 도구로 하는지 말하지 않는다.** 무엇을 해야 하는지만 말하고(「프리뷰를 먼저 세워 주세요」), 어느 도구 · 명령으로
   하는지는 팩토리의 스킬이 말한다. service key 로만 하는 일의 안내는 팩토리의 서버를 만드는 사람이 읽으므로 HTTP 의 길을 적어도 된다.

## 왜

- **팩토리를 건너뛰는 길이었다.** 에이전트가 레이어의 토큰으로 레이어를 바로 부르면, 팩토리는 그 호출을 세지도 막지도 못한다. 요금 · 한도 ·
  고객마다의 정책을 팩토리가 걸 자리가 없다. 레이어의 주소와 이름이 팩토리의 고객 쪽(에이전트의 sandbox, 대화, 스킬)에 그대로 드러난다.
  Orbital 은 팩토리 뒤에 숨는 기계여야 한다.
- **코드만은 도구가 아니라 git 이다.** MCP 도구의 인자는 모델이 글로 써서 보낸다. 코드를 도구로 올리면 저장소가 모델의 문맥을 지나고, 파일이 많거나
  이진 파일이 있으면 그 자체로 깨진다. git 은 에이전트의 sandbox 에서 바로 오가고 모델은 결과만 읽는다.
- **이어 주는 코드는 작업의 토큰을 쓴다.** git 을 이어 주는 코드는 밖에서 온 요청을 그대로 흘리는 자리라 버그가 나기 쉽다. 그 코드가 service key 를
  쓰면 버그 하나가 운영을 바꾸는 길이 된다. 작업의 토큰에는 운영을 바꾸는 능력이 아예 없어서, 이어 주는 코드가 무엇을 잘못 넘겨도 레이어가 막는다.
- **판정을 한 자리에 둔다.** 길이 둘이면 규칙이 갈라지기 쉽다. 묶음의 길은 SDK 와 레이어의 테스트가 아직 쓰므로 남기되, 같은 함수를 지나게 했다.
  그 과정에서 묶음의 길도 저장소에 놓인 `reference-transaction` 훅을 돌리던 것을 고쳤다(모든 git 명령에 `core.hooksPath=/dev/null`).
- **git 의 자격을 팩토리가 낸다.** 레이어의 토큰을 git 의 자격으로 건네면 다시 레이어의 토큰이 에이전트에게 간다. 팩토리가 자기 자격을 내고
  자기 길에서 확인하면, 누가 언제 코드를 받고 올렸는지를 팩토리가 보고 막을 수 있다.

## 값

- **코드가 팩토리의 서버를 거쳐 간다.** 팩토리는 그 통로를 운영해야 한다(대역폭, 시간 제한, 큰 저장소). 팩토리 쪽(`git.relay`)은 본문을 스트림으로 넘겨
  모아 두지 않지만, **레이어는 요청 본문을 상한(`Options::upload_limit`, 기본 64MiB)까지 메모리에 모으고, 받기의 답(pack)도 다 만든 뒤 보낸다.**
  한 번에 올리는 것은 상한이 묶지만, 받기(clone)의 답은 저장소 전체만큼 커질 수 있다. 파일 3194 개 · 줄어들지 않는 이력 약 21MiB 의 저장소로 잰 것은
  올리기 1.7 ~ 1.8초 · 받기 0.7 ~ 1.1초, 레이어 프로세스의 메모리 꼭대기는 그 크기만큼(약 25MiB) 늘었다. 상한을 넘는 올리기는 413 이고 git 은
  `RPC failed; HTTP 413` 만 보인다(본문의 글은 보이지 않는다. 스킬이 그 뜻을 적는다).
- **팩토리의 서버가 다시 뜨면 열린 작업과 git 의 자격이 사라진다.** 본보기는 자격을 디스크에 두지 않고 메모리에만 둔다. 자격이 통하지 않으면 팩토리의
  git 의 길은 403 과 글(`text/plain`)로 답한다. git 은 그 글을 `remote: …` 로 보인다(401 이면 글을 보이지 않고 자격을 다시 묻다 멈춘다). 글은
  「`workspace_open` 을 다시 불러 새 원격과 자격을 받고 `git remote set-url origin <새 원격>` 으로 바꾼 뒤 다시 하라」만 말하고 레이어를 드러내지 않는다.
  자격을 내지 않은 첫 요청에는 401 과 `WWW-Authenticate: Basic` 으로 답해 자격 도우미가 돈다.
- **레이어는 smart HTTP 의 v0 만 말한다.** 프로토콜 v2 · shallow · push-option · 지우기(`delete-refs`) · side-band 를 알리지 않는다. 그래서 git 은
  올리기의 결과를 진행 표시 없이 받고, 얕은 저장소에서 올리기는 받지 않는다.
- **받기를 줄인(gzip) 요청은 `gzip` 실행 파일로 푼다.** 레이어가 도는 자리에 `gzip` 이 있어야 한다. 풀린 크기도 상한 안이어야 하고, 넘으면 그 자리에서
  풀기를 멈춘다(이어 붙인 조각 512 개로 0.5MiB 가 512MiB 로 풀리는 요청에도 메모리를 상한만큼만 쓴다). 실제 `git` 이 have 가 많을 때 줄여 보내는 요청으로 잰다.

## 아직 정하지 않은 것

- 팩토리의 도메인으로 레이어에 바로 붙는 길. 팩토리가 통로를 운영하지 않도록 `git.<팩토리>` 같은 이름을 레이어에 바로 붙이고, 자격은 여전히
  팩토리가 내는 모양을 더할 수 있다.
- 작업을 만료 전에 거두기와, 작업에 누가 무엇을 했는지 적기(`actor`).
- git 의 자격을 팩토리의 파일이나 DB 에 두어 팩토리가 다시 떠도 이어지게 하는 일. 본보기는 두지 않기로 했다(자격이 디스크에 남지 않는 쪽을 골랐고,
  다시 여는 절차가 짧다). 실제 팩토리는 연결(OAuth)의 토큰도 다시 떠서 사라지면 플랫폼이 다시 연결해야 하므로 그쪽을 먼저 정한다.
- 받기의 답(pack)을 다 만들지 않고 흘려 보내기. HTTP 층의 답이 바이트 덩어리라 길 하나만 흘리도록 바꿔야 한다.
