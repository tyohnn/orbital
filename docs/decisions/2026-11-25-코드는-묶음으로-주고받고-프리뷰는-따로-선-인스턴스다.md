# 코드는 묶음으로 주고받고 프리뷰는 따로 선 인스턴스다

- 날짜: 2026-11-25
- 상태: 제안(구현하며 정했다. 사람의 확인이 남았다)
- 근거: [Orbital 기획안](https://claude.ai/artifact/R9fEaCArNwVN1aWt9WPdzY) 6절 · 9절, `crates/orbital-server/tests/lap.rs` 의 테스트 이름

## 결정

1. **코드는 묶음(git bundle)으로 주고받는다.** 레이어는 인스턴스마다 git 이력을 갖지만 git 서버를 띄우지 않는다. 에이전트는 묶음을 받아
   `git clone` 하고, 고친 뒤 `main` 을 묶음으로 올린다. 레이어는 `main` 의 이력을 잇는 묶음만 받는다.
2. **release 의 식별자는 인스턴스와 commit 에서 짓는다.** commit 이 나무 전체를 정하므로 파일이 하나라도 바뀌면 식별자가 달라진다.
   승인은 호출에 release 의 식별자를 적는 것으로 묶인다. 승인한 뒤 commit 이 더해지면 그것은 다른 release 다.
3. **프리뷰는 따로 선 인스턴스다.** 프리뷰마다 뜻 없는 식별자를 새로 지어 database 와 역할을 따로 세운다. 운영의 역할과 database 를 나눠 쓰지 않는다.
   마이그레이션을 처음부터 돌리고 씨앗 데이터를 넣는다. 운영의 행은 들어가지 않고, 운영의 서명 열쇠와 비밀도 이어지지 않는다.
4. **에이전트가 쓴 것은 관리 권한으로 돌리지 않는다.** 마이그레이션은 리허설에서도 운영에서도 마이그레이션 역할로 따로 접속해 돌린다.
5. **운영을 바꾸는 길은 service key 쪽에만 있다.** 토큰으로 그 길을 두드리면 core 가 거절한다(`ServiceKeyOnly`).
6. **레이어의 기록은 지금 파일 하나다.** 어느 인스턴스가 어느 조직의 것인지, release 마다 검사가 어떻게 끝났는지, 운영에 무엇이 올라 있는지를 JSON 파일에 적는다.

## 왜

- **묶음.** git 의 전송 규격을 HTTP 로 받으려면 git 서버와 그 인증을 따로 붙여야 한다. 묶음은 파일 하나라 토큰을 확인하는 같은 API 로 오가고,
  받은 쪽에서는 평소의 git 그대로다. 밖에서 온 객체는 받으면서 검사한다.
- **따로 선 프리뷰.** 프리뷰의 코드는 아직 승인받지 않았다. 운영과 역할을 나눠 쓰면 proxy 한 겹에만 기대게 된다. 따로 세우면 DB 가 한 번 더 막는다.
- **관리 권한.** 처음에는 리허설을 관리 연결에서 역할만 소유자로 바꿔 돌렸다. 그러면 마이그레이션이 `RESET ROLE` 한 줄로 관리 권한을 되찾는다.
  실제 DB 로 그 시도를 재는 테스트를 세우고 고쳤다.
- **기록.** 서버가 하나일 때는 파일로 충분하고, 표의 모양을 굳히기 전에 한 바퀴를 먼저 돌려 보려는 것이다.

## 값

- 묶음은 통째로 오간다. 저장소가 커지면 느려진다(지금 상한 64MB). 그때는 바뀐 부분만 담은 묶음으로 바꾼다.
- 리허설과 승격 때 운영 DB 의 문이 잠깐 닫힌다. 복제는 원본에 다른 연결이 없어야 해서다. proxy 가 요청을 붙잡게 되면 사라진다.
- 승격하는 동안 운영의 서버가 내려갔다 뜬다. 새 서버를 먼저 띄우고 요청을 돌리는 일은 router 가 생기면 한다.
- 레이어의 기록이 파일이라 서버를 둘 이상 띄울 수 없다.

## 아직 정하지 않은 것

- 레이어의 기록을 DB 의 표로 옮길 때의 스키마.
- 서버가 재시작됐을 때 운영의 서버를 다시 띄우는 일. 지금은 띄운 프로세스를 서버가 기억만 한다.
- 마이그레이션이 더하기만 하는지 가리는 방법. 지금은 마이그레이션이 하나라도 돌았으면 「되돌리면 데이터를 잃는다」로 본다.
