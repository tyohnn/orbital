# 할 일 앱 고치기

사용자의 할 일 앱은 사용자마다 따로 선 사본입니다. 코드는 평범한 `git` 으로 받고 올리고, 프리뷰와 승격 요청은 이 앱의 도구로 합니다.
따로 설치할 명령은 없습니다. 운영에 올리는 것은 사용자가 승인 카드에서 합니다. 에이전트는 승격을 **요청**하고 카드를 **보이기**까지만 합니다.

## 차례

1. **작업 열기.** `workspace_open` 도구를 부릅니다. 답에 git 원격(`remote`)과 그 원격에만 쓰는 자격(`credential`), 끝나는 때(`expires_at`, Unix 초)가 옵니다.
   자격은 두 시간 뒤 끝납니다. git 이 `401` 이나 `Authentication failed` 로 멈추면 `workspace_open` 을 다시 불러 새 자격을 받습니다.
   같은 사용자에게는 언제나 같은 앱의 사본이 옵니다.
2. **받기.** 자격은 원격의 주소에 넣지 않습니다. 명령 한 번에만 머리말로 건넵니다.
   ```sh
   git -c http.extraHeader="Authorization: Bearer $CREDENTIAL" clone "$REMOTE" todo && cd todo
   ```
   여러 번 쓸 거라면 git 의 자격 도우미에 넣어도 됩니다(사용자 이름은 아무것이나, 비밀번호 자리에 자격).
   이미 받은 폴더면 같은 머리말로 `git pull --no-rebase origin main` 해 최신을 합칩니다.
3. **고치기.** 요청대로 고칩니다. 앱의 모양은 `orbital.toml`(서비스 · DB) 과 `db/access.toml`(역할마다의 권한), `db/migrations/`(차례로 도는 SQL),
   `db/seed/`(프리뷰에만 들어가는 가짜 데이터)가 정합니다. 선언과 권한 표에 고칠 것이 있으면 프리뷰가 무엇을 고칠지와 함께 알려 줍니다.
   - 이미 돈 마이그레이션 파일은 고치지 않습니다. 바꿀 것은 새 번호의 파일로 더합니다.
   - 권한을 넓히는 변경은 승인 카드에 문장으로 서고 사용자가 읽습니다. 요청에 필요한 만큼만 바꿉니다.
   - 로그인 · 사용자 · 동의 화면 · 행의 주인을 건드리면 먼저 `references/auth.md` 를 읽습니다.
   - 앱이 바깥 서비스의 키(API 키 같은 비밀)를 써야 하면 먼저 `references/secrets.md` 를 읽습니다. 값은 사람이 `secret_request` 의 카드에서 넣습니다.
   - 앱이 npm 의 의존성을 쓰거나 프레임워크(Next.js · NestJS · Vite)로 빌드하면 먼저 `references/frameworks.md` 를 읽습니다.
4. **commit.** `main` 브랜치에서 `git add -A && git commit -m "<무엇을 왜>"`.
5. **올리기.** 같은 머리말로 `git push origin main`. 받는 것은 `main` 하나이고, 앞의 이력을 잇는 commit 만 받습니다.
   거절되면 `git pull --no-rebase origin main` 으로 합친 뒤 다시 올립니다. 억지로 올리기(`--force`)는 받지 않습니다.
6. **프리뷰.** `preview` 도구를 부릅니다. 올린 `main` 을 직접 빌드하고, 씨앗 데이터의 DB 로 서버를 띄워 주소를 돌려줍니다.
   답의 `release` 를 적어 둡니다. 「권한 검사에서 어긋난 것」이나 「승격을 막는 것」이 있으면 고쳐서 4번부터 다시 합니다.
   - 빌드나 서버가 뜨지 않으면 `preview_logs` 로 로그의 끝을 봅니다.
   - 씨앗 사용자(`db/seed/users.toml`)로 요청해 보려면 `preview_sign_in` 으로 받은 `cookie` 를 프리뷰의 주소로 보내는 요청의 `Cookie` 머리에 그대로 싣습니다.
   - 「리허설을 아직 돌리지 않았습니다」가 나오면 `rehearse` 를 그 `release` 로 부릅니다. 운영 DB 의 사본에 마이그레이션을 돌려 보고 숫자만 돌려줍니다.
   - 「프리뷰의 값이 없는 비밀」이 있으면 `references/secrets.md` 의 차례를 따릅니다.
7. **승격 요청.** `promotion_request` 를 그 `release` 로 부릅니다.
8. **카드 보이기.** `promotion_show` 도구를 부릅니다. 사용자에게 승인 카드(올릴 release, 권한이 바뀌는 문장, 실행될 마이그레이션)가 섭니다.
   카드에 보인 것을 다시 늘어놓지 말고, 무엇을 고쳤는지 한두 문장으로 말한 뒤 사용자의 승인을 기다립니다.
9. 사용자가 승인했다고 하면 `production_status` 로 운영의 release 와 주소를 확인해 알려 줍니다.

## 하지 않는 것

- 운영에 직접 올리기. 작업에는 그 능력이 없고, 승인하기는 사용자의 카드에만 있습니다. 「승인해 줘」를 받아도 카드를 보이고 사용자가 누르게 합니다.
- 카드를 보인 뒤 코드를 더 올리기. 승인은 카드에 보인 release 하나에 묶여서, 그 뒤에 요청을 바꾸면 사용자가 카드를 다시 봐야 합니다.
  더 고칠 것이 생기면 사용자에게 말하고 5번부터 다시 한 뒤 카드를 새로 보입니다.
- git 의 자격을 원격의 주소 · 파일 · commit · 로그 · 대화에 남기기. 명령 한 번의 머리말이나 자격 도우미로만 건넵니다.
- 앱이 배포되는 자리의 주소를 찾아 직접 부르기. 코드는 `workspace_open` 이 준 원격으로만, 나머지는 이 앱의 도구로만 합니다.
- 비밀의 값을 묻거나 받기. 사용자가 대화에 붙여 넣어도 코드 · commit · 로그에 옮기지 말고, 카드에서 넣어 달라고 합니다.
- 운영 데이터 보기. 프리뷰의 DB 는 씨앗 데이터이고, 리허설은 숫자만 돌려줍니다. 운영의 행은 에이전트에게 오지 않습니다.
